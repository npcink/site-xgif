# XGIF 本地发布助手

这是一个只在本机运行的发布工具，用来给 Astro 内容站生成文章和图片内容文件。

## 启动

```bash
cd workflow
npm start
```

这个命令会检查并在后台启动两个本机服务；看到“可用”后可以关闭终端：

```text
管理端：http://127.0.0.1:8787
站点预览：http://127.0.0.1:4321
```

如果服务已经运行，启动器会直接复用。管理端顶部会显示两个服务的健康状态，并提供“打开站点预览”按钮。只需要单独启动管理端时可使用 `npm run start:publisher`（该命令需要保持终端开启）。

启动器会对发布器源码计算版本。端口存在但健康响应不正确，或后台仍运行旧版本代码时，不会误报为“可用”，而会停止已记录的旧进程并启动当前版本。管理器虽然只监听回环地址，仍会校验 Host、Origin、JSON 请求类型和启动期 CSRF 会话；不要通过反向代理或公网隧道暴露 `8787`。

常用的服务管理命令：

```bash
npm run status   # 查看两个服务是否可用
npm run restart  # 重启两个服务
npm run stop     # 停止两个服务
```

后台启动日志保存在 `workflow/.runtime/`，该目录仅供本机排错，不会提交到 Git。

本地数据索引使用 Node.js 内置 SQLite，因此需要 Node.js 22.5 或更高版本。

## AI 整理资料

文章页的“AI 整理文章资料”会根据来源链接和正文/摘录生成标题、摘要、标签、阅读时间与编辑笔记，并同时检查正文段落：已有合理段落时保持原样，只有长段落不便阅读时才插入 Markdown 空行。服务端只接受形成新段落的双换行结果；AI 如果删除、改写任何正文字符、只插入普通单换行或合并已有段落，会丢弃段落结果并保留原文。超过 12,000 字的正文只整理元数据，页面会明确提示段落未处理。图片页的“AI 整理图片资料”会根据选中的图片生成标题、描述、标签、情绪和使用场景。结果会先显示为一张简要复核卡，详细字段默认收起，需要调整时再展开。

发布器使用 OpenAI 兼容的 Chat Completions 接口。AI 配置放在 `workflow/.env`；密钥只保留在本机服务端，不会发送到浏览器，也不会被 Git 跟踪。

```bash
XGIF_AI_API_KEY="你的密钥"
XGIF_AI_MODEL="你的模型名称"
# 可选：兼容服务或自建网关地址；默认 https://api.openai.com/v1
XGIF_AI_BASE_URL="https://api.openai.com/v1"
```

首次使用时，可从 `.env.example` 复制一份为 `.env` 后填写。修改 `.env` 后重启本地发布器即可生效。未配置时，发布器仍可正常手动发布内容；AI 按钮会提示缺少配置。

## 写入位置

- 文章：`site/src/content/articles/*.md`
- 图片内容：`site/src/content/images/*.md`
- 新图片文件：启用 R2 后写入 `xgif-memes-prod/memes/<sha256>.<ext>`
- 旧图片文件与本地回退：`site/public/images/memes/<year>/*`

## 内容库与真实预览

发布助手采用“左侧菜单、右侧工作区”的 PC 固定布局：内容入口集中在“内容”，“内容体检与标签”是独立管理工作区；回收站保留为短时恢复弹窗并在侧栏显示数量；同步记录并入“系统状态与恢复”的子页面。工作区和系统子页面会写入 URL，刷新和浏览器前进/后退会恢复当前位置。发布助手只面向本机桌面浏览器使用，移动端不属于产品与验收范围。

“内容库”把草稿、待同步、待上线、待验证、已上线分开筛选，并为每个阶段只突出一个下一步动作。“待验证”只表示本次线上核对失败，不会把上次已经确认上线的内容误降级为“待同步”。顶部任务摘要优先提示尚未完成的发布流程；内容、Git、云端三条状态轴在详情中分别显示。列表默认只突出标题、状态、日期和标签，摘要按需展开，排序、每页数量、内容体检、刷新、回收站和显示方式统一收在“筛选与工具”中。

点击整行只会查看当前内容；复选框和批量工具只在进入“批量管理”后出现，避免把当前查看误认为批量选择。批量模式支持当前页全选，并可继续扩展为“选择符合筛选的全部内容”；从全部结果中取消某一项时，该项会作为排除项保留。“发布到本地”可直接处理所选草稿；“退回草稿”收在“更多操作”中。服务端会先按状态统计可处理、跳过和失败数量。批量发布仍会逐条执行质量检查，失败项保持原状态，发布日期保持不变。退回草稿或删除已上线内容只会先改变本地站点，必须继续同步 Git 与 Cloudflare 后，线上页面才会下架。

“编辑属性”可以对所选内容追加、删除或替换标签，也可以批量修改分类、来源名称和发布日期。只有在弹窗中明确勾选的字段才会修改；发布中的内容仍会通过原有质量检查，失败项会保留选中以便调整后重试。

“内容体检与标签”使用独立工作区，同时提供检查结果与标签治理：展示每个标签的文章、图片、草稿和公开使用数量，标出不在规范词表中的标签。标签合并必须先选择来源标签和规范目标标签、预览受影响内容，再经确认写回 Markdown；成功后会刷新 SQLite 索引并创建私有内容快照。

素材库会同时显示使用次数、缺失替代文字和重复文件提示。文章正文支持粘贴或拖入图片，也可以从已有素材中复用；上传到正文的图片存放在 `site/public/images/articles/`，不会覆盖原文件。

“同步当前内容”和批量模式中的“同步所选”都会跳过草稿；如果当前位于受保护的 `main`，管理器会创建 `content-sync/<时间>` 内容分支，只提交所选文件并推送到远程仓库。推送完成后仍需创建并合并 PR，Cloudflare 部署完成且云端内容核对通过后，状态才会变为“已上线”。

同步前会自动执行“内容体检”。只有“可直接上线”的内容可以进入 Git 同步；来源链接无效、来源待确认、图片文件缺失等硬错误会退回草稿，首页级来源链接、临时标题、正文过短或重复来源等情况会要求人工确认。“内容体检与标签”工作区可以查看全部结果；“系统状态与恢复 → 同步记录”保存最近的批量同步分支、提交和比较链接。

也可以在终端生成完整检查报告：

```bash
npm run content:audit
```

结果写入 `workflow/records/content-audit-latest.md` 和 `.json`。这是发布前报告，不代替 Markdown、GitHub PR 或 Cloudflare 线上核验。

工具栏的“回收站”可以查看并恢复任何尚未永久清理的内容，不依赖当前浏览器。“移至回收站”只移动 Markdown，不删除图片文件或 R2 对象；最近一批删除可以撤销。回收站支持全选、批量恢复和明确确认后的永久删除；永久删除仍不会清理图片文件或 R2 对象。每个回收站 Markdown 都有独立 `.meta.json` 旁车；SQLite 丢失后会从这些文件重新建立列表。

## 本地数据安全

文章正文和图片元数据仍以 `site/src/content/**/*.md` 为公开权威源；外部来源文章同时在 `workflow/private-sources/articles/<contentId>.md` 保留本地私有正文副本，用于编辑恢复和异地私有备份。SQLite 只保存可重建的内容索引、回收站索引、本地操作历史和同步记录。数据库位于 `workflow/.runtime/xgif.sqlite3`，不会进入 Git；数据库迁移、重建代码和公开内容文件才进入公开 Git。

发布台启动时会检查数据库完整性。发现损坏时会先把原数据库隔离为 `.corrupt-*`，然后扫描 Markdown 与回收站旁车自动重建。常用维护命令：

```bash
npm run data:status   # 查看索引中的内容数、回收站数量与最近重建时间
npm run data:rebuild  # 主动从 Markdown 和回收站旁车重建索引
npm run data:backup   # 备份 SQLite，并为全部内容创建本机私有 Git 快照
npm run data:verify-recovery # 用当前真实内容和临时数据库演练损坏重建
npm run test:recovery # 在临时目录模拟数据库损坏和恢复，不触碰真实内容
```

备份保存在 `workflow/backups/`，不会进入公开仓库。其中 `content-history.git` 是独立的本机私有 Git 仓库，只白名单保存 Markdown、私有来源正文、内容台账、回收站和本地图片；`.env`、SQLite、日志和程序文件不会进入。发布台启动和每次内容变更后都会自动创建快照，手动“创建本地安全备份”会同时更新内容快照并备份 SQLite。

本机私有 Git 可以防止误删和误改，但仍和原文件处在同一台电脑。当前内容历史仓库已单独配置私有 GitHub 远端 `npcink/site-xgif-private-content`；每次安全快照都会尝试推送 `history` 分支，失败只会在备份结果中提示，不会阻断本地内容保存。不要把这个远端改成公开仓库，也不要把私密草稿推送到站点公开仓库。

管理端右上角会显示“内容 Git：已记录当前版本数/内容总数”。未跟踪文件或提交后又修改的文件不会计为已记录；这能防止把“文件在本机”误认为“已经进入 Git”。当前 `origin` 是公开仓库，因此发布台不会自动把草稿当作远程备份推送，私有草稿备份需要另行配置私有远程或加密备份目标。

左侧“系统状态与恢复”进入独立页面，按“运行状态 / 同步记录 / 恢复与备份”组织本机服务、AI、Git、R2、部署预览、联网边界和恢复操作，不再用浮层遮挡内容列表。数据安全状态会汇总 SQLite 备份数量、最近私有内容快照、最近恢复演练和 R2 本地对账。恢复演练会在临时目录模拟 SQLite 损坏并从真实 Markdown 与回收站旁车重建临时数据库，不修改真实数据库或内容文件；演练结果写入本机 `.runtime/recovery-drill.json`。

草稿预览路由只在 `astro dev` 中生成，生产构建不会输出 `/preview/` 页面。编辑器右侧的“列表卡片 / 文章页”用于快速检查输入；“真实预览”显示最后一次保存到 Markdown 的版本。

## 从 flomo 批量导入

“批量导入”接受 flomo 官方导出的 ZIP，并在本机完成解析、正文指纹查重和草稿生成。原始 ZIP 不会保存到仓库，也不会上传 Cloudflare；解析后默认勾选所有非精确重复内容，可用一个按钮全选或取消全选。短笔记、缺少候选标题或与现有文章高度相似的内容仍会显示提示，但不增加额外选择步骤；精确重复会自动禁用。

导入器会检查 memo 正文任意位置的 http/https 链接，包括独立链接、Markdown 链接以及“链接 / 来源 / 原文 / 出处：URL”格式。只有一个可信链接时会自动写入 `sourceUrl`；多个链接时优先采用唯一明确标注为来源的链接，否则标记为“需要整理”，不会擅自猜测。独立的来源链接行会从正文移除，正文语句中的上下文链接仍会保留。

来源名称会按域名规范化：`jandan.net` 显示为“煎蛋”，`zhihu.com` 显示为“知乎”，`hupu.com` 显示为“虎扑”，`ngabbs.com` 显示为“NGA 玩家社区”。其他未收录域名统一显示为“第三方”。未检测到链接的 flomo 内容默认使用 `sourceKind: "unknown"` 和“来源待确认”，只能保存为草稿；补充来源链接或主动改为原创后才能发布。

文末的 `#标签`、`- #标签`、`* #标签` 和 `+ #标签` 都会从正文剥离。描述文章内容的标签进入公开 `tags`；`故事汇`、`sq`、`煎蛋` 等仅用于 flomo 整理的分组标签不会公开展示，只写入本地 flomo 导入台账的 `importTags`，用于追溯导入批次。

已导入文章可随时执行来源审计。来源推断和“来源待确认”只会作用于草稿；已经发布的文章只清理与结构化字段完全重复的来源行和末尾导入标签：

```bash
npm run source:audit --prefix workflow
npm run source:audit:apply --prefix workflow
npm run data:rebuild --prefix workflow
```

第一条命令只显示可安全修复项；第二条只应用有明确证据的链接和来源名称，并把没有来源证据的 flomo“原创”改为“来源待确认”；第三条从 Markdown 刷新本地 SQLite 索引。

导入结果始终是 `draft: true` 的 Markdown 草稿，不会自动提交或推送。若点击“AI 整理选中项”，只有当前勾选的正文和来源元数据会发送给 `.env` 中配置的 AI 服务；安全通过的分段结果会随草稿保存，并在服务端再次逐字校验，正文仍只能新增 Markdown 空行，不能改字或删文。外部来源草稿发布时，完整正文会写入公开 Markdown，并在本机 `private-sources/articles/` 保留备份；再次退回草稿时，管理端仍可从私有副本恢复正文供编辑。每次成功导入会在 `records/flomo-imports.jsonl` 追加正文哈希、时间和目标文件；台账不保存正文。完整边界见 [`ADR-010`](../site/docs/decisions/ADR-010-external-article-full-body-publication.md)。

文章备注分成两个字段：`editorNote` 是可以显示给读者的“公开编辑手记”，`internalNote` 是只在本地内容库中显示的复核提醒。AI 只会建议公开编辑手记；flomo 导入批次、来源待核验等内部信息必须写入 `internalNote`，不能进入公开页面。

默认 ZIP 上限为 10 MB、解压后上限为 50 MB，可按需在 `.env` 中调整：

```bash
PUBLISHER_MAX_IMPORT_ZIP_BYTES="10485760"
PUBLISHER_MAX_IMPORT_UNCOMPRESSED_BYTES="52428800"
```

## 发布流程

文章页使用“保存草稿 → 真实预览 → 发布到本地 → 同步到云端”的固定流程。底部下一步操作一次只突出当前主动作；技术服务、Git 与同步工具默认收在“系统详情与工具”中。

文章正文旁的“选择已有素材”会读取图片 Markdown、R2 台账、本地文件和私有备份状态；选中后只向正文插入 Markdown 图片语法，不会重新上传或复制对象。文章详细资料还可以从同一素材库选择可选封面；`coverImage` 同时用于文章页首图和社交分享图，`coverAlt` 用于替代文字。正文中的二级、三级标题会自动生成文章目录，不需要另行维护。

1. 粘贴文章正文，可按需使用 AI 整理资料；先看简要结果，需要时再展开“详细资料”修改。
2. 保存草稿到 Markdown。输入中的修改会按内容分别暂存，并保留最近 20 个浏览器检查点；“版本历史”还可以读取本机私有 Git 快照并恢复指定 Markdown 版本。尚未保存时会明确显示状态，离开页面或关闭窗口时会提醒。
3. 使用右侧“真实预览”打开与线上相同的 Astro 文章模板。修改后必须重新保存，预览不会伪装成已保存版本。
4. 点击“发布到本地”。主按钮会自动执行重复检查与质量检查，成功后内容进入本地公开站点和“待同步”列表。
5. 在“待完成”中打开内容并执行它所显示的下一步；受保护的 `main` 会创建内容分支，合并 PR、Cloudflare 部署和线上核验完成后才显示为“已上线”。
6. 只想检查而暂不保存时，可点击“仅检查”。服务端在真正写入前仍会执行相同校验，不能绕过页面直接重复发布。

标题不满意时，可在“文章详细资料”的标题字段旁点击“AI 换标题”。一次只生成 3 个新的候选标题；选择候选只修改标题并进入未保存状态，不会覆盖摘要、标签或正文。正文、摘要或来源链接发生变化后，旧候选会自动失效，需重新生成。

图片页继续提供“立即发布”与“保存为草稿”，使用相同的未保存提示和质量检查；后续云端同步边界与文章一致。

发布台会自动为新内容生成 `YYYYMMDD-4位小写字母数字` 的稳定 ID，并同时用作 Markdown 文件名与公开 URL。不要手工修改已经生成的 `contentId`；标题和发布日期可以继续调整，不会改变公开地址。旧内容的一次性迁移命令是 `npm run content:ids:migrate`。

发布已有文章草稿时：

1. 在“内容库”选择草稿，点击“复核并发布”。
2. 选择保留 flomo 原始日期，或使用今天作为正式发布日期。
3. 点击“检查并发布草稿”。前端和服务端都会强制执行文章质量检查；错误会阻止发布，重复、正文为空或标签过多等警告需要人工确认。
4. `draft: false` 只表示内容已进入本地公开站点；内容库会继续显示“待同步、同步未完成或待上线”，直到云端页面通过内容匹配验证后才显示“已上线”。Git 提交、推送和部署细节可在“同步与技术信息”中查看。
5. 已发布文章可以通过相同入口“退回草稿”，下一次构建后将从公开站点移除。

## Cloudflare R2 图片存储

R2 是新图片的可选存储层，不是线上 CMS。标题、来源、授权和发布状态仍由 Markdown 与 Git 管理；D1、Vectorize 和线上后台不在这条链路中。已有 `site/public/images/memes/` 图片不会自动迁移。

启用前先安装站点依赖并完成一次 Cloudflare 登录：

```bash
cd site
npm ci
npx wrangler login
```

确认 Cloudflare 中已经存在 Bucket `xgif-memes-prod`，并将 `img.xgif.cn` 作为 R2 自定义域名后，在 `workflow/.env` 设置：

```bash
XGIF_R2_ENABLED="true"
XGIF_R2_BUCKET="xgif-memes-prod"
XGIF_R2_PUBLIC_BASE_URL="https://img.xgif.cn"
```

启用后，发布器会先校验图片并计算 SHA-256，再通过仓库锁定的 Wrangler 上传至 `memes/<sha256>.<ext>`，写入 `Cache-Control: public, max-age=31536000, immutable`，并验证自定义域名可以读取对象。上传验证后会先写入 R2 台账，再原子写入 Markdown；如果后续本地写入失败，台账会留下可检测的孤立记录，不会静默遗失远端对象。

远端对象与本机私有原始字节备份：

```bash
npm run r2:backup
npm run r2:reconcile
```

`r2:backup` 会按 SHA-256 下载、核验并保存 R2 原始字节，再推送到已配置的私有内容历史；`r2:reconcile` 会比较图片 Markdown、台账、真实远端对象和私有字节，列出可恢复的不一致状态。

R2 清理默认只观察，不删除：

```bash
npm run r2:cleanup
```

孤立对象必须连续无引用满 30 天、远端状态正常且私有字节备份完整，才会进入候选列表。删除时还必须明确输入一个完整对象键：

```bash
npm run r2:cleanup -- --confirm-delete memes/<完整sha256>.<ext>
```

命令一次只能删除一个内容寻址对象，并记录独立删除台账。不要批量拼接对象键，也不要手工绕过观察期。

线上保护固定为：`/memes/` 一年 Edge TTL、外站非空 Referer 拦截、查询串拦截，以及排除已验证机器人的单 IP `200 次/10 秒` 限速。空 Referer 仍允许，以兼容直接访问和消息应用预览；因此这套规则用于降低盗链与刷流量成本，不是私有访问控制。R2 图片 URL 不支持查询参数。

如需临时回到原来的 Git 图片目录，将 `XGIF_R2_ENABLED` 设为 `false` 并重启发布器即可；已经发布的 R2 URL 不受影响。

在非 `main` 内容分支勾选 Git 选项后，会执行：

```bash
git add <生成的文件>
git commit -m "Add ..."
git push
```

`main` 是受保护分支，管理端会停用自动提交和推送，服务端也会拒绝绕过页面直接提交。请先切换到内容分支，通过 `Astro site` 检查后再合并部署。只想生成本地文件时，取消 Git 选项即可。

## 图片发布保护

默认仅接受 JPEG、PNG、WebP 与 GIF，单文件不超过 8 MB，单边尺寸介于 160 和 6000 像素之间。文件名或浏览器声明的格式不作为判断依据，发布器会按文件内容校验。需要调整本机限制时，在 `.env` 中设置：

```bash
PUBLISHER_MAX_IMAGE_BYTES="8388608"
PUBLISHER_MIN_IMAGE_DIMENSION="160"
PUBLISHER_MAX_IMAGE_DIMENSION="6000"
```

这些限制仅影响本地发布台；网站构建和线上静态站点不读取这些变量。R2 的单对象限制不能替代这里的发布校验。

## 用户提供素材台账

选择“用户提供素材”发布图片时，请填写“公开发布确认日期”。发布台会在 `workflow/records/user-provided-assets.jsonl` 自动追加最小授权记录，并和内容文件、图片位置台账一起提交。该台账不参与 Astro 构建，不会在网站公开页显示；只保留确认日期、资源哈希、资源文件或 R2 地址与公开范围，禁止记录真实姓名、联系方式或原始素材链接。详见 [`records/README.md`](records/README.md)。

## 群聊转存与来源未知图片

从微信群、QQ 群等渠道保存且无法确认作者或授权的图片，选择“群聊转存 / 来源未知”即可直接发布；`source`、`sourceUrl`、`author`、`license`、`licenseUrl` 不需要填写，也不会由 AI 虚构。生成的 Markdown 使用 `sourceKind: "unknown"` 并明确标记“群聊转存（来源待核实）”。

这类图片的公开详情页会链接到 `/rights/`，权利人可通过 `1355471563@qq.com` 提交内容链接与权利说明，申请更正或下架。“来源待核实”和投诉入口用于如实披露与后续处理，不代表已经取得原作者授权。

## 说明

公开站点不需要数据库，也不会启动线上后台。本地发布台使用可删除重建的 SQLite 管理索引，Astro 只读取公开 Markdown 和图片文件。原创文章可以不填写外部来源链接；转载和编辑整理内容仍必须保留真实来源链接，完整正文会进入公开 Markdown，并在本机私有来源库保留备份。数据边界见 [`ADR-007`](../site/docs/decisions/ADR-007-local-sqlite-index.md) 与 [`ADR-010`](../site/docs/decisions/ADR-010-external-article-full-body-publication.md)。
