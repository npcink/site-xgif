# 成人幽默内容复核与离线推荐优化复盘

日期：2026-07-28

## 1. 本阶段目标

本阶段解决两个连续问题：

1. 从导入草稿中筛选、复核并本地发布一批成人幽默文章；
2. 让这些文章更容易在彼此的相关推荐中出现，同时不把它们推荐到普通文章下面。

实现继续遵守 ADR-012 的离线混合推荐架构：线上站点只读取静态内容 ID 清单，不增加在线模型、向量数据库、用户画像或实时推荐服务。

## 2. 关键约束

- 内容分组必须由人工确认，不能让模型自动判断；
- 普通内容必须硬排除成人幽默文章，不能只依赖相似度权重；
- 草稿、非公开内容、当前文章自身和失效 ID 不能进入推荐；
- M4 Ollama、SSH 隧道、SQLite 向量缓存和环境变量只存在于本机；
- 模型不可用时仍可生成规则推荐，但严格验收必须使用 `--require-embeddings`；
- 发布到本地、提交 Git、推送分支、部署上线是四个不同状态；
- 来源核对不等于获得转载许可，来源链接与版权处理流程仍需长期保留。

## 3. 最终方案

### 3.1 使用显式推荐分组

文章新增可选字段：

```yaml
recommendationGroup: "adult-humor"
```

未填写或填写 `general` 的文章属于普通内容。发布器只接受 `general` 和 `adult-humor`，无效值直接拒绝；管理界面要求人工选择，不由 AI 自动标记。

推荐分组不是标签。标签继续描述内容主题，分组只承担推荐边界。这样可以避免“婚姻”“生活”“情感”等宽泛标签把成人内容带入普通文章。

### 3.2 在所有推荐路径执行隔离

隔离不能只加在向量排序阶段，必须覆盖：

- 规则候选过滤；
- 混合向量优先结果；
- 静态清单中的 `preferredIds`；
- 相关内容补位；
- 稳定探索位；
- Astro 运行时对静态清单的再次校验。

普通内容始终排除 `adult-humor`。成人幽默文章优先并保留同组候选，即使共享标签或词面相似度很低，也不会被通用阈值提前丢弃。

推荐源哈希包含分组信息。文章只要改变推荐分组，静态清单就会被识别为需要重建，不能继续沿用旧分组结果。

### 3.3 兼顾相关性与完整覆盖

最初的混合排序已经能让成人幽默文章彼此优先，但 10 篇一起发布后发现：《南京旅行后的备孕玩笑》没有任何入站推荐。只检查“每篇都有三条同组推荐”仍不足以证明用户可以持续浏览。

最终保留两个相关性位置，并为成人幽默组增加一个确定性的覆盖边：

```text
前两个位置：向量相似度 + 规则相关度 + 新鲜度
第三个位置：必要时指向按稳定 ID 顺序排列的下一个同组条目
```

覆盖边只作用于已公开的成人幽默文章，明确忽略草稿和非公开内容。这样不需要在线状态、全局画像或复杂图算法，也能保证整个组从任意一篇出发最终可达。

## 4. M4 Ollama 向量链路

模型运行在 M4：

```text
qwen3-embedding:0.6b
1024 dimensions
```

Ollama 继续只监听 M4 的 `127.0.0.1:11434`。开发机通过临时 SSH 隧道映射到本机 `127.0.0.1:11435`，发布器使用 OpenAI 兼容的 `/v1/embeddings` 接口。

严格生成命令：

```bash
cd workflow
npm run recommendations:build -- --require-embeddings
```

向量本身只保存在本机 SQLite，可删除和重建；Git 只提交小型静态 ID 清单。

生成时使用隔离的 Git 快照，只加入本次确认提交的 10 篇文章。当前工作区里其他未提交的公开文章和图片不会进入这份清单，避免远端清单引用尚未提交的内容。

复核步骤：

1. 逐篇请求具体来源 URL，确认最终地址和 HTTP 200；
2. 把正文拆成足够长的文本片段，与来源页面逐段匹配；
3. 人工检查标题、摘要、成人关系、胁迫风险和未成年人风险；
4. 修正占位标题与过长标题；
5. 只通过插入 Markdown 空行拆分过长段落，不删除或改写原文字符；
6. 标记内部复核完成；
7. 运行发布前内容审计；
8. 先发布 2 篇试点，再发布剩余 8 篇；
9. 每次发布后重建向量清单并检查页面级推荐结果。

导入日期没有自动改成来源页面日期。仓库允许保留 flomo 记录日期或人工选择当天日期；来源日期和导入记录日期表达的事实不同，不能在没有产品决定时混为一谈。

## 7. 暴露的问题与修正

### 7.1 只验证单篇结果不足以证明推荐网络有效

两篇试点时，互相作为第一推荐即可说明基本隔离成立；扩展到 10 篇后，必须检查入站覆盖和图可达性。否则某篇文章虽然有三条推荐，却可能永远不会被其他文章推荐。

改进：验收同时检查每篇推荐位、普通内容泄漏、草稿泄漏、目标完整性和组内全可达。

### 7.2 分组优先必须早于通用相关度阈值

同组文章可能使用不同措辞和标签。若先套用通用相关度阈值，再考虑分组，稀疏内容会被提前丢弃。

改进：成人幽默同组匹配本身就是保留条件，之后再用向量和规则决定顺序。

### 7.3 静态清单不能成为绕过运行时边界的后门

旧清单或手工清单可能包含已经不允许的跨组 ID。

改进：Astro 运行时读取 `preferredIds` 时再次执行分组、草稿、公开状态和自引用检查。

### 7.4 生成成功不等于使用了向量

默认命令在端点不可用时会安全回退到规则模式。只看退出码 0，可能误把规则清单当成混合向量清单。

改进：正式验收使用 `--require-embeddings`，并检查输出中的 `mode`、模型和维度。

### 7.5 HTTP 404 需要先核对路由契约

测试时最初使用了带末尾斜杠的本地地址，得到 404。内容已经存在，真实原因是站点明确使用无尾斜杠路由。

改进：先用一个已知公开页面对照路由格式，再判断是缓存、构建还是地址错误。

## 8. 可复用的开发经验

### 8.1 用确定性边界约束概率排序

模型只负责“同一允许集合里谁更相关”。能否进入集合、是否公开、是否跨组、是否需要覆盖，全部由确定性代码决定。

### 8.2 小规模内容不需要重型推荐基础设施

当前规模使用本地嵌入缓存、静态清单和构建时校验已经足够。增加在线向量库、实时服务或用户画像只会扩大故障面、隐私面和维护成本。

### 8.3 先小批量试点，再扩展语料验证系统性质

2 篇适合验证发布链路和基本互推；10 篇才能暴露覆盖盲点。试点通过后仍需重新定义适合更大集合的验收指标。

### 8.4 生成产物也需要来源哈希与回归测试

静态清单不是随手生成的缓存，而是线上会直接使用的代码产物。影响候选集合的元数据必须进入来源哈希，关键边界必须有回归测试。

### 8.5 内容复核与版权判断保持分离

来源 URL 可访问、正文与来源一致，只能证明来源链和内容完整性；不能自动证明转载授权。公开页面仍需保留来源、版权更正和下架通道。

### 8.6 状态名称必须诚实

本地 `draft: false` 只表示本地站点可见。Git 提交、远端推送、PR 合并、Cloudflare 部署和线上内容核验仍是独立阶段，不能统称为“已上线”。

## 9. 后续维护步骤

新增或调整成人幽默文章时：

```text
核对来源和正文
→ 人工确认 recommendationGroup
→ 通过内容审计
→ 本地发布
→ 使用 --require-embeddings 重建
→ 检查 mode/model/dimensions
→ 验证同组推荐、普通内容零泄漏和组内可达性
→ 运行 workflow 与 site 完整测试
→ 再提交和部署
```

如果未来组内文章显著增加，先观察真实点击和人工质量抽查，再决定是否调整两个相关位置的权重。不要在没有真实问题时增加实时服务、更多模型或复杂配置。
