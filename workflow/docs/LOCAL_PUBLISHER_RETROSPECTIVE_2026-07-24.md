# XGIF 本地发布助手阶段复盘

## 文档目的

本文记录 2026-07-24 前后围绕 XGIF 本地发布助手完成的一轮连续产品化改造，覆盖参考产品分析、发布流程、内容治理、恢复能力、素材复用、AI 辅助、内容管理布局和桌面工作区收尾。

它不是功能清单的重复，而是回答四个长期问题：

1. 为什么本地发布助手采用现在的结构；
2. 哪些参考产品经验值得吸收，哪些不应照搬；
3. 本轮开发中出现了哪些具体问题，为什么会返工；
4. 后续扩展功能时应遵守什么判断和验收方法。

## 产品边界

XGIF 仍然是静态内容站，不是传统在线 CMS。

- `site/` 是公开 Astro 站点和生产部署边界；
- `workflow/` 是只监听本机的单人发布助手；
- Markdown、图片元数据、Git 和 R2 台账是内容权威源；
- SQLite 只保存可重建的索引、操作历史和缓存；
- AI 只在用户主动点击时调用，并且输出是建议，不是自动发布决定；
- 本地发布助手只验收 PC 桌面端，不为移动端增加另一套布局和交互成本。

因此，参考 Gridea、WordPress 等产品时，学习目标是成熟的工作流和信息组织，不是把本项目扩张成完整 CMS。

## 演进过程

### 1. 从参考产品中提炼发布流程

最初参考 Gridea 的价值，在于确认内容发布不是一个“保存”按钮，而是一条可解释的状态链：

```text
提供原始内容
→ 保存草稿
→ 真实预览
→ 发布到本地
→ 同步 Git
→ 等待部署
→ 线上核对
```

落地时没有复制 Gridea 的整套桌面客户端，而是把流程压缩到 XGIF 真正存在的 Markdown、GitHub 和 Cloudflare 边界中。编辑器开始明确显示下一步操作，内容详情分别展示内容、Git 和云端状态，避免把“本地文件已保存”误写成“已经上线”。

### 2. 建立内容治理和恢复能力

随后按“标签治理 → 素材复用 → 恢复状态看板 → 封面与目录”推进：

- 标签治理统计真实使用量，区分规范标签和待合并标签；
- 标签合并必须先预览受影响内容，再确认写回 Markdown；
- 素材库统一读取图片内容、R2 台账、本地文件和备份状态；
- SQLite 损坏恢复、私有内容快照、R2 对账进入系统状态；
- 文章支持可选封面、替代文字和由正文标题生成的目录。

这部分形成了一个重要原则：管理功能不能另建内容权威源，只能检查、组织和安全修改现有 Markdown 与台账。

对应提交：`8a6160a feat: govern local publishing workflow`。

### 3. 增加本地收藏，但保持读者数据本地化

收藏功能使用浏览器本地存储，不增加用户账号和线上数据库。随后补充导入、导出和独立收藏页，使数据可以由用户自行备份和迁移。

这说明“本地优先”不等于功能简陋。只要提供稳定 ID、版本化导出格式、重复处理和失败反馈，本地功能同样可以做到可恢复、可迁移。

对应提交：`8399148 feat(site): improve discovery and local favorites`。

### 4. 重做内容管理流程

早期内容管理同时显示列表、详情、状态和大量操作，重要动作缺少层级。后续改成更接近 WordPress 的“左侧菜单、右侧工作区”桌面结构，并完成：

- 内容库按草稿、待同步、待上线、待验证和已上线筛选；
- 当前查看与批量选择分离；
- 列表只保留标题、状态、日期和标签等高频信息；
- 详情作为次级上下文，不再和列表争夺同等视觉权重；
- 批量发布、同步、退回草稿、编辑属性和回收站形成明确动作组。

这里学习的是 WordPress 的稳定信息架构，而不是其视觉样式和历史包袱。

对应提交：`b62cf32 feat(workflow): redesign content management flow`。

### 5. 把 AI 从“黑盒整理”改成可控建议

用户反馈暴露了两个问题：

- “AI 整理文章资料”禁用时只表现为灰色，原因不够清楚；
- 自动生成的标题不满意时，只能重新整理整篇资料，成本和风险都过高。

因此，AI 被拆成两种范围不同的动作：

- “AI 整理文章资料”生成标题、摘要、标签等整套建议；
- 标题字段旁的“AI 换标题”一次生成三个新候选，只修改用户选中的标题。

候选标题在正文、摘要或来源发生变化后失效，避免把旧上下文生成的结果误用到新内容。AI 仍不自动保存、不自动发布，也不覆盖正文。

### 6. 系统性完善桌面控制台

桌面控制台继续补齐自动保存版本、Markdown 工具栏、内容分页、批量管理、发布状态语义、私有备份和真实浏览器测试。此时管理端已经从“几个表单”发展为稳定的本地工作台。

对应提交：`f0a5a3e feat(workflow): improve desktop publishing console`。

### 7. 收尾一级导航与弹窗边界

最后一次视觉检查发现，“内容体检与标签”“回收站”“同步记录”虽然都放在一级导航中，却全部打开弹窗，用户无法从入口判断接下来是切换页面还是执行临时任务。

收尾改造按任务复杂度重新选择容器：

| 功能 | 最终容器 | 原因 |
| --- | --- | --- |
| 内容体检与标签 | 独立工作区 | 长任务、信息密集、需要刷新和保留位置 |
| 回收站 | 模态弹窗 | 短时、聚焦、处理后返回原工作区 |
| 同步记录 | 系统页子页面 | 属于运行与发布证据，不应占用管理一级入口 |

同时增加：

- 回收站侧栏数量；
- 弹窗关闭后的焦点恢复；
- `#audit`、`#system/sync` 等工作区 URL；
- 刷新、浏览器前进和后退的位置恢复；
- 运行状态、同步记录、恢复与备份三个系统子页面。

### 8. 把正文整理合并进 AI 分析，但用确定性校验保护原文

长篇导入内容经常只有一个超长段落，直接阅读困难。最终没有增加单独的“整理段落”按钮，而是把段落判断合并到现有 AI 分析中：

- 原文本来已有合理段落时不调整；
- 只有段落明显过长时才建议插入空行；
- AI 不得删字、改字、改标点或重写句子；
- 服务端移除换行后逐字比对原文，任何不一致都拒绝采用；
- AI 失败或结果不合规时保留原文。

关键不是提示词写得更严，而是把“文章绝不能被删改”变成代码可验证的不变量。AI 负责判断阅读节奏，程序负责守住内容完整性。

### 9. 统一内容阅读入口并收紧详情弹窗

文章和图片都属于内容，因此详情地址统一为 `/<contentId>`，例如 `/20260711-sdiy`，不再按类型暴露两套路由，也不保留尾部 `/`。当前没有历史用户和外部链接负担，因此直接切换，不增加无意义的重定向兼容层。

文章弹窗也从“只有大标题和大摘要”调整为真正的阅读容器：

- 摘要降级为紧凑导语，不再占据首屏主体；
- 正文进入弹窗内部，段落之间保留合适空行；
- 正文结束后展示三条相关或探索内容；
- 来源按钮、独立文章页和关闭动作保持清晰分工；
- 独立详情页与弹窗共用相同内容 ID 和推荐逻辑。

推荐内容放在正文之后，而不是为了塞推荐强行缩短正文区域。长文章继续自然滚动，读完后才进入下一步发现。

### 10. 图片详情按“完整查看”而不是“卡片封面”处理

图片库卡片使用 `cover` 可以保持网格整齐，但详情页的任务是看完整内容，必须使用真实宽高比和 `contain`。本轮修复了详情主图被横向容器裁切的问题，并同步收敛右侧标题、描述和栏间距：

- 优先使用元数据中的真实 `width / height`；
- 缺失尺寸时才按横图、竖图、方图回退；
- 详情页和详情弹窗使用 `object-fit: contain`；
- 卡片封面继续使用原有裁切逻辑；
- 标题和描述采用响应式上限，避免标题压过图片。

同一张图片应该用 `cover` 还是 `contain`，取决于当前容器是浏览缩略图还是查看原内容。

### 11. 分两阶段建立离线混合推荐

推荐能力按复杂度分两阶段落地：

1. 第一阶段用标签稀有度、标题、摘要、分类、情绪、场景和稳定探索位做确定性排序；
2. 第二阶段用本地 `qwen3-embedding:0.6b` 向量重排规则候选。

向量只在本地生成并缓存在可重建 SQLite 中，最终只把内容 ID 清单写入 `site/src/data/recommendations.json`。线上 Astro 页面不依赖模型、隧道、SQLite 或在线向量服务；清单缺失、过期或包含已删除 ID 时，页面会过滤并用规则补足。

发布助手只在“系统状态与恢复”中提供一处推荐状态和更新动作，显示模式、模型、覆盖率、新鲜度和本地向量配置状态。没有给每篇文章增加开关，也不会在向量服务不可用时用一次普通更新静默覆盖已经存在的混合清单。

架构取舍详见 [`site/docs/decisions/ADR-012-offline-hybrid-recommendations.md`](../../site/docs/decisions/ADR-012-offline-hybrid-recommendations.md)。

### 12. 清理页面标题重复，建立单一 H1 契约

内容库、内容体检和系统页一度同时显示顶栏标题与内容区旧标题，形成“系统状态与恢复 / 系统状态与恢复”这类重复。根因不是文案重复，而是全局工作区标题已经接管页面语义后，旧组件仍保留自己的页面级标题。

最终约束为：

- 每个工作区只有一个页面级 `h1`；
- 页面内部模块从 `h2` 开始；
- 顶栏标题承担当前位置和页面语义；
- 内容区只保留任务说明、状态和操作；
- 浏览器回归测试直接统计关键工作区的标题文本和 `h1` 数量。

这类问题只看单个组件不容易发现，必须同时检查完整页面、DOM 层级和真实桌面截图。

### 13. 分离公开代码 GitHub 与私有内容 GitHub

收尾时发现，主工作区中的草稿和导入台账会被普通 `git status` 显示为修改或未跟踪文件。如果管理端只显示一个“Git 与 PR”状态，用户无法判断这些内容究竟应该进入公开代码仓库，还是已经由私有内容仓库保护。

最终没有把 `site-xgif` 整体改为私有，而是保留两条职责清楚的 Git 边界：

- 公开仓库 `npcink/site-xgif` 保存代码、文档、公开内容和部署历史；
- 私有仓库 `npcink/site-xgif-private-content` 保存白名单限定的内容安全快照；
- 草稿、回收站、私有来源正文和恢复台账只由私有内容 GitHub 承担异机恢复；
- `.env`、SQLite、日志和模型向量不进入任一仓库；
- 私有推送失败只提示并允许重试，不能阻断本地正文保存；
- 管理端分别显示公开 Git 当前版本数和私有 `history` 同步版本。

这里最重要的经验是：`git status` 表示主仓库工作树的差异，不等于数据没有备份，也不等于所有差异都应该提交到当前远端。界面必须把“公开发布历史”和“私有恢复历史”分开说明。

完整取舍见 [`ADR-013`](../../site/docs/decisions/ADR-013-public-code-private-content-github-boundary.md)。

### 14. 用单一路径闭合 Flomo 导入、质量检查与人工处理

这一轮真实使用反馈不是“缺少更多功能”，而是操作链被拆散了：导入页有多个相似按钮；长段落被体检发现后，用户还要回内容库寻找文章；编辑页没有说明为什么需要处理；“更多操作”只有一个动作时又增加了一层点击。

收尾后把流程收敛为：

```text
Flomo ZIP
→ 解析、去重与来源判断
→ 默认选择可直接发布项
→ 检查并发布
→ 同一条质量检查
→ 不满足条件时保存草稿 / 从体检直接打开处理
```

具体约束如下：

- 导入页只保留“检查并发布 N 条”和“保存所选为草稿”；没有全选、独立的批量 AI 或段落修复按钮；
- 超过 180 字的 Markdown 段落是发布错误，而不是仅供参考的体检提示；单篇、批量和 Flomo 直发共用该门槛；
- AI 仅在需要时安全插入段落空行，服务端逐字验证原文；失败、超长或不合规时保持草稿，不以改写换取通过；
- 体检页的待处理文章整行可点击，将 blocker、warning、notice 一起带入编辑页，用提示卡给出处理顺序；这些诊断不写入公开内容或内部复核备注；
- 导入来源复核仍使用明确的“我已确认”控件；内容位置和 Git/部署细节分别呈现，避免让一个标签承担所有状态。

这一次的关键教训是：**提示不等于流程闭环，质量规则不等于用户已经知道如何修复。** 当系统要求人工处理时，必须把“原因、可复用的处理动作、复核入口”放在同一上下文，而不是用新的按钮补洞。

完整决策见 [`ADR-014`](../../site/docs/decisions/ADR-014-flomo-import-quality-gate.md)。

### 15. 按单人、本地、仅桌面边界再次收敛

后续逐页走查发现，功能边界虽然正确，但入口和按钮仍按多人后台的思路持续增加。项目只有一个使用者，管理器只在本机桌面运行，因此不需要用更多导航和显式按钮来帮助角色分工。

本轮按三条主任务重新整理：

```text
内容库 → 继续处理 / 同步 / 需处理
新建 → 文章或图片 → 保存草稿 / 发布到本地
导入 → 只默认选择可直接发布项 → 检查并发布 / 保存草稿
```

具体收敛如下：

- 一级导航只保留“内容库 / 新建 / 导入内容 / 系统”，回收站和体检从内容库进入，标签管理归入系统；
- 文章和图片统一使用“保存草稿 / 发布到本地”，编辑器不再暴露 Git 提交与推送选项；
- 删除独立“仅检查”，发布动作始终执行强制检查并原处反馈；
- 删除固定四阶段流程条和卡片/详情双预览切换，只保留紧凑输入预览与真实站点预览；
- 文章的两个 AI 动作合并到“AI 辅助”，图片保留一个 AI 动作；
- 内容库草稿统一使用“继续处理”，同步动作统一叫“同步”，复制与退回草稿放入“更多”；
- 内容体检只负责检查与直达处理，原因逐条展示；已经通过的条目不可点击；
- 导入默认只勾选 ready，review、similar 不勾选，exact 禁用；筛选按处理状态而不是勾选状态。

这次收敛没有合并数据安全边界：保存草稿、发布到本地、Git 同步、云端部署仍是四个不同事实；标签合并预览、永久删除确认和来源确认也继续保留。**单人使用可以减少入口和确认噪音，但不能删除不可逆动作的证据与保护。**

## 关键设计决策

### 学习参考产品的方法

参考产品分析分三层：

1. **目标层**：它解决了什么真实问题；
2. **机制层**：它用什么状态、反馈和恢复机制解决；
3. **外观层**：它如何排列菜单、按钮和面板。

XGIF 优先学习前两层。只有当现有信息架构已经出现重复痛点时，才借鉴第三层。这样可以避免复制大产品为多用户、插件生态和线上数据库准备的复杂度。

### 先定义状态，再设计按钮

内容发布最容易出错的地方不是颜色和间距，而是状态命名。如果“保存”“发布”“同步”“上线”混成一件事，界面越漂亮，误导越严重。

每个状态必须回答：

- 当前事实发生在本地内容、Git 还是云端；
- 下一步唯一主动作是什么；
- 操作失败后内容停留在哪里；
- 用户怎样恢复或重试。

### 容器必须匹配任务

以后增加管理功能时，先使用以下准则：

- **完整工作区**：需要筛选、刷新、深度滚动、跨记录处理或 URL 恢复；
- **详情面板**：需要在不离开列表的情况下查看一条记录；
- **模态弹窗**：短时、聚焦、完成或取消后立即返回；
- **下拉菜单**：低频次级动作，不承载持续状态；
- **内联提示**：只说明当前字段或动作，不承担完整流程。

不能因为已经有一个可复用的 `<dialog>`，就把所有新功能继续塞进弹窗。

### 数据安全优先于界面便利

删除、恢复、标签合并、批量发布和同步都必须保留可解释的失败边界：

- 文件操作成功但 SQLite 写入失败时，不能为了数据库一致性撤销已经安全完成的文件操作；
- 回收站旁车必须能在 SQLite 丢失后重建索引；
- 永久删除必须由选择和确认两步组成；
- 标签合并必须先预览影响；
- 本地发布、Git 推送和线上部署必须分别显示事实。

### AI 必须范围明确

AI 操作应遵守：

1. 用户主动触发；
2. 按钮附近说明可用性和联网边界；
3. 输入上下文发生变化时旧建议失效；
4. 生成候选而不是强制覆盖；
5. 不自动提交、不自动发布；
6. 服务端继续执行确定性的质量检查。

对于正文整理还要增加第七条：AI 输出必须通过“忽略换行后与原文完全一致”的校验，否则整体丢弃。

### 推荐是构建产物，不是线上服务

推荐系统应遵守：

- 模型和向量只存在于本机；
- SQLite 向量缓存可以删除重建；
- Git 只提交小型推荐 ID 清单；
- 页面始终过滤草稿、非公开、已删除和当前内容；
- 静态清单不可用时由确定性规则兜底；
- 管理端如实显示模式、覆盖率和过期状态，不能仅凭“代码存在”宣称第二阶段正在生效。

这使推荐质量可以逐步提升，而不会把静态站变成需要长期运维的在线 AI 系统。

### 桌面端不等于可以无限堆叠

本项目不考虑移动端，可以使用固定侧栏、宽表格和更高的信息密度，但仍应控制：

- 一个页面只有一个主要任务；
- 一级导航必须代表稳定工作区；
- 内容区不使用无意义卡片矩阵；
- 同一层级只突出一个主动作；
- 技术信息默认收纳到系统页；
- 长列表必须有分页、折叠或明确分组。

### 做得好的地方

- 每轮建议在获得用户确认后都落实为可运行代码，而不是停留在方案；
- 没有把 Gridea、WordPress 的完整复杂度带进静态站；
- Markdown、Git、R2 和 SQLite 的权威边界始终清楚；
- AI 保持主动触发、建议优先和确定性校验；
- 用户反馈中的具体困惑都转化成了回归测试；
- 收尾时使用真实桌面视口复核，而不只依赖静态代码检查。

### 下次重点关注

1. 新功能开发前先写清“任务时长、上下文、容器、状态、恢复方式”；
2. 禁用按钮必须同时提供原因和恢复路径；
3. 一级导航只放稳定工作区，不放偶发弹窗动作；
4. 继续区分本地内容、Git 和云端事实，不创造含混的“已发布”状态；
5. 优先观察真实使用频率，再决定是否增加标签搜索、同步筛选等功能；
6. 每次阶段收尾都检查失效选择器、焦点恢复、URL 恢复和未提交数据边界。
7. AI 处理正文时先定义可机器验证的不变量，不能只依赖提示词；
8. 推荐状态必须同时核对清单模式、模型、覆盖率和语料哈希；
9. 视觉验收同时检查截图、计算样式、DOM 标题层级和实际路由；
10. 代码提交与内容批次分开，未审核草稿不能因为“顺手收尾”进入公开 Git。
11. 看到主仓库工作区变更时，先判断它属于公开发布还是私有恢复，不用“全部提交”代替边界判断。
12. 体检、质量检查和编辑器必须共用规则，但诊断只在当前处理上下文中传递，不成为新的内容字段或公开元数据。

## 后续功能判断清单

准备新增功能时，依次回答：

1. 这是实际重复出现的问题，还是参考产品里“看起来应该有”的功能？
2. 它属于内容创作、内容管理还是系统恢复？
3. 它应该使用工作区、详情面板、弹窗还是内联反馈？
4. 它修改哪个权威数据源？失败后怎样恢复？
5. 是否需要联网？用户能否在动作前知道发送范围？
6. 是否会让“发布一篇文章或一张图片”增加额外必填步骤？
7. 能否通过现有状态、按钮或批量工具解决，而不新增入口？
8. 需要哪些契约、单元、HTTP 或浏览器测试防止回归？

如果无法明确回答第 1、3、4 项，应先暂停实现并重新调查。
