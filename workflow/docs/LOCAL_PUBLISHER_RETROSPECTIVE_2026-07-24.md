# XGIF 本地发布助手阶段复盘

## 文档目的

本文记录 2026-07-24 前后围绕 XGIF 本地发布助手完成的一轮连续产品化改造，覆盖参考产品分析、发布流程、内容治理、恢复能力、素材复用、AI 辅助、内容管理布局和桌面工作区收尾。

它不是功能清单的重复，而是回答四个长期问题：

1. 为什么本地发布助手采用现在的结构；
2. 哪些参考产品经验值得吸收，哪些不应照搬；
3. 本轮开发中出现了哪些具体问题，为什么会返工；
4. 后续扩展功能时应遵守什么判断和验收方法。

## 产品边界

XGIF 仍然是静态内容站，不是传统在线 CMS。

- `site/` 是公开 Astro 站点和生产部署边界；
- `workflow/` 是只监听本机的单人发布助手；
- Markdown、图片元数据、Git 和 R2 台账是内容权威源；
- SQLite 只保存可重建的索引、操作历史和缓存；
- AI 只在用户主动点击时调用，并且输出是建议，不是自动发布决定；
- 本地发布助手只验收 PC 桌面端，不为移动端增加另一套布局和交互成本。

因此，参考 Gridea、WordPress 等产品时，学习目标是成熟的工作流和信息组织，不是把本项目扩张成完整 CMS。

## 演进过程

### 1. 从参考产品中提炼发布流程

最初参考 Gridea 的价值，在于确认内容发布不是一个“保存”按钮，而是一条可解释的状态链：

```text
提供原始内容
→ 保存草稿
→ 真实预览
→ 发布到本地
→ 同步 Git
→ 等待部署
→ 线上核对
```

落地时没有复制 Gridea 的整套桌面客户端，而是把流程压缩到 XGIF 真正存在的 Markdown、GitHub 和 Cloudflare 边界中。编辑器开始明确显示下一步操作，内容详情分别展示内容、Git 和云端状态，避免把“本地文件已保存”误写成“已经上线”。

### 2. 建立内容治理和恢复能力

随后按“标签治理 → 素材复用 → 恢复状态看板 → 封面与目录”推进：

- 标签治理统计真实使用量，区分规范标签和待合并标签；
- 标签合并必须先预览受影响内容，再确认写回 Markdown；
- 素材库统一读取图片内容、R2 台账、本地文件和备份状态；
- SQLite 损坏恢复、私有内容快照、R2 对账进入系统状态；
- 文章支持可选封面、替代文字和由正文标题生成的目录。

这部分形成了一个重要原则：管理功能不能另建内容权威源，只能检查、组织和安全修改现有 Markdown 与台账。

对应提交：`8a6160a feat: govern local publishing workflow`。

### 3. 增加本地收藏，但保持读者数据本地化

收藏功能使用浏览器本地存储，不增加用户账号和线上数据库。随后补充导入、导出和独立收藏页，使数据可以由用户自行备份和迁移。

这说明“本地优先”不等于功能简陋。只要提供稳定 ID、版本化导出格式、重复处理和失败反馈，本地功能同样可以做到可恢复、可迁移。

对应提交：`8399148 feat(site): improve discovery and local favorites`。

### 4. 重做内容管理流程

早期内容管理同时显示列表、详情、状态和大量操作，重要动作缺少层级。后续改成更接近 WordPress 的“左侧菜单、右侧工作区”桌面结构，并完成：

- 内容库按草稿、待同步、待上线、待验证和已上线筛选；
- 当前查看与批量选择分离；
- 列表只保留标题、状态、日期和标签等高频信息；
- 详情作为次级上下文，不再和列表争夺同等视觉权重；
- 批量发布、同步、退回草稿、编辑属性和回收站形成明确动作组。

这里学习的是 WordPress 的稳定信息架构，而不是其视觉样式和历史包袱。

对应提交：`b62cf32 feat(workflow): redesign content management flow`。

### 5. 把 AI 从“黑盒整理”改成可控建议

用户反馈暴露了两个问题：

- “AI 整理文章资料”禁用时只表现为灰色，原因不够清楚；
- 自动生成的标题不满意时，只能重新整理整篇资料，成本和风险都过高。

因此，AI 被拆成两种范围不同的动作：

- “AI 整理文章资料”生成标题、摘要、标签等整套建议；
- 标题字段旁的“AI 换标题”一次生成三个新候选，只修改用户选中的标题。

候选标题在正文、摘要或来源发生变化后失效，避免把旧上下文生成的结果误用到新内容。AI 仍不自动保存、不自动发布，也不覆盖正文。

### 6. 系统性完善桌面控制台

桌面控制台继续补齐自动保存版本、Markdown 工具栏、内容分页、批量管理、发布状态语义、私有备份和真实浏览器测试。此时管理端已经从“几个表单”发展为稳定的本地工作台。

对应提交：`f0a5a3e feat(workflow): improve desktop publishing console`。

### 7. 收尾一级导航与弹窗边界

最后一次视觉检查发现，“内容体检与标签”“回收站”“同步记录”虽然都放在一级导航中，却全部打开弹窗，用户无法从入口判断接下来是切换页面还是执行临时任务。

收尾改造按任务复杂度重新选择容器：

| 功能 | 最终容器 | 原因 |
| --- | --- | --- |
| 内容体检与标签 | 独立工作区 | 长任务、信息密集、需要刷新和保留位置 |
| 回收站 | 模态弹窗 | 短时、聚焦、处理后返回原工作区 |
| 同步记录 | 系统页子页面 | 属于运行与发布证据，不应占用管理一级入口 |

同时增加：

- 回收站侧栏数量；
- 弹窗关闭后的焦点恢复；
- `#audit`、`#system/sync` 等工作区 URL；
- 刷新、浏览器前进和后退的位置恢复；
- 运行状态、同步记录、恢复与备份三个系统子页面。

## 关键设计决策

### 学习参考产品的方法

参考产品分析分三层：

1. **目标层**：它解决了什么真实问题；
2. **机制层**：它用什么状态、反馈和恢复机制解决；
3. **外观层**：它如何排列菜单、按钮和面板。

XGIF 优先学习前两层。只有当现有信息架构已经出现重复痛点时，才借鉴第三层。这样可以避免复制大产品为多用户、插件生态和线上数据库准备的复杂度。

### 先定义状态，再设计按钮

内容发布最容易出错的地方不是颜色和间距，而是状态命名。如果“保存”“发布”“同步”“上线”混成一件事，界面越漂亮，误导越严重。

每个状态必须回答：

- 当前事实发生在本地内容、Git 还是云端；
- 下一步唯一主动作是什么；
- 操作失败后内容停留在哪里；
- 用户怎样恢复或重试。

### 容器必须匹配任务

以后增加管理功能时，先使用以下准则：

- **完整工作区**：需要筛选、刷新、深度滚动、跨记录处理或 URL 恢复；
- **详情面板**：需要在不离开列表的情况下查看一条记录；
- **模态弹窗**：短时、聚焦、完成或取消后立即返回；
- **下拉菜单**：低频次级动作，不承载持续状态；
- **内联提示**：只说明当前字段或动作，不承担完整流程。

不能因为已经有一个可复用的 `<dialog>`，就把所有新功能继续塞进弹窗。

### 数据安全优先于界面便利

删除、恢复、标签合并、批量发布和同步都必须保留可解释的失败边界：

- 文件操作成功但 SQLite 写入失败时，不能为了数据库一致性撤销已经安全完成的文件操作；
- 回收站旁车必须能在 SQLite 丢失后重建索引；
- 永久删除必须由选择和确认两步组成；
- 标签合并必须先预览影响；
- 本地发布、Git 推送和线上部署必须分别显示事实。

### AI 必须范围明确

AI 操作应遵守：

1. 用户主动触发；
2. 按钮附近说明可用性和联网边界；
3. 输入上下文发生变化时旧建议失效；
4. 生成候选而不是强制覆盖；
5. 不自动提交、不自动发布；
6. 服务端继续执行确定性的质量检查。

### 桌面端不等于可以无限堆叠

本项目不考虑移动端，可以使用固定侧栏、宽表格和更高的信息密度，但仍应控制：

- 一个页面只有一个主要任务；
- 一级导航必须代表稳定工作区；
- 内容区不使用无意义卡片矩阵；
- 同一层级只突出一个主动作；
- 技术信息默认收纳到系统页；
- 长列表必须有分页、折叠或明确分组。

### 发现的问题

| 严重程度 | 问题描述 | 根本原因 | 已采取或后续改进 |
| --- | --- | --- | --- |
| 必须改正 | `content-audit-dialog` 承载标签治理和 100 多条检查结果，形成大弹窗与嵌套滚动 | 按组件复用推进功能，没有先按任务复杂度选择容器 | 已改为独立工作区，并增加 URL 恢复 |
| 必须改正 | 一级菜单中的“同步记录”打开临时弹窗，导航语义与实际行为不一致 | 信息架构沿用早期工具按钮，而功能已经成长为系统证据 | 已并入系统页子导航 |
| 应当改正 | “AI 整理文章资料”和发布复核动作在早期缺少范围说明，禁用状态主要依赖灰色 | 先实现动作，后补可用性解释和任务边界 | 已增加状态说明，并拆出只改标题的三候选动作 |
| 应当改正 | 内容管理早期同时展示过多状态、详情和操作 | 功能逐项叠加，没有及时重做主次关系 | 已采用内容库、详情上下文和系统页分层 |
| 建议改进 | 标签列表目前为了首屏可用性保留局部滚动 | 标签治理和体检结果仍共享一个页面，需要平衡概览与完整展开 | 若标签数量持续增长，再增加标签搜索或独立标签视图；不提前扩展 |

### 做得好的地方

- 每轮建议在获得用户确认后都落实为可运行代码，而不是停留在方案；
- 没有把 Gridea、WordPress 的完整复杂度带进静态站；
- Markdown、Git、R2 和 SQLite 的权威边界始终清楚；
- AI 保持主动触发、建议优先和确定性校验；
- 用户反馈中的具体困惑都转化成了回归测试；
- 收尾时使用真实桌面视口复核，而不只依赖静态代码检查。

### 下次重点关注

1. 新功能开发前先写清“任务时长、上下文、容器、状态、恢复方式”；
2. 禁用按钮必须同时提供原因和恢复路径；
3. 一级导航只放稳定工作区，不放偶发弹窗动作；
4. 继续区分本地内容、Git 和云端事实，不创造含混的“已发布”状态；
5. 优先观察真实使用频率，再决定是否增加标签搜索、同步筛选等功能；
6. 每次阶段收尾都检查失效选择器、焦点恢复、URL 恢复和未提交数据边界。

## 后续功能判断清单

准备新增功能时，依次回答：

1. 这是实际重复出现的问题，还是参考产品里“看起来应该有”的功能？
2. 它属于内容创作、内容管理还是系统恢复？
3. 它应该使用工作区、详情面板、弹窗还是内联反馈？
4. 它修改哪个权威数据源？失败后怎样恢复？
5. 是否需要联网？用户能否在动作前知道发送范围？
6. 是否会让“发布一篇文章或一张图片”增加额外必填步骤？
7. 能否通过现有状态、按钮或批量工具解决，而不新增入口？
8. 需要哪些契约、单元、HTTP 或浏览器测试防止回归？

如果无法明确回答第 1、3、4 项，应先暂停实现并重新调查。
