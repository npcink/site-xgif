# 本地发布助手可靠性复盘（2026-07-29）

## 背景

本轮工作最初从“按钮太多、同步队列被单篇异常阻断”开始，随后扩展到发布状态、批处理、恢复和运维事实的系统审计。第一轮修复完成后，第二轮故障导向复核又发现：自动化测试通过并不等于远端操作、本地持久化和异常恢复已经形成闭环。

## 已确认的经验

### 1. 内容合格性和批次执行必须分离

一篇内容不合格只能阻止它自己进入公开分支。批次应先逐篇体检，再把合格项、需复核项和阻断项分别处理，不能用一个布尔结果代表整批。

### 2. 发布状态必须绑定不可变内容版本

文件路径、标题或当前工作区 dirty 状态都不能证明远端包含哪个版本。发布事实必须绑定 Markdown SHA-256，并在复制到隔离工作树后再次核对该哈希，防止体检与推送之间发生外部修改。

### 3. 远端副作用前必须先留下可恢复意图

“先推送、后写回执”存在不可消除的丢失窗口：远端已经成功，本地却可能因写盘失败而不知道。正确顺序是：

1. 在隔离分支创建提交；
2. 追加 `prepared` 回执并保留本地分支；
3. 推送远端；
4. 追加 `push_succeeded` 或 `push_failed` 回执；
5. 只有终态回执落盘后才清理本地分支。

### 4. 本地保存不能依赖远端网络完成

Markdown、SQLite 索引和本机私有 Git 是本地持久化；GitHub 私有远端只是第二层副本。日常保存应先完成本地快照并返回，远端推送使用有界超时在后台串行重试，不能占住所有写操作。

### 5. “新鲜”必须比较对应事实

- SQLite 备份应与内容、回收站和操作记录的最近逻辑变更时间比较，不能使用启动时也会波动的数据库/WAL 文件时间，更不能与内容 Git 提交时间比较；
- 恢复演练应比较运行时代码版本和内容指纹，不能只比较条数；
- 推荐清单的“内容最新”和“向量能力正常”是两个状态，规则降级不能伪装成完整健康。

### 6. 错误文本是外部不可信数据

Git、GitHub CLI、SSH 和第三方接口的 stderr 可能包含凭据 URL、Token 或本机路径。任何错误在进入 API、浏览器、SQLite 或 JSONL 前必须经过统一脱敏。

### 7. 验收必须覆盖故障窗口

单元测试和正常构建无法证明以下场景：

- 体检后文件被外部修改；
- 准备回执写入后进程中断；
- 推送成功但终态回执写入失败；
- 私有远端永久不返回；
- 推荐向量服务恢复后从规则模式重新升级。

这些场景需要专门的故障注入测试。真实内容同步只作为受控验收，不替代可重复的临时仓库测试。

## 第二轮复核补充

第一轮修复后的再次审计证明，“有串行队列”和“有版本号”仍不足以自动消除所有竞态：

- 编辑器打开时校验一次版本不够；质量检查和 Markdown 生成也会消耗时间，真正替换文件前必须再次核对打开时版本。
- 标记为“本地安全备份”的操作不能暗中等待 GitHub。手动远端同步也只能占用私有备份队列，不能占住内容保存队列。
- GitHub 状态必须逐分支隔离失败；一个分支超时只能让该分支变成“远端待确认”。
- 追加式日志描述的是数据模型，不代表必须使用非原子的文件追加。发布回执采用“读取并验证现有日志 → 写临时文件 → 原子替换”，防止中断留下半行。
- 恢复和永久删除不能信任浏览器回传的路径。浏览器只提交回收站 ID，实际文件、类型和原位置必须来自服务端重建后的权威索引。
- 只读 HTTP 方法也可能触发 SQLite 增量索引刷新；这类隐藏写入同样必须进入内容写队列。
- AI 安全分段不能只相信上游的 `applied` 标记；真正发布前的批处理模块必须再次证明候选正文仅插入换行且没有改写字符。

## 本次采用的修复原则

- 不引入消息队列、在线 CMS 或新数据库；
- 继续以 Markdown 为内容真相、SQLite 为可重建索引；
- 使用追加式事件、保留分支、原子写入和内容哈希建立恢复路径；
- 所有远端事实失败时保守显示，不猜测成功；
- 保留用户当前脏工作区，不借修复之名改写内容。
