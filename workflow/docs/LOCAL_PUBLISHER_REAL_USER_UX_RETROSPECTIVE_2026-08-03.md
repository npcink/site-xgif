# 本地发布助手真实用户审查复盘（2026-08-03）

状态：阶段收尾

适用范围：`workflow/` 的内容库、文章编辑、导入、批量发布、内容检查与同步上线界面

## 1. 原定目标

本阶段不是增加更多发布能力，而是以真实用户连续操作的方式检查现有项目，解决以下问题：

- 高频操作难找、低频操作占据主界面；
- 相似按钮在不同页面使用不同交互和命名；
- AI 标题、正文分段和资料整理彼此覆盖或让用户误解；
- 导入确认、批量复核和推荐分组需要逐篇打开；
- 发布进度、内容质量、Git 状态和线上状态混为一谈；
- 自动化测试通过，但真实内容数量和真实页面布局仍可能暴露问题。

验收标准是：用户能沿着“导入或编辑 → 集中复核 → 发布到本地 → 同步上线 → 内容检查”完成任务；界面状态与后端事实一致；任何 AI 整理都不能静默改写正文；失败项可单独恢复或重试。

## 3. 工作审视报告

### 3.1 发现的问题

| 严重程度 | 具体问题 | 根本原因 | 已采取的改进 |
| --- | --- | --- | --- |
| 必须改正 | `workflow/public/app.js` 曾把“需处理”同时用于发布流程未完成和内容质量债务；点击状态栏入口还会切换到独立工作区，导致顶部状态栏消失 | 没有先区分“内容位置”和“内容质量”两个正交维度 | 一级状态只表达内容位置；质量审计改名“内容检查”并移入工具菜单 |
| 必须改正 | 批量确认标题调用 `/api/content/batch` 时出现 400，前后端批量项目契约不一致 | UI 增加批量入口后没有先用后端 schema 做端到端合同验证 | 批量请求使用稳定项目身份和服务端版本校验，并增加浏览器回归 |
| 必须改正 | AI 生成标题后执行正文整理，标题候选被重新渲染覆盖 | 多个 AI 动作共享结果区和重置逻辑，没有保持各自状态 | 标题候选、正文整理和字段候选分开保存与渲染 |
| 必须改正 | AI 分段若只依赖提示词，存在删字、改字或截断正文的风险 | 把概率模型输出误当作可信变换 | 客户端与服务端都比较正文字符序列；不一致时丢弃候选并保留原文 |
| 应当改正 | 内容库长期显示固定批量按钮，即使所选内容不支持相应动作 | 以功能清单组织界面，而不是以当前任务组织界面 | 草稿、本地待同步和云端流程分别只显示适用动作，通用低频动作进入“更多” |
| 应当改正 | “更多”只有一个子项，多个页面仍保留重复按钮 | 机械套用下拉菜单和按钮组件，没有按动作频率复核 | 单一动作直接展示；只有两个以上低频动作才使用菜单 |
| 应当改正 | 批量发布弹窗把推荐分组、内容摘要、正文展开和整批确认堆在同一视觉层级 | 先实现字段，再补布局，缺少任务顺序 | 按“识别内容 → 核对异常 → 选择分组 → 逐项确认 → 发布”排序，并禁用未完成的主动作 |
| 应当改正 | 浏览器测试等待真实内容库中的草稿，但真实草稿数量后来变为 0 | 测试把环境数据当成固定夹具 | 状态行为使用 `page.route` 固定草稿、待同步和待部署数据；真实数据只用于目视验收 |
| 应当改正 | 修改 CSS 后沿用相同缓存版本，真实浏览器仍可能加载旧样式 | 代码验证关注源文件，遗漏浏览器缓存事实 | 每次交付 UI 资源同步更新 `styles.css` 和 `app.js` 查询版本 |
| 建议改进 | 重启旧进程时偶尔超过 5 秒，`restart` 会停止后不继续启动 | 进程退出窗口与启动器超时边界接近 | 先用 `npm run status` 确认事实，再只启动缺失服务；不得盲目重复启动 |

### 3.2 做得好的地方

- 用户反馈始终作为真实操作证据处理，没有把界面困惑归因于“用户不理解”。
- 多次修改都保留 Markdown 内容真相、SQLite 可重建索引和隔离同步边界，没有为 UI 问题引入新后台或第二套状态系统。
- 批量能力减少了逐篇重复操作，但没有取消来源、分组、内部备注和发布决定的人类确认。
- 正文保护采用程序化字符比较，而不是依赖模型承诺。
- 验证同时覆盖单元、HTTP、浏览器、真实数据和实际布局，并明确它们各自能证明什么。
- 脏工作树中的公开内容、运行台账和视觉基线始终与程序提交分离。

### 3.3 下次重点关注

1. 先写“用户正在完成什么任务”，再决定按钮、Tab、菜单或弹窗。
2. 新状态必须先归类为内容质量、内容位置、远端流程或运行健康，禁止跨维度复用同一名称。
3. 新 AI 动作必须列出输入、可修改字段、不变量、人工确认点和失败回退。
4. 浏览器测试使用固定夹具验证逻辑；真实内容只验证集成与视觉，不作为断言前提。
5. 所有 UI 交付都要检查资源缓存版本、1280 × 800 布局和重新启动后的实际运行源码。
6. 提交前按白名单精确暂存，公开内容同步与程序开发继续使用不同分支和凭据。

## 4. 形成的产品与交互规范

### 4.1 导航承载稳定任务，筛选承载临时状态

侧边栏只放长期稳定的工作区：内容库、新建、导入内容、同步上线、系统。状态不是工作区，不进入侧边栏。

内容库一级状态最多保留四个：

```text
全部 / 草稿 / 发布中 / 已上线
```

详细技术阶段只在相关一级状态下出现。内容质量检查属于低频治理工具，不伪装成内容位置 Tab。

### 4.2 一个词只表达一个事实

- “草稿”：尚未进入本地公开内容。
- “发布中”：本地公开后，尚未完成远端同步、合并、部署或线上核验。
- “已上线”：线上页面已经匹配当前内容版本。
- “需确认”：内容质量建议，需要人工判断，但不自动撤回历史线上内容。
- “阻断发布”：当前版本不能进入下一次发布或同步。

禁止使用笼统的“需处理”同时表示上述多个状态。

### 4.3 高频动作直接出现，低频动作渐进披露

- 同一时刻只保留一个主动作。
- 当前状态不适用的动作隐藏，而不是排列一排禁用按钮。
- 单一低频动作直接显示，不创建只有一项的“更多”。
- 两个以上低频通用动作才进入“更多”。
- Hover 只能补充说明，不能承担打开菜单、确认选择或改变状态的核心交互。

### 4.4 批量处理减少重复劳动，不减少必要判断

适合自动化的部分是读取、检查、生成候选、筛选高置信项和集中展示；标题、来源、推荐分组、内部复核和发布决定仍由人确认。

批量工作台必须支持：

- 单项失败不阻断整批；
- 已确认项与未确认项清楚区分；
- 主动作展示剩余门槛并在条件不足时禁用；
- 修改候选不会静默清空其他已经完成的工作；
- 关闭后不在列表留下过期成功提示。

### 4.5 内容检查与发布进度必须独立

内容检查回答“当前内容是否适合进入下一次公开流程”；发布进度回答“已发布版本走到同步、合并、部署或核验的哪一步”。

历史已上线内容出现新规则警告时：

- 不自动下线；
- 明确标记为历史复核债务；
- 下次编辑或同步前按规则处理；
- 只有确定性阻断项使用危险色。

## 5. AI 与正文完整性规范

每个 AI 动作必须声明：

| 项目 | 要求 |
| --- | --- |
| 输入 | 只发送完成任务必需的正文和元数据 |
| 输出 | 只能作为候选，不能直接成为发布事实 |
| 可修改字段 | 明确白名单；未列出的字段保持原值 |
| 正文不变量 | 去除允许新增的 Markdown 空行后，字符序列必须与原文一致 |
| 版本门禁 | 生成前记录内容 SHA-256，写回前服务端重新读取并比较 |
| 人工确认 | 标题、来源、推荐分组、内部备注和发布均需明确确认 |
| 失败回退 | 丢弃不合格候选，保留原文和现有编辑状态 |

“整理分段”不能被实现为润色、摘要、改写或截断；超长内容无法完整处理时宁可跳过，也不能部分覆盖正文。

## 6. 真实用户审查标准流程

```text
确认当前分支与脏工作树
→ 启动管理端和站点预览
→ 从用户入口完成一条核心任务
→ 检查按钮、状态、错误和恢复路径
→ 核对控制台、网络请求和服务日志
→ 用固定夹具补回归测试
→ 用真实数据做视觉与集成复核
→ 重启并确认运行源码版本
→ 精确暂存、提交、推送
```

必须覆盖的核心路径：

1. 新建或导入草稿；
2. AI 标题与正文整理的组合使用；
3. 批量确认资料和推荐分组；
4. 发布到本地后的状态变化；
5. 发布中二级状态和同步入口；
6. 内容检查的需确认与阻断项；
7. 单项失败、取消、重试、回收站和恢复；
8. 浏览器前进、后退和刷新后的工作区恢复。

## 7. 验证证据分层

| 证据 | 能证明 | 不能证明 |
| --- | --- | --- |
| 单元与合同测试 | 状态计算、输入输出和安全规则 | 页面实际可用、远端已发布 |
| HTTP 集成测试 | 本机 API 与安全边界 | 浏览器布局、GitHub 或线上结果 |
| 浏览器回归 | 可见交互、键盘和工作区恢复 | 真实数据覆盖、线上部署 |
| 真实数据目视检查 | 当前内容数量和实际布局 | 未来内容数量、所有异常分支 |
| 本地重启与版本检查 | 当前运行进程加载本轮源码 | 已提交、已推送或已合并 |
| Git 提交与推送 | 远端分支包含本轮代码 | CI、合并、部署或线上验收 |

任何收尾报告都要分别陈述这些事实，不能用“测试通过”代替“已经上线”。
