# XGIF 本地发布助手最终交接与开发方法

日期：2026-07-30

状态：工程阶段收口；后续按真实内容需求维护

## 1. 文档目的

本文不是另一份功能说明，而是本阶段历史的总入口。它回答四个问题：

1. 本地发布助手最终解决了什么问题；
2. 为什么形成现在的架构和操作边界；
3. 开发中出现过哪些系统性错误，如何避免复发；
4. 下一位维护者应按什么顺序调查、修改、验证和发布。

长期约束以
[`LOCAL_PUBLISHER_ENGINEERING_STANDARD.md`](LOCAL_PUBLISHER_ENGINEERING_STANDARD.md)
为准；架构理由以 ADR 为准；本文保留阶段结论、方法和交接状态。

## 2. 最终结论

发布助手已经从“本地表单加若干脚本”收敛为单人、本机、PC 优先的内容工作台。核心闭环为：

```text
导入或新建
→ 保存草稿
→ 确定性体检与人工复核
→ 本地公开
→ 从 origin/main 创建隔离内容分支
→ GitHub PR 与 CI
→ Cloudflare Workers Builds
→ 线上正文、状态与资源核验
```

真正的完成不是某个按钮返回成功，而是下列事实分别成立：

- Markdown 已原子写入；
- SQLite 索引可由 Markdown 和旁车重建；
- 私有内容已形成本机快照，私有远端同步不阻塞保存；
- 公开内容版本已绑定发布回执；
- PR、检查、合并和部署事实来自各自权威系统；
- 线上页面匹配当前内容，删除内容返回 404 或 410；
- 推荐清单与内容版本一致，且降级状态没有被伪装成健康。

## 3. 架构与真相边界

| 层 | 权威事实 | 允许的职责 | 禁止替代的事实 |
| --- | --- | --- | --- |
| Markdown | 正文、公开元数据、稳定 ID | 内容真相、Git 审阅与恢复 | 不能表示 PR、部署或线上状态 |
| SQLite | 本地索引、操作视图、向量缓存 | 查询、聚合、重建 | 不能成为唯一内容或发布真相 |
| 私有内容 Git | 草稿、私有来源、回收站与历史 | 本机恢复和异地副本 | 不能进入公开站点仓库 |
| 发布回执 | 内容版本、批次、分支、提交和阶段 | 幂等、重试、故障恢复 | 不能证明 PR 已合并或页面已上线 |
| GitHub | 分支、PR、检查、合并 | 公开代码和内容审阅 | 不能证明 Cloudflare 已提供当前页面 |
| Cloudflare | 构建与部署 revision | 静态站部署和 R2 字节 | 不能拥有内容编辑或推荐决策 |
| 线上 URL | 当前读者实际看到的结果 | 最终内容与下架核验 | HTTP 200 本身不能证明版本匹配 |

`site/` 是唯一部署目录；`workflow/` 只在本机运行；`old/` 只保留视觉参考。不要把本地管理器、凭据、SQLite、日志、私有正文或模型缓存部署到线上。

## 4. 演进脉络

### 4.1 先把产品边界变小

项目确认只有一个本机使用者、不做移动端和在线后台后，删除了多用户、权限、移动导航、重复入口和常驻服务的假设。复杂度预算转向内容安全、恢复和发布事实。

经验：明确的非目标与功能列表同样重要。没有真实用户和历史兼容包袱时，应直接迁移到单一正确模型，不保留两套状态和长期兼容分支。

### 4.2 先定义状态，再设计界面

“草稿、本地发布、已推送、PR、部署、线上核验”原本被多个页面混用。修正后，内容位置与内容质量拆成两个维度，列表、详情、同步页和系统页复用同一状态计算。

经验：按钮只触发状态转换，不能发明事实。灰色按钮、一个“同步成功”布尔值或模糊的“已发布”都会隐藏真实阻断点。

### 4.3 把内容真相和查询能力分开

Markdown 继续作为不可替代的内容真相，SQLite 只承担可重建索引。回收站使用稳定 ID 和旁车恢复；私有 Git 保存白名单内容历史；R2 只保存图片字节。

经验：增加数据库之前先问“删除数据库后能否恢复”。本地工具最危险的不是吞吐不足，而是误删、覆盖和无法解释的隐式状态。

### 4.4 把代码开发和内容发布分开

直接从脏开发分支同步内容会夹带代码和草稿。最终流程从最新 `origin/main` 创建临时 worktree，只复制白名单内容和实际引用的本地资源，并按发布包哈希写回执。

经验：Git 隔离不是操作习惯，而是产品安全边界。内容提交、代码提交和推荐产物提交必须分别建立分支、白名单和验收。

### 4.5 把正常路径扩展为可恢复协议

系统曾经只能说明“推送成功或失败”，不能处理推送成功后本机写盘中断、旧分支重试、删除下架、私有远端超时等故障窗口。最终采用：

```text
准备提交
→ 先记录 prepared
→ 执行远端副作用
→ 记录 push_succeeded 或 push_failed
→ 终态持久化成功后再清理恢复点
```

经验：任何远端副作用前都要留下可恢复意图；任何清理动作前都要确认终态已经持久化。

### 4.6 用确定性边界约束 AI

AI 只生成标题、摘要、标签和段落候选。正文整理必须证明只插入 Markdown 空行，没有删字、改字或重排。后来进一步增加本地确定性分段，在安全断句存在时不依赖模型。

经验：AI 可以提高整理效率，不能证明来源、授权、文本完整性、发布状态或删除结果。概率能力必须被确定性不变量和人工复核包住。

### 4.7 推荐保持离线和静态

当前规模采用规则排序、本地嵌入缓存、显式推荐分组和静态 ID 清单。成人幽默内容通过确定性分组隔离；向量只在允许集合中排序。服务失败时可规则降级，但健康状态必须显式标注。

经验：先用规则定义候选集合和安全边界，再让模型处理相关度。小规模内容不需要在线向量库、实时画像或第二个控制面。

### 4.8 用真实发布和下架演练验证系统

单元测试不能证明 GitHub、Cloudflare 和线上页面组成的事实链。最终通过受控内容执行发布、下架、恢复、再次下架，并分别核对 200、404、构建 revision 和内容版本。

经验：测试负责可重复地覆盖分支，受控演练负责证明真实边界；两者缺一不可，也不能互相冒充。

## 5. 系统性问题、修正和可复用规则

| 系统性问题 | 根本原因 | 已采用的修正 | 长期规则 |
| --- | --- | --- | --- |
| 单篇异常阻断整批 | 用整批布尔值代替逐项状态 | 先体检分组，再逐项执行并保留失败项 | 批处理必须允许部分成功 |
| 当前工作区 clean 被当成远端事实 | 版本身份不稳定 | 使用 `contentId + 发布包 SHA-256` 回执 | 任何同步状态都绑定不可变版本 |
| 推送后写回执存在丢失窗口 | 远端副作用没有预写意图 | `prepared → push_*` 两阶段事件 | 先留恢复点，再访问远端 |
| 保存草稿等待私有 GitHub | 把异地副本当成本地事务 | 本机快照先完成，远端独立有界队列 | 网络失败不能阻止本地保存 |
| 页面分别计算“已上线” | 相邻事实互相代替 | 统一状态计算，远端查询逐分支隔离 | 状态只能由权威系统回答 |
| AI 分段看似成功但可能改字 | 相信上游 `applied` 标志 | 发布边界再次执行字符级校验 | 不信任跨边界状态声明 |
| Markdown 链接被当成裸 URL | 按字符模式猜语义 | 区分结构化链接、自动链接和裸 URL | 审计规则按用户可见语义工作 |
| 编号系列被误报重复来源 | 只看共享 URL | 识别同名、显式、唯一编号系列 | 启发式只能产生警告，不能抹平证据 |
| 线上正文已更新却仍显示待上线 | 验证器比较了 Markdown 隐藏链接目标 | 先转成渲染可见文本再选择锚点 | 线上验证比较读者可见结果 |
| 动态标签破坏视觉基线 | 把内容数据变化当成布局变化 | 只遮罩数据拥有的 ticker 区域 | 遮罩需最小化，结构和布局仍要比较 |
| 备份“新鲜”判断不可靠 | 比较了 WAL、启动或文件时间 | 比较对应逻辑变更时间和内容指纹 | 新鲜度必须说明在比较什么事实 |
| 删除只改变本地 Markdown | 没有远端下架协议 | 墓碑、`git rm`、回执和 404/410 核验 | 删除也是一次完整发布 |
| 启动器复用旧进程 | 只检查端口可达 | 核对受管 PID、源码版本和健康响应 | 可达不等于运行的是当前代码 |

## 6. 开发与修改规范

### 6.1 调查顺序

1. 先运行 `git status --short --branch`，保护用户脏工作区；
2. 明确事实属于 Markdown、SQLite、Git、GitHub、Cloudflare 还是线上页面；
3. 在最新生产基线建立独立 worktree；
4. 用最小复现确认问题，不根据 UI 文案直接猜根因；
5. 先写会失败的回归测试，再修根因；
6. 更新长期规范或 ADR，而不是只留下聊天记录。

### 6.2 实现顺序

1. 先收紧状态、类型、白名单和输入不变量；
2. 再修改服务端状态转换和持久化；
3. 最后修改界面展示；
4. 数据迁移必须提供只读预览与显式 `--apply`；
5. 没有兼容负担时，迁移到单一格式并删除双写；但内容删除、来源和授权仍需人工确认。

### 6.3 验证顺序

```bash
cd workflow
npm test
npm run test:browser

cd ../site
npm run test:all
npm run check:deploy

cd ..
git diff --check
```

按风险补充恢复演练、SQLite `quick_check`、私有 Git `fsck`、R2 只读对账、故障注入和受控真实发布。

### 6.4 发布报告

交付必须分开报告：

1. 本地测试与构建；
2. 提交 SHA 和远端分支；
3. PR 与 CI；
4. Cloudflare 部署 revision；
5. `/build.json` 当前提交；
6. 线上内容匹配或下架状态；
7. 未执行或尚待人工完成的阶段。

## 8. 工作审视报告

### 原定目标

系统性修复本地发布助手，完成真实内容与推荐发布验证，并将经验固化为可维护规范。

### 完成情况

- [x] 已完成：产品边界、状态模型、批处理、版本回执、恢复、删除、安全和启动诊断收敛；
- [x] 已完成：离线混合推荐、分组隔离、清单发布和降级状态治理；
- [x] 已完成：内容分段迁移、来源系列识别、结构化链接审计和视觉数据遮罩；
- [x] 已完成：单元、HTTP、浏览器、Astro、CI、真实部署和下架演练；
- [x] 已完成：长期工程规范、ADR、阶段复盘和最终交接索引；
- [ ] 未完成：8 个已推送图片内容的人工公开复核与新基线 PR；原因是内容发布决定不应由工程收尾静默代替。

### 发现的问题

| 严重程度 | 问题描述 | 根本原因 | 改进建议 |
| --- | --- | --- | --- |
| 必须改正 | `workflow/server.js` 的线上核验曾把 Markdown 链接目标 URL 作为正文锚点 | 验证源语法而不是渲染语义 | 先生成可见文本，并保留回归测试 |
| 应当改正 | 第一轮收尾把“队列为空”表述为全部发布闭环 | 混淆远端已有分支与 PR/线上事实 | 交付前同时查看 `contentSafety`、`publicationCounts` 和 attention 明细 |
| 应当改正 | 旧内容分支长期未建 PR 后与 `main` 发生冲突 | 推送后的人工阶段没有及时完成 | 将 pushed-no-PR 纳入每日收口清单；过期时从新主线重建白名单分支 |
| 建议改进 | 多份阶段复盘缺少统一入口 | 每轮按时间记录，未同步更新总索引 | 用本文作导航，长期规则只维护一份 |

### 做得好的地方

- 始终保留原脏工作区，并在独立 worktree 精确修改；
- 没有为了收口引入在线 CMS、消息队列或第二套数据库；
- 关键判断均由测试、真实仓库状态、部署 revision 和线上页面交叉验证；
- 发现最终状态不一致后停止写“全部完成”，继续定位到可复现根因。

### 下次重点关注

- 发布结束必须检查“已推送未建 PR”和线上 attention 明细，不能只看同步队列；
- 线上核验应继续围绕读者可见文本和资源，不比较 Markdown 隐藏语法；
- 新增迁移先预览、备份和全量验证，再一次性应用；
- 新功能先证明真实需求，优先复用现有状态、队列和入口。
