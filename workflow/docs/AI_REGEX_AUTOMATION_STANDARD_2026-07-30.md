# XGIF 正则与 AI 自动化规范及阶段复盘

状态：当前有效

适用范围：`workflow/` 中的内容整理、体检、推荐与图片资料辅助

日期：2026-07-30

## 1. 本阶段结论

本地发布助手不追求“让 AI 接管发布”，而是把不同类型的问题交给最合适的工具：

```text
固定语法和格式
→ 正则或解析器识别
→ 确定性代码校验

标题、摘要、标签、图片画面和语义相似
→ AI 或向量模型生成候选
→ 人工集中复核

任何 Markdown 写回
→ 内容版本校验
→ 服务端字段校验
→ 保持草稿或进入既有发布门禁
```

最终原则是：正则负责“可精确定义的模式”，AI 负责“需要理解语义的候选”，人负责“事实、价值和发布决定”。

## 2. 什么时候使用正则

正则适用于输入边界稳定、匹配结果可以通过样例穷举、误判成本可控的任务：

| 任务 | 使用方式 | 原因 |
| --- | --- | --- |
| 内容 ID 和日期 | 完整匹配 | 语法固定，必须确定性拒绝非法值 |
| 占位标题 | 完整匹配 | 模式有限，可稳定识别待整理项 |
| 来源前缀和尾部标签行 | 行级匹配 | 只识别结构，不推断来源真实性 |
| 行尾空白和连续空行 | 只读审计 | 适合批量发现，不应默认改写已发布内容 |
| HTTP URL 初筛 | 候选提取后再交给 URL 解析器 | 正则只负责定位，协议、主机和安全边界由解析器验证 |

实现要求：

1. 高价值模式集中在 `content-patterns.js`，不得在多个模块复制略有差异的表达式。
2. 每个模式至少有一个正例和一个反例，并通过 `npm run patterns:examples` 执行。
3. 带全局标志的表达式不得作为跨调用共享的可变实例；需要全局扫描时返回新实例。
4. 正则只识别结构，不推断作者、授权、推荐分组、来源真实性或内容质量。
5. 批量格式治理默认使用 `npm run patterns:audit` dry-run；修改公开 Markdown 前必须评估内容哈希、推荐清单和同步凭据的连锁变化。

不应使用一个大正则解析 Markdown、HTML 或 URL。遇到嵌套结构、转义、协议安全或语义判断时，使用现有解析器和明确的数据模型。

## 3. 什么时候使用 AI

AI 适合答案不唯一、需要语言或视觉理解、并且结果可以由人快速筛选的任务：

- 为占位标题生成标题候选；
- 为过短摘要或缺失标签生成可编辑候选；
- 为图片生成客观 `altText`、描述和标签候选；
- 使用既有向量缓存找出语义近似文章；
- 在严格字符不变量下提出段落空行建议。

AI 不拥有以下决定：

- 是否已完成内部复核；
- 内容属于哪个推荐分组；
- 来源、作者、授权或链接是否真实；
- 内容是否应发布、删除、合并或下架；
- Git、PR、部署或线上状态；
- 图片实际尺寸和比例。

模型结果始终按不可信外部输入处理。服务端必须限制字段类型、长度和数量；图片 `altText` 最长 160 字；标题、摘要和标签写回前重新校验当前 Markdown SHA-256。

## 4. 批量 AI 工作台规范

批量整理的目标是减少逐篇打开和重复调用，而不是扩大自动写入范围。

标准流程：

```text
读取所选草稿和内容 SHA-256
→ 仅筛出占位标题、短摘要或缺标签的文章
→ 限并发请求 AI
→ 按模型、地址和完整输入哈希复用运行时缓存
→ 集中展示候选
→ 人工逐项勾选、修改和确认
→ 服务端重新读取并校验 SHA-256
→ 只更新已确认字段，内容继续保持草稿
```

约束：

1. 已经合理的字段保持原值，不用 AI 做无目的改写。
2. 一项失败不阻断其他候选生成或保存。
3. 缓存只减少相同请求，不替代版本校验，也不证明模型结果正确。
4. 批量保存不能顺带确认内部复核、推荐分组或发布状态。
5. 旧接口可以在兼容期保留，但新界面必须走完整的编辑候选流程。

## 5. 语义重复候选规范

确定性重复检查仍是门禁：

- 正文哈希相同；
- 来源 URL 相同；
- 稳定内容 ID 冲突。

向量相似只用于发现“表达不同但可能重复”的人工复核候选：

- 只读取当前模型的本地缓存，不因打开体检页自动调用模型；
- 只使用与当前语义输入哈希一致的缓存；
- 默认相似度阈值为 0.92；
- 候选按相似度排序并限制返回数量；
- 两两比较有平方级成本，因此限制参与比较的文档数量；
- 不自动删除、合并、退回草稿或改变推荐关系。

缓存不存在或过期时应明确提示刷新离线推荐，不能把“没有可用向量”显示为“没有重复内容”。

## 6. 图片替代文字规范

`altText` 描述读者看不到图片时需要知道的客观画面：

- 可描述主体、动作、构图和理解图片必要的可见文字；
- 不猜测人物身份、心理、动机、来源或授权；
- 不堆砌 SEO 关键词；
- 不重复“图片中显示”“这是一张图片”等无信息前缀；
- 无独立 `altText` 的历史内容继续使用标题兜底。

实际宽高和比例来自文件检测，AI 不能覆盖。

## 7. 本阶段暴露的工程问题

### 7.1 分散正则会产生静默漂移

同一概念若在导入、标题检查和来源解析中各写一份表达式，修复其中一处后其他入口仍会采用旧规则。集中注册表和可执行样例比复制粘贴更容易审计。

### 7.2 批量 AI 不能省略人工确认

逐篇调用效率低，但把全部结果直接写回会把效率问题变成内容风险。正确优化点是“集中生成、集中复核、一次确认”，而不是取消复核。

### 7.3 缓存不能代替并发控制

相同输入缓存能减少费用和等待，但用户可能在候选生成后修改文件。写回前仍必须重新校验内容版本。

### 7.4 相似度不是事实

向量分数只能说明语义接近。两篇文章可能是系列、引用、更新版或真正重复；自动合并会破坏来源和发布事实链。

### 7.5 自动格式化也可能扩大变更

删除几个空行看似安全，却会改变公开 Markdown 哈希、推荐语料哈希和同步版本。没有内容收益时，应报告而不是制造一次发布。

## 8. 验证门槛

涉及本规范的改动至少执行：

```bash
cd workflow
npm run patterns:examples
npm run patterns:audit
npm test
npm run test:browser

cd ../site
npm run build

cd ..
git diff --check
```

还应验证：

- AI 服务未配置时，手工编辑和发布流程仍可使用；
- 候选生成后文件变化时写回返回版本冲突；
- 一项模型调用失败时其他条目可以继续；
- 语义缓存缺失、过期或维度不一致时保守降级；
- `altText` 超长或类型错误时服务端拒绝；
- 体检页不会因为语义检查隐式调用外部模型。

验证证据必须分开表述：测试通过不等于 AI 内容质量已人工验收，本地运行不等于已提交，推送分支不等于已合并或上线。

## 9. 后续自动化判断清单

增加新的正则或 AI 能力前先回答：

1. 输入是否有稳定语法？如果有，能否用解析器或小型正则确定性处理？
2. 输出是否需要语义判断？如果需要，能否作为候选而非事实？
3. 误判会造成提示噪声，还是会修改、发布或删除内容？
4. 是否有内容 SHA-256 或其他版本锁防止覆盖新修改？
5. 是否保留单项失败、人工编辑和取消路径？
6. AI 不可用时核心工作流是否仍然成立？
7. 结果是否会改变公开内容、推荐清单或同步凭据？
8. 能否通过集中复核减少操作，而不取消必要的人类判断？

无法明确回答时，先做只读审计和候选报告，不增加自动写入。
