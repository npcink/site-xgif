# 本地发布助手阶段收尾：流程、经验与后续边界

日期：2026-07-27

## 1. 本阶段结论

本地发布助手已经从“功能逐项堆叠的管理页面”收敛为一个面向单人、本机、桌面浏览器的内容工作台。

当前核心闭环是：

```text
导入或新建内容
→ 在文章或图片工作台整理
→ 保存草稿
→ 自动内容体检
→ 发布到本地
→ 在“同步上线”创建隔离内容分支
→ GitHub PR 合并
→ Cloudflare 部署
→ 线上核验
```

这里有三个必须长期保持清楚的边界：

1. “发布”只表示内容已经写入本地公开站点，不等于已上线。
2. “同步上线”只负责把公开内容提交并推送到 GitHub 内容分支，不等于 PR 已合并。
3. 只有 Cloudflare 部署完成且线上内容核验通过，才显示“已上线”。

## 2. 已确认的产品约束

发布助手当前只有一名使用者，只在本机运行，并且不做移动端。因此本阶段明确删去或不再扩展：

- 多用户、角色与权限管理；
- 移动端导航、响应式编辑器和触屏交互；
- 线上管理后台；
- 为低频功能单独设置一级入口；
- 同一动作在多个页面重复出现；
- 仅用于解释流程、却不能直接完成任务的按钮和卡片。

桌面端最低验收基线为 `1280 × 800`。布局可以密集，但必须让主要任务、当前状态和下一步动作始终可见。

## 3. 文章流程的收敛

### 3.1 主工作区

文章编辑器采用三段式桌面结构：

- 左侧：全局导航；
- 中间：标题、正文和直接作用于正文的工具；
- 右侧：发布信息、封面、预览三个标签；来源并入发布信息，正文上方保留一条可直接打开的来源摘要。

标题生成与正文整理合并到正文旁的“AI 辅助”菜单，仅在主动使用时展开；标题候选仍只修改标题，整理与分段仍受原文逐字校验。

### 3.2 来源信息

来源链接缺失不再阻止发布。真实情况可以是：

- 有明确原文链接；
- 只有来源名称，暂时找不到具体链接；
- 来源尚待确认；
- 原创内容。

系统不应为了通过检查而诱导填写网站首页或虚构链接。重复来源只作为提醒：同一链接可能对应系列内容，也可能是误复制，用户确认后即可继续。

“公开编辑手记”不再作为常规公开字段。编辑过程中的复核说明属于本机内部信息；只有确实需要呈现给读者的内容，才应写入正文。

### 3.3 AI 与确定性校验

AI 只提供建议，不拥有发布决定权：

- 标题一次生成三个候选，选择后只修改标题；
- 正文整理只允许插入 Markdown 段落空行；
- 如果 AI 删除、改写或重排原文字符，服务端丢弃正文结果；
- 摘要、标签和阅读时间需要人工复核；
- 长段落、临时标题等检查仍由确定性规则完成。

这避免了把“模型看起来处理成功”误当成“内容已安全修改”。

### 3.4 发布动作

顶部只固定当前主要下一步“发布”以及条件满足时的“预览”。“保存草稿”和“版本记录”收纳到“更多”，使用时再展开。

“发布”不再因为前置条件而静默变灰。点击后系统保存当前内容并执行发布检查；如果存在问题，直接把原因和修复入口显示在文章上下文中。真实预览是重要建议，但未预览时通过确认提示处理，不再造成无法解释的阻塞。

## 4. 图片流程的收敛

图片编辑器与文章编辑器使用相同的工作台心智：

- 中间区域显示选图、真实比例预览和主要操作；
- 右侧“资料”管理标题、描述和标签；
- 右侧“来源”管理作者、来源链接、授权和来源情况；
- 右侧“设置”管理发布日期与补充正文；
- 顶部只固定主要下一步“发布”；预览按状态出现，保存草稿和版本记录收纳到“更多”。

图片比例以实际文件尺寸自动判断，不要求用户在“方图、宽图、长图”之间重复选择。AI 可以整理描述和标签，但不能覆盖真实尺寸判断。

图片来源继续遵守诚实标注：

- 明确原创或有原始链接时如实填写；
- 用户明确提供且允许公开时使用“用户提供”；
- 无法确认作者和授权时标记“来源待核实”，并保留下架入口；
- 不虚构作者、授权或第三方来源。

## 5. 导入与内容体检

导入、新建、体检和发布不应成为四套互不相通的页面。

合理流程是：

1. 导入只负责把外部内容转成可编辑草稿；
2. 文章或图片工作台负责修正资料和正文；
3. 保存时允许保留未完成状态；
4. 发布时自动执行强制体检；
5. 体检问题必须能回到对应内容和字段修复；
6. “需处理”集中查看跨内容的问题，不重复提供另一套编辑器。

体检结果需要区分：

- 阻断发布：图片缺失、文件无效、必要契约不成立；
- 待人工确认：临时标题、长段落、重复来源、来源待核实；
- 建议项：摘要、标签、封面等可以改善但不应过度阻断发布的内容。

缺少来源链接本身不是硬错误。

“草稿”只表示内容可见性，不再表示体检未通过。历史已经上线但仍有内部复核备注未确认的内容标记为“历史复核债务”，保持现有线上状态；下次编辑或同步前必须完成复核。

## 6. 同步上线的隔离边界

旧做法可能从当前开发分支直接创建内容分支，存在把代码提交或工作区修改一起带入公开内容同步的风险。

现在的同步逻辑是：

```text
获取最新 origin/main
→ 创建临时 worktree
→ 创建 content-sync/<时间> 隔离分支
→ 只复制白名单内的文章或图片 Markdown
→ 只提交所选公开内容
→ 推送 GitHub
→ 按内容 ID 与 Markdown SHA-256 写入同步凭据
→ 删除临时 worktree
```

白名单仅允许：

- `site/src/content/articles/*.md`
- `site/src/content/images/*.md`

当前工作分支不切换，开发代码、未提交修改、草稿、数据库、日志和私有记录都不会被夹带。推送成功后删除本地临时分支；同一内容哈希再次同步时复用已有凭据，不重复创建提交。如果远端拒绝推送，则保留本地分支，并只重试凭据记录的原分支。

发布助手只读查询 GitHub PR、检查和 Workers Builds 状态；创建与合并 PR 仍需人工完成：

1. 打开 GitHub 比较链接并创建 PR；
2. 等待 CI；
3. 合并 PR；
4. 等待 Cloudflare Workers Static Assets 部署；
5. 执行线上核验。

发布助手不能把“分支已推送”描述成“网站已上线”。

完整状态链为：

```text
本地版本
→ 内容分支已推送
→ PR 已创建
→ 检查中 / 检查失败 / 检查通过
→ PR 已合并
→ Workers Builds 通过 / 失败
→ 线上内容已核验
```

## 7. 本阶段暴露的问题

### 7.1 灰色按钮没有解释

按钮禁用虽然能防止错误操作，却隐藏了系统判断。用户只能看到“不能点”，不知道缺什么。

改进原则：主要动作尽量保持可操作；点击后给出具体原因、修复位置和可继续路径。

### 7.2 同一流程在多个位置重复

保存、发布、同步、预览、AI 和体检曾分别出现在顶部、底部、卡片和侧栏，造成“哪个才是主入口”的疑问。

改进原则：一个任务只保留一个主入口。低频信息放入标签或系统页，不再靠增加卡片解决。

### 7.3 信息和操作混在一起

来源、封面、发布方式、高级设置和内部说明被堆在正文下方，页面过长，正文编辑失去中心。

改进原则：正文画布保持专注；补充资料进入固定右侧检查器；只把直接作用于正文的工具放在正文附近。

### 7.4 共享样式类造成跨页面碰撞

文章和图片工作区复用同一个工具栏类时，一处布局修改可能意外改变另一处页面。

改进原则：共享基础视觉可以复用，但布局职责需要显式的页面级类和桌面回归测试，不能只凭类名相似合并。

### 7.5 “响应式”规则破坏桌面基线

为窄屏准备的媒体查询曾在 `1280px` 基线下过早触发，导致图片表单堆叠。项目既然明确不做移动端，就不应让移动端假设反过来损害桌面效率。

改进原则：先固定真实使用环境的验收尺寸，再决定是否需要响应式规则。

### 7.6 Git 同步没有隔离当前开发状态

内容发布与代码开发共用仓库时，直接在当前分支提交很容易把两个不同目的的变更混到一起。

改进原则：内容同步从生产基线创建临时工作树，并使用严格文件白名单；代码提交和内容发布分别审查。

## 8. 可复用的开发方法

### 8.1 先定义状态，再设计按钮

先明确“草稿、本地发布、已推送、PR、已部署、已核验”等事实，再决定页面展示什么动作。不能先做一个“同步上线”按钮，再让后台状态勉强解释它。

### 8.2 用真实约束换取简单

单人、本机、桌面端不是缺陷，而是可以主动利用的产品约束。它允许移除账户体系、移动导航、在线权限和复杂兼容层，把注意力集中到内容处理效率。

### 8.3 AI 负责建议，规则负责安全

凡是涉及原文完整性、文件格式、路径白名单、发布状态和 Git 边界，都使用确定性代码检查。AI 适合生成候选和整理建议，不适合成为唯一验证者。

### 8.4 低频能力进入上下文，不进入主导航

版本历史、恢复、标签治理、授权说明等功能应该在需要时出现，而不是因为“已经开发”就长期占据主界面。

### 8.5 失败要保留恢复点

同步失败时保留本地内容分支；数据库损坏时从 Markdown 重建；草稿进入私有历史。所有自动化都应优先保证内容可恢复，而不是追求表面上的一步完成。

### 8.6 验证必须覆盖真实桌面流程

本阶段的验证组合包括：

- 单元测试：来源规则、发布契约、AI 输出完整性、隔离同步；
- HTTP 集成测试：服务端路由、防护和真实请求；
- 桌面浏览器回归：`1280 × 800` 下的文章、图片、标签切换和操作状态；
- 差异检查：只提交代码、测试和文档，不夹带用户内容与本地记录。

浏览器测试不是为了覆盖所有视觉细节，而是锁定最容易回归的结构边界和关键操作。

## 9. 后续开发判断清单

每次准备增加按钮、字段或页面前，先回答：

1. 它是否让发布一篇文章或一张图片更快？
2. 这个问题是否在真实使用中重复发生？
3. 能否合并到现有动作、标签或状态说明中？
4. 它属于本地保存、公开同步、云端部署还是线上核验？
5. 它是否可能夹带私有内容或当前开发分支？
6. AI 结果是否有确定性校验和人工复核入口？
7. 在 `1280 × 800` 下，主要任务是否仍无需寻找？
8. 删除它是否反而让流程更清楚？

如果前两项不能明确回答“是”，优先记录观察，不立即开发。

## 10. 当前维护建议

短期不再扩展大型功能，后续只围绕真实发布记录处理：

- 观察来源缺失、重复来源和长段落提示是否仍造成误解；
- 记录发布失败的真实原因，只有重复出现才增加自动修复；
- 检查“同步上线”中 PR、部署和线上核验状态是否准确；
- 保持公开 Git 与私有内容 Git 的权限和白名单分离；
- 每次 UI 调整都运行桌面浏览器测试；
- 定期删除已经不再承担任务的说明卡、重复按钮和旧入口。

阶段目标不是让发布助手拥有更多功能，而是让“整理内容、发布到本地、同步上线”三个动作始终简单、诚实、可恢复。
