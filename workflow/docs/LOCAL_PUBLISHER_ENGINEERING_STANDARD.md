# XGIF 本地发布助手工程规范

状态：当前有效

适用范围：`workflow/` 本地发布助手，以及它对 `site/` 内容目录的读写和同步

最后更新：2026-07-30

## 1. 目标与非目标

本工具是单人、本机、PC 优先的内容工作台。它的目标是让“整理内容、发布到本地、同步上线、故障恢复”简单、诚实、可恢复。

长期不主动引入：

- 多用户、角色、权限和在线管理后台；
- 在线 CMS、常驻消息队列或第二套内容数据库；
- 为低频动作增加一级菜单、固定卡片或重复按钮；
- 由 AI 自动决定发布、来源、授权或线上状态；
- 把公开代码、公开内容和私有草稿放入同一提交。

若真实使用约束改变，应先写 ADR，再改变这些边界。

## 2. 真相源和事实边界

不同事实必须由拥有它的系统回答，不能用相邻状态代替：

| 事实 | 权威来源 | 是否可重建 |
| --- | --- | --- |
| 内容正文和公开元数据 | `site/src/content/**/*.md` | 否 |
| 本地内容、回收站和操作索引 | SQLite | 是，可从 Markdown 与旁车重建 |
| 本地版本与同步批次关系 | `publication-events.jsonl`，按内容 SHA-256 绑定 | 由私有内容 Git 备份 |
| 内容分支、PR 和检查 | GitHub | 只读查询 |
| 构建和部署 | Cloudflare Workers Builds | 只读查询 |
| 页面是否真正上线 | 线上 URL 的内容核验 | 否，必须实时核验 |
| 推荐清单 | `site/src/data/recommendations.json` | 是，可重新生成 |
| 私有正文和草稿历史 | 本机私有 Git及其私有远端 | 否 |

禁止的状态替代包括：

- `draft: false` 不等于已推送或已上线；
- 当前工作区 clean 不等于远端已包含该内容；
- PR 合并或构建通过不等于线上内容核验通过；
- HTTP 200 不等于内容版本正确；
- 推荐规则回退成功不等于向量服务健康；
- SQLite 文件时间不等于内容备份新鲜。

## 3. 状态模型

内容位置和内容质量是两个维度，必须分开表达。

内容位置：

```text
草稿
→ 本地发布
→ 内容分支已推送
→ PR 已创建
→ 检查通过
→ PR 已合并
→ 部署通过
→ 线上内容已核验
```

内容质量：

```text
合格 / 需人工复核 / 阻断
```

规则：

1. “草稿”只表示公开可见性，不表示质量失败。
2. 历史上线内容出现复核债务时保持线上位置，但编辑或再次同步前必须解决。
3. 远端查询失败时显示“远端待确认”并保留最后已知事实，不猜测成功。
4. 所有页面使用同一状态计算，不为列表、详情和系统页分别发明别名。
5. 每个状态必须能回答“依据是什么、下一步是什么、失败后如何恢复”。

## 4. UI 与交互规范

### 4.1 信息架构

- 一级入口固定为“内容库 / 新建 / 导入内容 / 同步上线 / 系统”。
- 同一任务只保留一个主入口；版本、恢复、标签治理和技术细节按需展开。
- 编辑器保持三段式：左侧全局导航、中间内容画布、右侧上下文检查器。
- 最低桌面验收尺寸为 `1280 × 800`。没有明确需求时，不为移动端增加会破坏桌面密度的布局。

### 4.2 动作层级

- 每个工作区同一时刻只有一个主动作。
- 次要动作进入“更多”、标签页或上下文菜单。
- 不使用无法解释的灰色主按钮；用户点击后应看到具体阻断原因和修复位置。
- 批量选择只在进入批量模式后出现，避免把“当前查看”和“批量选择”混为一谈。
- 间距使用统一层级：同组动作紧邻，动作组之间留出明显间隔，危险动作与常规动作分组。

### 4.3 渐进披露

功能入口在与任务相关时出现：

- AI 标题和分段在正文上下文中按需展开；
- 筛选、排序、每页数量、刷新和回收站归入“筛选与工具”；
- Git、部署和线上事实集中在“同步上线”；
- 备份、恢复和标签治理集中在“系统”。

新增按钮前必须先证明现有入口无法承载该任务。

## 5. 批处理和队列规范

批次不得由最差单项决定。标准流程是：

```text
读取所选内容及版本
→ 逐项体检
→ 分为可执行、需复核、阻断和跳过
→ 只执行可执行项
→ 逐项记录结果
→ 返回部分成功摘要和可重试项
```

必须满足：

1. 单项失败只影响自己，健康内容继续处理。
2. 失败项保留原状态和选择，便于修复后重试。
3. 批次返回成功、失败、跳过数量，并为每项返回明确原因。
4. 写入前携带编辑器打开时的 SHA-256；真正替换文件前再次核验，冲突时拒绝覆盖。
5. 体检后的文件复制到隔离工作树后再次核对 SHA-256。
6. AI 分段在批处理边界再次证明只增加换行，没有删除、改写或重排字符。
7. 内容写入、隐藏索引刷新和删除恢复进入单进程串行队列。
8. AI、质量检查和纯只读查询不占用内容写队列。
9. 私有远端推送使用独立串行队列和有界超时，不能阻塞本地保存。
10. 导入初次解析只负责分类；发布资格必须按用户最终编辑的标题、来源、分组和正文重新检查。
11. 有异常时界面可以只显示异常项，但不能丢失同批已选的健康项目。
12. 整批推荐分组和复核确认必须允许单项覆盖，并绑定当前内容哈希。

不要用“整批一个布尔值”、`Promise.all` 无隔离失败或一个全局远端异常代替逐项结果。

### 5.1 批量发布专用门禁

“发布到本地”不是普通状态切换。批量发布必须使用专用的“检查 → 人工确认 → 按版本执行”流程，通用批量状态接口只能用于退回草稿。

检查结果至少包含：

- 明确的内容类型和仓库相对路径；
- 标题、来源、摘要和必要的正文上下文；
- 内容 SHA-256；
- 长段落数量和最长段落；
- 内部复核备注及状态；
- 当前推荐分组及是否需要人工选择；
- 不能自动处理的逐项阻断原因。

执行请求必须逐项携带检查时的 SHA-256。文章还必须携带本次由人确认的推荐分组；服务端重新规范化允许值并在写入前再次执行版本和质量检查。不得把推荐分组交给 AI 猜测，也不得因为缺失分组把用户赶到八个单篇编辑器。

### 5.2 可自动处理与人工判断

批量门禁按责任处理问题：

- 格式、段落、版本、路径和字段允许值由系统处理或校验；
- 来源真实性、内部备注是否已核对、推荐分组等语义决定由人确认；
- 人工判断集中在批量清单中，只有需要阅读全文才能决定的异常才进入单篇处理；
- AI 只在本地规则无法完成段落整理时提供候选，写入前仍由确定性不变量决定能否采用。

## 6. 同步上线规范

### 6.1 隔离提交

内容同步必须：

1. 获取最新 `origin/main`；
2. 创建临时 worktree 和 `content-sync/<时间>` 分支；
3. 只复制所选公开文章或图片 Markdown；
4. 重新核验内容哈希；
5. 精确暂存并提交白名单文件；
6. 写入 `prepared` 发布回执并保留本地分支；
7. 推送远端；
8. 写入 `push_succeeded` 或 `push_failed` 终态回执；
9. 终态持久化成功后才清理临时分支和工作树。

不得切换当前开发分支，也不得夹带代码、草稿、数据库、日志或私有记录。

### 6.2 幂等与恢复

- 发布身份为 `contentId + Markdown SHA-256`。
- 相同版本已有成功回执时，不重复创建同步分支。
- 推送失败只重试回执记录的隔离分支，不能推送当前工作分支。
- 推送成功但终态回执失败时保留本地分支，以 GitHub 远端和本地分支共同恢复事实。
- 回执采用临时文件加原子替换的逻辑追加；现有日志损坏时拒绝继续写入。
- 推送成功后可以自动创建或复用对应 `content-sync/*` PR；创建失败必须保留分支与比较链接，且永不自动合并。

### 6.3 上线判定

PR、检查、合并和部署逐分支查询；一个分支失败不得污染其他分支。只有线上页面按预期内容核验通过，才能显示“已上线”。

正文锚点必须来自渲染后可见语义，而不是原始 Markdown 语法。Markdown 链接保留标签文本并去除目的地址，图片保留替代文本并去除资源地址；否则源文件中的 URL 会造成线上已正确渲染却被误判失败。

## 7. 数据安全与恢复规范

- 日常保存顺序是 Markdown 原子写入、SQLite 索引、本机私有 Git；私有 GitHub 是异地副本，不是保存前置条件。
- SQLite 损坏时先隔离原文件，再从 Markdown、回收站旁车和操作记录重建。
- SQLite 备份新鲜度与逻辑内容变更时间比较，不与 WAL 或启动时间比较。
- 恢复演练必须绑定运行时代码版本和内容指纹，不能只比较条数。
- 回收站恢复和永久删除只接受记录 ID；路径、类型和原位置来自服务端权威索引。
- R2 对象使用内容寻址、私有字节备份和观察期清理，不提供批量模糊删除。
- `.env`、SQLite、日志、模型向量、私有正文和运行时回执不得进入公开仓库。
- `publication-events.jsonl` 由私有内容 Git 强制纳入快照，公开仓库保持忽略。

恢复能力至少覆盖：

1. Markdown 或图片误删；
2. SQLite 损坏；
3. 回收站索引丢失；
4. 内容分支推送失败；
5. 推送成功但本机终态记录中断；
6. 私有远端超时或不可用；
7. 推荐向量服务不可用后的规则降级与恢复。

## 8. 安全规范

- 服务只监听回环地址，并校验 Host、Origin、JSON Content-Type、请求大小和 CSRF 会话。
- 浏览器传入的路径、类型、远端状态和上游 `applied` 标记均不可信，服务端重新解析并验证。
- Git、GitHub CLI、SSH 和第三方接口错误在进入 API、SQLite、JSONL 或浏览器前统一脱敏并限制长度。
- 文件操作使用白名单根目录、规范化路径和原子替换。
- 密钥只存在于本机 `.env` 或受控凭据存储；测试输出、错误消息和文档不得出现实际值。

## 9. AI 与推荐规范

- AI 只生成候选，不拥有发布决定、事实判定或权限。
- 原文完整性、路径、格式、授权、质量门禁和状态转换使用确定性规则。
- AI 整理正文只允许增加 Markdown 段落空行；服务端执行字符级不变量检查。
- 短文不提供补全、扩写或凑字数能力。少于 80 字只触发人工完整性确认，确认写入 `shortFormReviewed: true`，正文变化后自动失效。
- AI 不虚构来源、作者、授权或原文链接。
- 推荐生成区分“静态清单是否最新”和“向量能力是否健康”。
- 向量失败时可以使用规则推荐继续构建，但界面和状态必须明确标记降级原因；严格验收使用 `--require-embeddings`。

## 10. 错误处理和可观测性

每个跨边界动作至少记录：

- 操作对象与稳定 ID；
- 输入版本或内容哈希；
- 开始、准备、成功或失败阶段；
- 可安全展示的错误摘要；
- 恢复或重试目标。

错误文案应回答：

1. 哪一项失败；
2. 其他项目是否继续；
3. 内容是否已经写入本地或远端；
4. 用户下一步应修复、重试还是等待；
5. 系统保留了哪个恢复点。

“发生错误”“同步失败”或把原始 stderr 直接显示给用户都不合格。

## 11. 验证和发布门槛

### 11.1 每次代码变更

```bash
cd workflow
npm test
npm run test:browser

cd ../site
npm run build

cd ..
git diff --check
```

另外按风险选择：

- 数据层：运行恢复演练、SQLite `PRAGMA quick_check` 和私有 Git `fsck`；
- R2：运行只读 `r2:reconcile`；
- 依赖变化：运行 `npm audit`；
- 发布状态：使用临时仓库或受控内容做逐阶段验证；
- UI：在 `1280 × 800` 检查主动作、间距、渐进披露和错误态。

### 11.2 故障注入

涉及队列、远端或持久化时至少覆盖：

- 单项失败而同批其他项成功；
- 体检后文件被外部修改；
- `prepared` 后进程中断；
- 推送成功但终态回执失败；
- 一个 GitHub 分支查询失败；
- 私有远端超时；
- 损坏 JSONL、SQLite 或回收站旁车；
- 推荐向量服务降级和恢复。

### 11.3 发布证据

必须分别报告：

1. 本地代码和测试结果；
2. 提交 SHA 与远端分支；
3. PR 和 CI；
4. 部署 revision；
5. 线上内容核验。

前一项成功不能替代后一项。没有执行的阶段要明确写“未执行”。

## 12. Git 和提交边界

代码提交应精确暂存：

- `workflow/` 程序、测试、公开说明和工程文档；
- `site/` 中与本轮代码契约直接相关的 ADR、模板或静态生成数据。

默认排除：

- 私有或待复核文章与图片 Markdown；
- `publication-events.jsonl` 和当前体检快照；
- `.env`、SQLite、日志、备份、回收站和私有正文；
- 与本轮无关的公开内容修改；
- 已由独立 `content-sync/*` 分支承载的内容。

公开内容同步和代码开发使用不同分支、不同白名单、不同验收。脏工作区中禁止使用宽泛的 `git add .`，也不得 reset、stash 或覆盖用户内容。

## 13. 变更前判断清单

增加能力前逐项回答：

1. 这是重复出现的真实问题，还是一次性不适？
2. 它缩短核心发布流程，还是只增加可见复杂度？
3. 能否复用现有入口、状态或队列？
4. 它改变了哪个事实源或责任边界？
5. 单项失败时，其他内容是否仍能继续？
6. 远端副作用前是否已有可恢复意图？
7. 进程中断后能否判断已经做到哪一步？
8. 是否可能夹带私有内容、开发代码或凭据？
9. AI 输出是否有确定性校验和人工复核？
10. 提交后的独立源码是否可以通过测试和构建？

不能明确回答时先记录观察和故障证据，不立即增加功能。
