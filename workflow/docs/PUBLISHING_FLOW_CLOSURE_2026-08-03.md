# XGIF 导入与发布流程闭环记录（2026-08-03）

状态：历史阶段记录；当前提交与合并状态以 GitHub 主线为准

适用范围：`workflow/` 本地发布助手、`site/src/content/` 内容合同，以及 GitHub 内容分支同步

## 1. 本阶段解决的问题

本阶段从真实使用反馈“发布或者导入文章的流程比较繁琐”出发，不增加新的内容系统，而是缩短已有路径并统一事实边界。

调查发现的主要摩擦是：

- 导入资格沿用 ZIP 初次解析结果，用户修正标题、来源或正文后仍可能被旧状态阻断；
- 推荐分组需要逐篇设置，异常内容和正常内容混在同一列表；
- 导入发布前存在重复确认，内容库发布又重复复核同一版本；
- 本地发布成功后，用户还要重新寻找同步入口并手工创建 PR；
- 固定字数检查把“短文”误判为“正文不完整”，诱导补写原文；
- 自动化通过、本地服务可用、GitHub 已推送和线上已核验容易被混成一个结论。

最终目标不是“更多按钮”，而是一条短、可解释、可恢复的主路径：

```text
导入并解析
→ 只集中处理异常
→ 整批确认推荐分组与内容复核
→ 按最终编辑内容重新体检
→ 发布到本地 Markdown
→ 继续同步上线
→ 推送隔离内容分支并创建或复用 PR
→ 人工合并
→ 部署与线上内容核验
```

## 2. 已接受的产品决策

### 2.1 导入资格必须以最终内容为准

ZIP 解析状态只用于初步分类，不能拥有最终发布资格。用户修改后的标题、来源、分组和正文必须在服务端重新执行质量检查；任何入口都不能信任客户端传入的 `ready` 状态。

有异常时默认只显示“需处理”项，但正常项仍保持选中并留在同一批次。这样用户集中处理少数例外，不需要重新选择整批内容。

### 2.2 批量操作减少重复劳动，不取消人工判断

- 推荐分组可以一次应用到所选文章，单项仍可覆盖；
- 来源不明、短文和疑似重复可以整批确认一次；
- 确认只对当前内容版本有效；标题、来源或正文变化后自动失效；
- 单项失败只保留该项，其他安全项目继续发布；
- 精确重复始终跳过，不能靠人工确认绕过。

### 2.3 短文不补写

字数只决定是否需要人工确认，不能决定原文是否完整。

少于 80 字的正文遵循以下合同：

1. 未确认时显示“请确认原文完整”；
2. 确认后写入 `shortFormReviewed: true`；
3. 正文变化后确认自动失效；
4. 排版只能增加 Markdown 段落空行；
5. 不提供补全、扩写、润色、续写或凑字数功能；
6. 去除允许新增的空行后，字符和标点必须与原文完全一致。

因此站点质量测试不得再使用“正文必须至少 80 字”作为完整性证明。正确门槛是“正文非空、不是历史摘要占位；短文具有明确人工确认”。

### 2.4 本地发布后直接进入同步，但不自动合并

本地发布完成后提供“继续同步上线”。同步仍使用从 `origin/main` 创建的隔离 `content-sync/*` 分支，只携带白名单公开内容和依赖资源。

推送成功后：

- 查询该内容分支是否已有 PR；
- 没有时自动创建 PR；
- 创建失败时保留已推送分支和比较链接；
- 永不自动合并；
- PR、CI、合并、部署和线上核验分别报告。

## 3. 关键实现合同

### 3.1 正文不变量

`safeParagraphSuggestion` 是所有自动分段结果的最终边界。候选正文只允许插入换行，并且必须增加真实 Markdown 段落；删除、替换、截断、重排字符或把已有段落合并都会被拒绝。

AI 提示词不是安全边界。服务端确定性校验才是安全边界。

### 3.2 内容版本

发布和批量写入携带 `contentSha256`。检查后、真正写入前以及隔离工作树复制后都重新核验版本；发现并发修改时拒绝覆盖。

人工复核状态与当前 Markdown 一起进入内容哈希。内容变化后不能复用旧确认。

### 3.3 短文确认

`shortFormReviewed` 是内容元数据，不是 UI 临时状态：

- Flomo 直发在用户确认短文批次后写入；
- 内容库批量发布在明确确认后写入；
- 单篇编辑器正文变化时重置为 `false`；
- Astro schema 负责解析该字段；
- 内容审计和站点质量测试使用同一语义。

### 3.4 GitHub PR

GitHub 操作使用 `gh`，普通 Git 操作继续使用 shell `git`。PR 自动化只接受 `content-sync/*` 分支，先查询现有 PR，再创建新 PR。失败消息必须脱敏且有界，不能把本地路径、令牌或完整 stderr 写入浏览器或操作记录。

## 4. 开发过程中的经验

### 4.1 先找主流程，不从按钮开始

流程繁琐往往不是缺少能力，而是同一判断被拆到多个页面、多个按钮和多个状态中。正确顺序是：

1. 写出用户要完成的完整任务；
2. 找出只有系统能做的确定性检查；
3. 找出必须由用户判断的少数例外；
4. 把例外集中展示；
5. 让主动作连续进入下一阶段。

### 4.2 长度、质量和完整性不是同一事实

固定阈值适合触发复核，不适合证明文本完整。原文可能天然很短，也可能很长但已经截断。完整性必须来自来源事实、人工确认和字符不变量，而不是凑够数字。

### 4.3 测试夹具必须尊重其他真实门槛

本阶段出现过两类测试误导：

- 为验证导入路径构造了超长单段正文，意外触发真实长段落防线；
- 为验证短文确认创建了两篇相同正文，意外触发真实重复内容防线。

修正方法不是放宽生产规则，而是让夹具只制造当前测试需要的变量。测试失败时先判断它是否揭示了另一条正确的不变量。

### 4.4 运行目录也是工程合同

仓库根目录没有 `package.json`。发布器命令在 `workflow/` 执行，站点命令在 `site/` 执行。错误目录导致的 `ENOENT` 不是代码失败，但会污染验收叙述，因此文档和自动化必须写明工作目录。

### 4.5 真实用户验收不能只看测试

本阶段同时使用：

- 单元与契约测试验证状态和安全规则；
- HTTP 集成验证本机 API；
- 浏览器回归验证工作区与交互；
- 实际本地页面验证真实内容、控制台和布局；
- Astro build 与内容测试验证发布器输出能被站点消费；
- 逐字脚本验证 68 字短文只增加一个段落空行。

短暂出现的“123 已上线、1 发布中”在远端状态刷新后收敛为“124 已上线”。这说明缓存状态需要诚实标记“正在刷新”，也说明一次截图不能代替最终接口事实。

### 4.6 脏工作树中先确定归属，再提交

共享工作树同时存在代码、公开内容、视觉基线、运行台账和其他文档。收尾时必须：

- 列出精确候选文件；
- 排除 `workflow/records/*.jsonl`、视觉快照和无关内容；
- 检查新模块是否已被候选代码引用；
- 在隔离工作树验证“仅候选文件”的构建和测试；
- 禁止 `git add .`、stash、reset 或覆盖其他会话改动。

## 6. 后续变更规则

以后修改导入或发布流程前，必须回答：

1. 新动作是否缩短主路径，而不是增加按钮？
2. 它处理的是内容质量、内容位置、远端状态还是运行健康？
3. 客户端状态是否会在服务端按最终内容重新验证？
4. 人工确认绑定哪个内容版本，修改后如何失效？
5. AI 输出的可修改字段和字符不变量是什么？
6. 单项失败是否会阻断健康项目？
7. 远端副作用失败后保留哪个恢复点？
8. 自动化、真实浏览器、构建和远端证据分别覆盖什么？
9. 精确提交是否排除了私有记录和其他工作？

不能明确回答时，先做只读调查，不继续增加功能。
