# XGIF 仓库收尾与 Git 卫生规范

状态：生效

版本：1.0

日期：2026-08-03

适用范围：`site-xgif` 的代码、文档、公开内容、私有运行台账、分支和 worktree 收尾

## 1. 目的

本规范解决的不是“怎样让 `git status` 变空”，而是怎样在多分支、多 worktree、本地运行数据与公开代码混合存在时，得到一个真实、可恢复、可继续工作的仓库状态。

它补充以下文档：

- [开发与交付规范](DEVELOPMENT_AND_DELIVERY_STANDARD.md)：约束日常开发、验证和 PR；
- [发布、恢复与阶段收尾规范](RELEASE_CLOSURE_STANDARD.md)：约束代码进入生产后的证据链；
- [ADR-013](decisions/ADR-013-public-code-private-content-github-boundary.md)：约束公开仓库与私有内容历史的职责边界。

仓库收尾必须同时回答：

1. 有价值的代码是否已经进入受保护主线；
2. 未提交状态究竟是新工作、历史形状造成的假差异，还是不能公开的运行数据；
3. 分支、PR 和 worktree 是否仍有独立恢复价值；
4. 删除任何对象前，代码和私有状态能否从明确位置恢复；
5. 收尾后是否仍能正常启动本地发布台并继续工作。

## 2. 2026-08-03 收尾案例

本次收尾从一个落后主线、包含大量未提交状态的主工作区开始。最终结果为：

- 有价值的候选通过 PR #47 汇总并合并，主线提交为 `d183309`；
- PR 所需的 Astro site、Local publisher 和 Workers Builds 检查通过；
- 第一轮删除 25 个本地旧分支和 13 个远端旧分支；
- 第二轮在保护运行数据后删除最后一个本地开发分支及其远端分支；
- 自动生成但已被 PR #3 替代的 Cloudflare 分支经 PR #4 关闭说明复核后删除；
- 最终公开仓库只有 `main`、一个主 worktree、零开放 PR；
- 本地 `flomo-imports.jsonl` 和 `r2-assets.jsonl` 没有提交到公开主线，而是由私有内容仓库 `history` 提交 `92c94de` 保存；
- 本地发布台、Astro 预览和 SQLite 在迁移后重新验证可用。

以上 SHA、分支数量和 PR 状态是本次时间点证据，不得当作以后运行的当前事实。长期有效的是下面的判断方法。

## 3. 核心经验

### 3.1 `git status` 是线索，不是变更所有权

旧分支落后主线时，已经进入 `main` 的文件可能继续显示为修改或未跟踪。普通 `git diff main` 还可能把“旧分支未跟踪、但主线已跟踪”的文件显示为删除。

本次 146 条状态记录中，逐文件比较工作区内容哈希与 `main:<path>` 后确认：

- 120 条与主线 blob 完全一致；
- 26 条才是真实内容差异。

因此，收尾时必须比较文件内容与权威基线，不能按状态条数推断工作量，更不能直接 `git add -A`。

### 3.2 “没有需要提交的公开代码”是合法结论

26 条真实差异继续按所有权拆分后包括：

- 已被主线实现替代的生产巡检方案；
- 会撤销数据遮罩策略的旧视觉测试与截图；
- 少一条收口链接的旧文档版本；
- 两份属于私有恢复边界的本地运行台账。

它们都不应形成新的公开提交。收尾的成功标准是保留正确事实，不是必须制造 commit。

### 3.3 合并判断不能只看祖先关系

分支可能通过 squash、cherry-pick 或选择性重建进入主线，此时 `git branch --merged` 仍会显示未合并。删除前应组合判断：

- PR 是否已合并或明确关闭；
- 分支独有提交影响的路径是否已经进入主线；
- 当前树内容是否被主线等价覆盖；
- 是否仍有开放 PR、活动 worktree 或未备份状态；
- 是否存在明确的替代实现和关闭说明。

PR #14 已合并但分支提交不是 `main` 的直接祖先；PR #4 未合并，但关闭说明明确记录其被 PR #3 替代且方案违反静态部署边界。两者都需要语义证据，不能只运行一个 Git 命令。

### 3.4 公开 Git 与私有内容 Git 必须分别收口

`workflow/records/flomo-imports.jsonl` 和 `workflow/records/r2-assets.jsonl` 会被公开仓库 Git 跟踪，但其本地完整版本属于用户运行状态。普通代码或文档收尾不得顺带公开它们。

清理旧工作区前，本次分别核对了：

```text
工作区文件 blob
= 本地私有 history blob
= 远端私有 origin/history blob
```

只有三者一致，且私有 Git 对象检查通过后，才允许清理承载这些文件的旧分支状态。

### 3.5 主 worktree 还承载被忽略的运行数据

主 worktree 不只是源码目录，还可能包含：

- `workflow/.env`；
- `workflow/.runtime/xgif.sqlite3` 及 WAL；
- `workflow/backups/`；
- `workflow/private-sources/`；
- `workflow/trash/`；
- 私有导入包和本地项目配置。

这些路径不会出现在普通 `git status` 中。强制删除主 worktree 即使没有丢失已跟踪代码，也可能删除唯一的本地运行状态。

本次最初尝试用 `git worktree move` 迁移主工作区，Git 在任何写入发生前拒绝了操作，因为初始主 worktree 不能这样移动。正确方案是：停止占用进程，单独保护私有台账，移除辅助 worktree，在主路径原地切换到已验证的 `main`，再恢复私有台账。

### 3.6 先停服务，再迁移 SQLite

迁移前发现本地发布台仍打开 SQLite、WAL 和日志，Astro 预览也仍在旧路径运行。直接移动目录会让进程继续持有旧 inode，并可能造成数据库与路径状态分裂。

标准顺序是：

```text
npm run stop
→ 确认端口与文件占用消失
→ 迁移或切换工作区
→ PRAGMA quick_check
→ npm run start
→ npm run status
```

### 3.7 删除应精确、延后且尽量可恢复

- 先删除已合并、无开放 PR、无 worktree 占用的明确候选；
- 对选择性吸收的分支记录原 SHA，再按明确名单删除；
- 当前脏分支和系统生成分支在证据不足时保留；
- 临时台账副本在恢复验证后移入 macOS 废纸篓，而不是直接永久删除；
- 每次删除后重新 fetch/prune 并列出远端 heads、worktree 和状态。

## 4. 事实来源模型

| 对象 | 能证明什么 | 不能单独证明什么 |
| --- | --- | --- |
| 工作区文件内容 | 当前磁盘上的真实字节 | 文件是否应该提交 |
| `main:<path>` blob | 主线记录的文件内容 | 生产是否运行该版本 |
| 分支提交图 | 提交祖先与独有提交 | squash 或重建是否已吸收语义 |
| GitHub PR | 审查、checks、关闭和合并事实 | 私有运行数据是否已备份 |
| 公开 `origin/main` | 公开代码权威主线 | 本地发布台运行版本 |
| 私有 `origin/history` | 白名单内容与恢复台账的异机历史 | 公开部署是否完成 |
| SQLite / WAL | 当前本地派生状态 | 公开 Markdown 的最终真相 |
| `/build.json` 与生产探测 | 线上构建和探测路径 | 本地恢复链是否完整 |

任何收尾结论都应指出依赖了哪一行事实，避免用相邻证据代替目标事实。

## 5. 标准收尾流程

### 5.1 冻结写入面

先记录并只读检查：

```bash
pwd
git status --short --branch
git worktree list --porcelain
git fetch origin --prune
gh pr list --state open
```

如果本地发布台或预览正在使用待迁移工作区，先使用项目命令停止。不要直接 kill 未确认的进程，不要在 SQLite WAL 活跃时移动数据库。

### 5.2 建立候选清单

分别列出：

- 当前分支相对 `origin/main` 的独有提交；
- 本地与远端分支的 ahead/behind 和 merged 状态；
- 每个 worktree 的路径、分支、HEAD、脏状态和用途；
- 开放、已合并和已关闭 PR；
- 被忽略但需要保护的本地运行目录。

不要把分支、worktree 和目录混为一类对象：删除 worktree 不等于删除分支，删除远端分支也不等于本地状态已处理。

### 5.3 去除历史形状造成的假差异

对每个状态路径：

1. 如果工作区和 `main` 都有文件，比较 `git hash-object <file>` 与 `git rev-parse main:<file>`；
2. 内容相同的文件标记为“已在主线，不提交”；
3. 内容不同或一侧缺失的文件进入真实差异清单；
4. 对未跟踪文件执行同样的主线 blob 检查，不能直接视为新文件；
5. 对二进制视觉基线使用文件哈希、测试意图和截图审查共同判断。

### 5.4 按所有权拆批

真实差异至少拆为：

- 公开代码；
- 公开内容；
- 文档；
- 视觉基线；
- 私有运行台账；
- 被忽略的本地状态。

每批只允许进入对应的交付路径。代码和文档走公开 PR；私有内容走 `history`；运行缓存和 SQLite 不进入任一公开提交。

### 5.5 收敛有价值改动

旧分支包含混合改动时，从最新 `origin/main` 创建隔离 worktree，把仍有价值的部分重建为可审查的最小批次。不要为了保留旧提交形状而整分支合并。

候选进入主线前必须：

- 精确暂存路径；
- 检查 staged diff 和秘密模式；
- 按改动范围运行测试；
- 完成正确性、可读性、架构、安全性和性能五轴审查；
- push、PR、checks 和合并结果逐层核对。

### 5.6 清理分支

| 分支状态 | 默认动作 |
| --- | --- |
| `main` / 默认分支 | 永不作为清理候选 |
| 当前 worktree 正在检出或有未提交状态 | 保留，先处理所有权与备份 |
| 完整祖先、无开放 PR、无 worktree | 可用非强制本地删除，并精确删除远端 |
| PR 已 squash/重建合并 | 核对 PR 与树内容后，可记录 SHA 并删除 |
| 未合并但有明确替代 PR 和关闭说明 | 审查差异及架构边界后，可删除 |
| 未合并、有独有提交、无明确替代证据 | 保留并报告 |
| 系统或机器人生成分支 | 不能仅凭名称删除；核对对应平台和 PR |

删除远端分支后必须重新运行 `git ls-remote --heads origin`，不能只相信本地 remote-tracking ref。

### 5.7 清理 worktree

删除前逐个满足：

- 不是仍承载运行状态的主工作区；
- 没有未提交或未跟踪的独有工作；
- 分支内容已进入主线、私有历史或明确放弃；
- 没有进程打开其中的数据库、日志或服务文件；
- 没有开放 PR 或继续验收用途；
- 使用确切绝对路径执行 Git worktree 命令。

`git worktree prune --dry-run --verbose` 只用于发现失效注册，不是批量删除授权。

### 5.8 保护并恢复本地运行状态

如果必须原地切换主工作区：

1. 停止发布台与预览；
2. 对需保留的私有台账创建临时副本并比较哈希；
3. 确认私有 `history` 本地与远端同步；
4. 切换到目标主线；
5. 恢复私有台账；
6. 对 SQLite 执行 `PRAGMA quick_check`；
7. 重启服务并核对状态；
8. 临时副本移入可恢复位置，待人工决定何时清空。

### 5.9 最终复核

至少输出：

```text
公开 status
本地与远端 branches
worktree list
open PRs
HEAD 与 origin/main
远端 heads
私有 history 本地与远端 SHA
私有台账 blob 对比
SQLite quick_check
本地服务 status
```

如果公开 `git status` 仍显示私有台账，必须明确说明这是受保护运行数据，而不是“代码未提交”。不要用 `assume-unchanged` 或 `skip-worktree` 隐藏事实。

## 6. 常见错误与纠正

| 错误 | 风险 | 正确做法 |
| --- | --- | --- |
| 根据 `git status` 条数判断未完成工作 | 把已在主线的内容重复提交 | 对每个路径比较工作区与主线 blob |
| 只用 `git branch --merged` 删除 | 遗漏 squash/重建分支，或误判独有工作 | 联合 PR、树内容、worktree 和替代证据 |
| 为了清空状态提交所有差异 | 公开私有台账或引入旧实现 | 允许得出“无公开提交”的结论 |
| 批量更新视觉截图 | 用新基线掩盖数据或等待问题 | 先审查测试意图、遮罩和 CI 产物 |
| 直接删除主 worktree | 丢失 `.env`、SQLite、私有来源和备份 | 先盘点 ignored 数据，优先原地收口 |
| 服务运行时迁移 SQLite | WAL、路径和进程状态分裂 | 项目级 stop → 迁移 → quick_check → start |
| 把私有台账提交到公开 PR | 破坏公开/私有边界 | 同步私有 `history` 并保留公开工作区事实 |
| 因为机器人分支很旧就删除 | 丢失仍生效的平台配置 | 核对 PR 关闭原因和当前架构替代方案 |
| 删除后不复核远端 | 本地显示干净但远端 ref 仍存在 | fetch/prune 后使用 `ls-remote` 验证 |

## 7. 收尾报告模板

```text
基线：<origin/main sha>
主线结果：<PR + merge sha + checks>
真实差异：<总状态 / 与主线相同 / 真实差异>
公开提交：<文件与 commit，或明确 no-op>
私有状态：<history sha + blob verification>
分支：<删除 / 保留及原因>
worktree：<删除 / 保留及原因>
本地运行：<stop / sqlite check / restart status>
远端：<heads + open PRs>
未执行：<tests / production / human acceptance>
保留问题：<owner + next evidence>
```

## 8. 完成定义

仓库收尾只有同时满足以下条件才算完成：

- 公开代码和文档的有效改动已通过受保护主线流程，或明确审查为无需提交；
- 工作区状态已按内容哈希和所有权分类，不存在“未知来源”差异；
- 私有内容与台账已在本地和异机私有历史中得到一致验证；
- 不再有无用途的开放 PR、远端分支、工作分支或辅助 worktree；
- 保留对象都有明确原因，删除对象都有恢复证据；
- 主工作区仍可启动本地发布台，SQLite 检查正常；
- 最终报告区分公开代码、私有运行数据、主线、部署和人工验收；
- 没有通过隐藏状态、覆盖用户数据或制造空提交来获得表面整洁。

## 9. 后续执行思路

收尾完成后，默认停止继续整理历史。新的开发必须由真实自用过程中的重复摩擦、数据风险或发布阻断触发，并重新从最新 `origin/main` 建立小批次。历史分支和旧 worktree 不再作为需求来源，项目规范、当前主线和真实用户任务才是下一轮工作的起点。
