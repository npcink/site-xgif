# ADR-013：公开代码与私有内容使用独立 GitHub 仓库

## 状态

已接受

## 日期

2026-07-24

## 背景

XGIF 的公开站点、程序和已经发布的 Markdown 适合保存在公开仓库，并由受保护的 `main` 分支触发 Cloudflare Workers Builds。草稿、回收站、私有来源正文和恢复台账同样需要异机备份，但不能因为“都需要 GitHub”就进入公开仓库。

把整个 `site-xgif` 改为私有仓库看似可以统一处理内容，实际会把两类职责重新混在一起：

- 公开代码与生产部署需要可审查、可复现的 Git 历史；
- 私有内容需要更宽的恢复覆盖面，但不应参与公开 PR 和生产构建；
- SQLite、日志、密钥和模型向量仍不能因为仓库私有就失去最小化原则；
- 同一个工作区同时存在公开 Git 工作树与独立内容历史，管理端必须明确展示两者的真实状态。

## 决策

保留两个职责独立的 GitHub 仓库：

1. `npcink/site-xgif` 保持公开，只保存程序、文档、公开内容和部署配置；
2. `npcink/site-xgif-private-content` 保持私有，只接收 `workflow/backups/content-history.git` 的 `history` 分支。

私有内容历史使用固定白名单保存：

- `site/src/content/articles/`
- `site/src/content/images/`
- `site/public/images/memes/`
- `site/public/images/articles/`
- `workflow/records/`
- `workflow/private-sources/`
- `workflow/trash/`

`.env`、SQLite、日志、运行时缓存、模型和向量不进入任一仓库。

发布助手启动和内容写入后自动创建私有快照并尝试推送。远端失败不能阻断本地正文保存；管理端必须显示“待重试”及安全处理后的错误，并提供单独的“同步私有内容 GitHub”动作。该动作不能创建公开提交、PR 或部署。

公开 Git 状态只统计程序和可公开内容。草稿与 `public: false` 图片即使出现在主工作区，也不能计入公开仓库的待提交数量。

## 备选方案

### 把 `site-xgif` 整体改为私有仓库

仓库数量更少，但仍无法解决公开部署与私有恢复内容的权限、提交和审查边界。私有仓库也不能代替内容白名单和秘密排除，因此拒绝。

### 在同一仓库使用私有分支保存草稿

GitHub 仓库的可见性作用于整个仓库，不作用于单独分支；公开仓库中的“私有分支”不能作为保密边界，因此拒绝。

### 只保留本机备份

能防止误改，但不能覆盖整机损坏或丢失，恢复风险不可接受，因此拒绝。

### 使用在线数据库或对象存储保存草稿

会引入新的在线写入接口、认证、数据模型和恢复路径。当前单人本地工作流不需要这套复杂度，因此拒绝。

## 后果

- 公开 PR 不会因为本地草稿和回收站变化而长期显示待提交；
- 草稿、回收站和恢复副本具有独立的异机 Git 历史；
- 永久删除后，私有仓库最新快照不再包含该文件，但旧提交仍可用于误删恢复；
- 两个仓库必须分别核对：公开仓库看 PR、检查和部署，私有仓库看 `history` 提交是否与本机快照一致；
- 私有仓库并不降低来源、授权、最小数据和秘密管理要求；
- 若未来改变仓库可见性或备份介质，必须先写新的 ADR，说明迁移、权限和恢复验证方式。
