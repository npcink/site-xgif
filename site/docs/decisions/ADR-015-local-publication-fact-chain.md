# ADR-015：本地发布助手使用内容版本凭据与统一发布事实链

## 状态

已接受

## 日期

2026-07-29

## 背景

本地发布助手同时使用当前工作区 Git 状态、远程分支、GitHub PR、Cloudflare 检查和线上页面判断发布进度。此前这些事实由不同页面分别计算，造成三个问题：

- 隔离内容分支推送成功后，当前工作区文件仍然未提交，内容会再次显示为“待同步”；
- 内容库为避免线上探测，将所有远程内容显示为“待上线”，而系统状态会显示其中一部分已经上线；
- 推送失败虽然保留了隔离分支，但重试入口推送的是当前开发分支。

质量检查也曾使用“草稿”同时表示内容可见性和检查未通过，导致历史已上线内容被描述成草稿。

## 决策

1. Markdown 继续作为内容真相，SQLite 继续作为可重建索引。
2. 每次隔离同步按 `contentId + Markdown SHA-256` 写入追加式发布凭据，记录批次、分支、提交、阶段、推送结果和失败原因。
3. 同一内容版本已有成功凭据时不得重复创建同步分支；内容发生变化后自动形成新的版本。
4. 推送失败只重试凭据记录的 `content-sync/*` 分支，不能退化为推送当前工作分支。
5. 系统状态、内容库、详情与批量选择统一使用同一个发布状态查询；列表可以使用缓存，但不能使用另一套状态定义。
6. GitHub PR 和检查状态通过只读 `gh` 查询补充。无法查询时保持“已推送、远端待确认”，不猜测 PR、合并或部署成功。
7. 线上页面仍是最终内容核验依据。PR 合并或 Workers Builds 成功都不能单独成为“已上线”。
8. 质量状态使用“合格 / 需复核 / 阻断”，不再复用“草稿”。历史已发布但复核未完成的内容标记为复核债务，保持线上状态；下次编辑或同步前必须解决。
9. 内容写入使用原子替换，并携带编辑器打开时的内容 SHA-256。版本不一致时返回冲突，不覆盖较新 Markdown。
10. 本机写操作通过单进程串行队列执行；AI、质量检查和只读接口不进入该队列。
11. 隔离工作树复制完成后必须重新计算 Markdown SHA-256；与上线体检版本不一致时停止同步。
12. 远端推送采用 `prepared → push_succeeded/push_failed` 两阶段事件。终态事件落盘前保留本地 `content-sync/*` 分支。
13. 私有内容 Git 先完成本地快照；远端推送有界超时并在后台串行执行，不阻塞日常内容保存。
14. 外部命令错误在进入 API、操作历史或发布凭据前统一脱敏。
15. 编辑保存完成质量检查后、替换 Markdown 前，再次校验打开时的内容版本。
16. 发布凭据保持追加式事件语义，但底层使用临时文件与原子替换，避免非完整 JSON 行。
17. GitHub PR 查询按分支隔离错误，一个分支不可用不影响其他分支的事实。
18. 本地安全备份不等待私有远端；显式私有远端同步使用独立队列，不占用内容写队列。
19. 回收站恢复与永久删除只接受记录 ID，路径和内容类型以服务端索引为准。
20. AI 分段结果在批量发布边界重新做字符级验证，不能只信任上游状态标记。

## 替代方案

### 只检查当前工作区是否 dirty

被拒绝。隔离同步刻意不修改当前工作分支，因此工作区状态不能证明远程内容分支是否已经包含同一版本。

### 同步成功后自动提交当前开发分支

被拒绝。这样会破坏隔离边界，并可能夹带代码、草稿或其他未完成修改。

### 以 SQLite 作为发布主状态

被拒绝。SQLite 可损坏并可重建，不能独自保存不可重建的发布事实。追加式凭据与 GitHub/线上只读事实共同提供恢复来源。

### 引入消息队列或在线 CMS

被拒绝。该工具是单人、本机、桌面工作台；单进程串行队列已经满足并发边界，不增加长期运行服务。

## 后果

- 同一内容版本的同步具有幂等性，失败重试有准确目标；
- 状态展示以事实阶段为准，不再把“已推送”描述为“已上线”；
- 历史复核问题可以治理，但不会意外下线既有内容；
- 编辑冲突会显式返回，用户需要重新打开内容后再保存；
- 发布凭据不包含正文或密钥，只记录公开内容路径、哈希和远程事实。
- 推送成功但终态回执暂时失败时，本地分支仍是可恢复依据；
- 本地内容保存不再以私有 GitHub 可用为前提。
