# ADR-007：本地 SQLite 只作为可重建索引

## 状态

已接受

## 日期

2026-07-23

## 背景

本地发布台已经需要分页、批量发布、删除、回收站和操作恢复。仅靠每次扫描 Markdown 与浏览器 `localStorage`，无法可靠保存回收站索引和本机操作状态；但把文章正文迁入数据库，会破坏当前“静态站点、Git 可审计、没有线上后台”的边界。

关键约束：

- 文章正文和图片元数据必须继续由 `site/src/content/**/*.md` 承载并进入 Git；
- R2 只保存新图片字节，不保存发布状态；
- SQLite 丢失或损坏不能影响站点构建、线上文章或本地草稿文件；
- `workflow/` 仍然只监听 `127.0.0.1`，不新增 D1、线上 CMS 或远程数据库；
- 回收站不能只依赖 SQLite 或某一个浏览器的 `localStorage`。

## 决策

使用 Node.js 内置 SQLite，数据库固定保存在 `workflow/.runtime/xgif.sqlite3`，不提交 Git。它只保存以下可重建数据：

- Markdown 内容索引；
- 回收站索引；
- 本地操作历史；
- 数据库迁移版本。

数据库结构迁移保存在 `workflow/db/migrations/` 并提交 Git。启动发布台时执行 `PRAGMA quick_check`；如果数据库损坏，则先把数据库及 WAL/SHM 隔离为 `.corrupt-*` 文件，再从 Markdown 与回收站旁车元数据自动重建。

删除草稿时先把 Markdown 移入 `workflow/trash/content/`，再在文件旁写入 `.meta.json`，其中记录原路径、删除时间、内容哈希和恢复状态。SQLite 写入失败不能撤销已经安全完成的文件操作；下次启动可以从旁车重新建立回收站索引。

数据库在线备份必须使用 SQLite Backup API。备份保存在本机忽略目录 `workflow/backups/`，默认轮换保留 14 份；不直接复制工作中的 `.db` 文件。

由于公开仓库不适合作为未发布草稿备份，`workflow/backups/content-history.git` 维护一个独立的本机私有 Git 历史。它只允许 Markdown、内容台账、回收站和本地图片进入；密钥、SQLite、日志与程序文件不在路径白名单内。发布台启动和每次内容变更后自动提交快照。

## 权威数据顺序

1. `site/src/content/**/*.md`：文章和图片元数据权威源；
2. R2 或 `site/public/images/`：图片字节权威源；
3. 公开 Git：已发布并提交内容的版本历史与远程灾备；
4. 本机私有 Git：所有草稿和内容文件的本机误操作恢复历史；
5. `workflow/trash/**/*.md` 与旁车：本地删除恢复源；
6. SQLite：可删除、可重建的管理索引。

SQLite 永远不能成为文章正文、图片授权信息或 R2 对象位置的唯一保存位置。

## 备选方案

### 继续使用 JSONL 与浏览器状态

实现简单，但无法跨浏览器可靠恢复删除记录，查询和迁移也会逐渐复杂，因此不再作为管理索引。

### 把正文存进 SQLite

能简化传统 CMS 查询，但会形成 Markdown 与数据库双重权威源，增加同步失败和恢复难度，因此拒绝。

### 使用 Cloudflare D1 或线上后台

适合多用户远程管理，但当前只有一名本地维护者，且公开站点是纯静态产物。它会引入认证、线上写入和额外运维边界，因此暂不采用。

## 后果

- 删除或损坏 SQLite 后，重新启动发布台即可恢复内容和回收站索引；
- 数据库损坏可能丢失不重要的操作历史，但不会丢失文章；
- 未提交草稿会进入本机私有 Git，但仍不受异机灾备保护；如果需要抵御整台电脑或磁盘丢失，必须使用私有远程仓库或加密外部备份；
- `workflow/trash/` 与 `workflow/backups/` 是本机恢复资料，不进入公开仓库；
- 运行本地发布台需要 Node.js 22.5 或更高版本。
