# ADR-017：保留 Astro，不迁移到 Hexo 或 Ghost

## 状态

已接受

## 日期

2026-08-03

## 背景

XGIF 当前不是一个只负责渲染 Markdown 的普通博客，而是一套面向单人、本机和桌面浏览器的静态内容发布系统：

- `site/` 使用 Astro 7、Markdown Content Collections 和静态输出，部署到 Cloudflare Workers Static Assets；
- `workflow/` 是只在本机运行的发布台，负责导入、AI 辅助整理、内容体检、批量发布、隔离 Git 同步、删除恢复、R2 对账和离线推荐；
- 文章与图片使用两套经过校验的内容结构，并共享不可变 `contentId` 和根级详情 URL；
- 公开 Markdown、图片字节、本机 SQLite 派生索引、公开 Git、私有内容 Git 和生产部署证据各自承担不同职责；
- 在线站点保持纯静态，不部署本地发布台、私有正文、密钥、模型、向量或在线管理后台。

评估时，工作区包含 113 个文章 Markdown 和 11 个图片元数据 Markdown。数量只是 2026-08-03 的本地快照，不是长期架构常量；真正影响选型的是上述内容契约、发布边界和恢复链路。

本次评估要回答：改用 Hexo 或 Ghost，能否在保持现有内容、URL、发布安全和恢复能力的前提下，显著降低维护成本或改善真实发布体验。

## 决策

继续使用 Astro 作为公开站点框架，继续以 Markdown 和 Git 作为公开内容与发布历史的权威源，继续保留本机发布台。

当前不迁移到 Hexo，也不引入 Ghost 作为完整 CMS 或 Headless CMS。后续应优先围绕真实发布记录精简和修复现有工作流，而不是更换静态站点框架或新增在线内容运行时。

## 判断依据

### Astro 已经匹配当前边界

Astro 当前只承担构建公开静态页面的职责。内容校验、编辑管理、私有恢复、推荐生成和 Git 同步都在明确的本地边界内完成。现有实现已经具备：

- 严格的文章和图片 Schema；
- 稳定内容 ID、无尾斜杠 URL、静态详情页与详情弹窗；
- 搜索、标签、收藏、图片库、RSS、sitemap 和结构化数据；
- 静态推荐清单及模型不可用时的规则兜底；
- 构建、链接、浏览器视觉和生产巡检；
- 从内容分支、PR、Cloudflare 构建到线上核验的事实链。

更换框架不会自动减少这些产品要求，只会要求重新实现和重新验证。

### Hexo 是横向迁移，不是能力升级

Hexo 官方定位是基于 Markdown、front matter、主题和插件生成静态文件的博客框架：

- [Hexo 文档](https://hexo.io/docs/)
- [Hexo Front-matter](https://hexo.io/docs/front-matter)
- [Hexo 主题](https://hexo.io/docs/themes)
- [Hexo 插件](https://hexo.io/docs/plugins)

它可以满足传统博客的文章、标签、分类、主题和静态部署需求，但这些基础能力 Astro 已经具备。迁移后仍需重写或适配：

- 两套内容集合和现有字段校验；
- 文章与图片共用的稳定详情路径；
- 详情弹窗、收藏、搜索和图片库；
- 推荐清单、来源与授权规则；
- Cloudflare 部署配置和现有测试体系；
- 本地发布台写入路径、同步白名单与恢复逻辑。

如果通过 Hexo 主题、脚本和插件补齐这些能力，最终只是把现有 Astro 实现改写为另一套框架代码，迁移成本高，日常维护成本没有可证明的下降。

因此，Hexo 只适合“从零开始建设一个更传统、更简单的博客”这一不同目标，不适合替换当前 XGIF。

### Ghost 的优势与当前需求不匹配

Ghost 的主要价值是在线编辑、预览与定时发布、多人角色、Newsletter、会员和订阅：

- [Ghost 发布与定时](https://ghost.org/help/publishing-content/)
- [Ghost 团队角色](https://ghost.org/help/managing-your-team/)
- [Ghost Content API](https://ghost.org/docs/content-api/)

当前 XGIF 已明确选择单人、本机、桌面工作台，不需要多人权限、在线后台、Newsletter 或会员系统。完整迁移到 Ghost 会把内容权威源从 Markdown/Git 改为在线数据库和管理后台，并引入新的运行时、认证、升级、备份与生产故障面。

Ghost 官方推荐的自托管生产环境包括 Ubuntu、Node.js、MySQL、NGINX、Systemd 和至少 1 GB 内存，明显重于当前纯静态部署：[Ghost 自托管要求](https://docs.ghost.org/hosting/)。使用 Ghost(Pro) 可以减少运维，但会引入持续费用；价格和套餐能力应在真正准备采用时重新核对：[Ghost(Pro) 价格](https://ghost.org/pricing)。

把 Ghost 作为 Headless CMS、继续用 Astro 渲染，也不能消除上述问题。它会形成 Ghost 数据库与现有本地发布台并存的两套内容入口，还需要处理 API 拉取、构建触发、字段映射、图片迁移和故障降级。除非 Ghost Admin 将明确替代本地发布台，否则不应增加这一层。

Ghost 支持 JSON 导入和导出，但自定义迁移格式贴近其数据库结构，不等于可以无损保留 XGIF 的现有字段和恢复契约：

- [Ghost 自定义迁移格式](https://ghost.org/docs/migration/custom/)
- [Ghost 数据导出](https://ghost.org/help/exports/)

## 备选方案

### 迁移到 Hexo

优点：

- Markdown 和静态部署心智简单；
- 博客主题与插件生态成熟；
- 对传统文章、标签和归档站点足够直接。

拒绝原因：

- 与 Astro 能力高度重叠；
- 现有自定义页面、内容 Schema、发布台和测试必须重写；
- 没有证据表明迁移后发布更快、故障更少或维护更省。

### 用 Ghost 替换站点和发布台

优点：

- 提供成熟的在线编辑、预览、定时发布和团队权限；
- 可以进一步使用 Newsletter、会员和订阅能力。

拒绝原因：

- 当前没有对应的真实需求；
- 破坏纯静态、本地优先和 Markdown/Git 权威边界；
- 增加数据库、在线后台、安全、升级和恢复成本；
- 现有图片、来源、推荐、发布证据和私有恢复契约不能直接替代。

### Ghost Headless CMS + Astro

优点：

- 可以保留当前 Astro 前端；
- 可以使用 Ghost Admin 作为远程内容编辑器。

拒绝原因：

- 同时维护 Ghost 和本地发布台会形成双重内容真相；
- 增加 API、构建触发、内容同步和故障处理；
- 当前单人本地工作流不能证明这份复杂度有收益。

## 后果

- 不发生框架迁移，不需要转换现有内容、URL 或 Cloudflare 部署配置；
- 现有未提交内容和开发改动不会因为选型评估被触碰；
- 后续工程工作继续以真实发布痛点为依据，优先删除重复入口、修正状态和提高恢复可靠性；
- 不以“CMS 功能更多”作为引入在线运行时的充分理由；
- 如果未来需求变化，应新写 ADR，并说明如何迁移内容权威源、URL、图片、私有数据、恢复与生产证据。

## 重新评估条件

只有以下情况之一反复出现并成为真实瓶颈时，才重新评估 Ghost 或其他在线 CMS：

1. 两名或更多编辑需要在不同设备远程协作；
2. 本机发布台成为持续可用性瓶颈，而不是偶发操作不便；
3. Newsletter、会员或付费订阅成为明确产品目标；
4. 需要定时发布、角色权限和审核流，并且无法在当前边界内简单实现；
5. 非技术编辑必须独立完成编辑与发布；
6. 真实数据证明当前 Git/PR 发布链路长期阻碍内容产出。

仅因为想更换主题、追求流行工具或希望减少少量前端代码，不足以触发迁移。

## 低风险验证方式

如果未来满足重新评估条件，先做隔离 PoC，不直接迁移生产：

1. 选取 5 篇覆盖原创、外部来源、图片引用和特殊标签的文章；
2. 映射 `contentId`、来源、授权、公开状态和推荐分组；
3. 验证现有 URL 能否保持，或能否提供完整重定向；
4. 验证图片、导出、恢复和删除后的可追溯性；
5. 比较一次真实发布从编辑到线上核验所需时间；
6. 只有 PoC 证明维护成本和发布体验显著改善，才提出新的迁移 ADR。

PoC 不得接管正式域名、覆盖现有内容权威源，或绕过当前生产发布链路。
