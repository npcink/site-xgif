## 背景

XGIF 已经形成两套职责不同的运行面：

- `site/` 是 Astro 纯静态公开站点，读取公开 Markdown 和静态推荐清单；
- `workflow/` 是只监听本机回环地址的单人发布台，负责导入、新建、AI 辅助、内容体检、批量发布、删除恢复、推荐生成、R2 对账和 Git 同步；
- 公开内容、私有内容、图片字节、SQLite 派生索引、公开 Git、私有 Git 和线上部署证据各自有明确权威边界；
- 本地发布、分支推送、PR、合并、Cloudflare 部署和线上核验是不同事实，不能合并成一个模糊的“发布成功”；
- 当前工作模式是单人、本机、PC 优先，不需要在线管理后台、多用户权限或移动端编辑。

在确认不迁移 Hexo 或 Ghost 后，需要进一步判断：是否应该改用 Publii、Front Matter CMS、Keystatic、Decap CMS、Sveltia CMS、Pages CMS 或 Memos，还是继续开发现有发布台。

本次选择比较的是未来维护成本和边界匹配度，而不是已经投入多少代码。即使现有系统已经开发完成，如果第三方方案能以更低的未来成本完整承担关键职责，也应允许替换；反之，不能因为第三方项目功能更多就引入不需要的运行时和双重内容真相。

## 候选项目

### Publii

- 项目：[GetPublii/Publii](https://github.com/GetPublii/Publii)
- 许可证：GPL-3.0
- 形态：Windows、macOS 和 Linux 桌面静态 CMS，支持离线编辑和多种发布目标。

与 XGIF 最相似的是“本地管理、离线编辑、生成静态站点、明确执行发布”的整体产品心智。

值得学习：

- 本地站点、内容、设置和发布目标的分层；
- 非技术用户理解得了的预览、备份和发布体验；
- 发布失败后的状态说明和恢复入口；
- 桌面应用如何管理站点数据与迁移。

不适合直接采用：

- Publii 同时拥有内容管理和站点生成，会替换现有 Astro 站点而不是只补充编辑层；
- 它的直接上传模式不能自然表达 XGIF 的受保护分支、PR、CI、Cloudflare 构建和线上核验；
- 现有文章/图片双内容模型、稳定 `contentId`、R2、推荐和来源治理需要重新实现；
- GPL-3.0 代码不能在未完成许可证评估时直接复制到当前项目。

### Front Matter CMS

- 项目：[estruyf/vscode-front-matter](https://github.com/estruyf/vscode-front-matter)
- 许可证：MIT
- 形态：运行在 Visual Studio Code 内的本地文件 CMS。

它的内容、数据、媒体和 taxonomy 工作台与 XGIF 本地发布台最接近。

值得学习：

- 内容列表的搜索、筛选、排序、分组和分页；
- 内容、媒体、数据和标签各自拥有专门工作区；
- 正文编辑、元数据侧栏、媒体插入和站点预览之间的短路径；
- 通过配置支持不同内容类型和静态站框架。

不适合直接采用：

- 它依赖 VS Code，目标用户与 XGIF 独立本地工作台不同；
- 通用 Markdown 编辑能力不能替代 XGIF 的发布事务、内容哈希、隔离同步、删除墓碑和线上验证；
- 维护者已说明项目会继续维护，但重大功能开发取决于个人需求、公司投入或社区支持，不宜成为核心发布链硬依赖。

### Keystatic

- 项目：[Thinkmill/keystatic](https://github.com/Thinkmill/keystatic)
- 许可证：MIT
- 形态：用 TypeScript Schema 管理 Markdown、YAML 和 JSON，支持本地文件与 GitHub 模式，并支持 Astro。

它是技术上最接近 XGIF 现有 Astro 和文件内容模型的候选。

值得学习：

- 从 Schema 自动生成字段表单；
- collection、singleton、字段和编辑布局的抽象；
- monorepo 路径前缀、本地存储和 GitHub 存储的切换；
- 列表列、预览 URL、图片字段和正文文件的配置方式。

不适合现在直接采用：

- 官方仍将项目标记为实验性；
- 它主要解决结构化内容 CRUD，不提供 XGIF 已有的体检、批量安全事务、私有恢复、R2 对账和生产证据链；
- 默认 slug 心智与不可变 `contentId` 不完全一致；
- 接入后仍需维护大量自定义服务，不能证明比当前实现更简单。

### Decap CMS 与 Sveltia CMS

- 项目：[decaporg/decap-cms](https://github.com/decaporg/decap-cms)、[sveltia/sveltia-cms](https://github.com/sveltia/sveltia-cms)
- 许可证：MIT
- 形态：面向静态站的 Git-based CMS；Sveltia CMS 是兼容这一配置模型的现代实现。

值得学习：

- 将保存草稿、继续编辑、提交审核和批准发布映射到分支、提交和 PR；
- 同一内容持续更新时复用远端工作分支；
- 内容库的列表/网格、排序、筛选、分组、全文搜索和批量操作；
- Sveltia 的 Git、S3 兼容存储、Cloudflare R2 和媒体资产库设计；
- 远端冲突、认证失败和发布失败的显式反馈。

不适合现在直接采用：

- 它们主要面向在线 CMS，而 XGIF 明确保持本机发布台；
- 其草稿通常已经写入远端分支，XGIF 草稿和私有正文不能进入公开仓库；
- 通用 Editorial Workflow 不能替代来源、授权、AI 原文完整性和内容哈希检查；
- CMS 的 Publish 不能代表 Cloudflare 已部署或线上内容已经核验。

### Pages CMS

- 项目：[pagescms/pagescms](https://github.com/pages-cms/pagescms)
- 许可证：MIT
- 形态：直接编辑 GitHub 仓库文件的静态站 CMS，使用 `.pages.yml` 描述内容和媒体。

值得学习：

- 明确把 CMS 定义为编辑层，不替代站点生成器和部署平台；
- 用一个配置文件描述集合、字段、媒体、列表、提交模板和操作；
- 保存结构化文件时保留 Schema 外未知字段；
- 将 GitHub Actions 暴露为有上下文的明确操作；
- 区分媒体输入路径、公开 URL、扩展名、重命名和提交策略。

不适合现在直接采用：

- 它直接写 GitHub，与 XGIF 本地内容和私有恢复边界不一致；
- 自托管需要 PostgreSQL、GitHub App 和在线认证，增加当前不需要的运行时；
- 不能直接承担本地 AI、内容体检、隔离 worktree、R2 内容寻址和线上核验。

### Memos

- 项目：[usememos/memos](https://github.com/usememos/memos)
- 许可证：MIT
- 形态：Markdown 原生的快速采集和时间线笔记系统。

值得学习：

- 打开即写、先采集后整理；
- 时间线、标签、附件、归档和轻量搜索；
- 通过 API 或消息入口接收外部内容。

不适合直接采用：

- 它是在线服务和数据库应用，不是静态发布系统；
- 如果与 Flomo、本地 Markdown 同时保存正文，会增加第三份内容真相；
- 它不处理来源治理、公开同步和生产证据。

## 方案比较

| 方案 | 与当前边界匹配 | 能否替代现有发布台 | 新增复杂度 | 结论 |
| --- | --- | --- | --- | --- |
| Publii 整体替换 | 低 | 只能替代基础编辑与静态生成 | 高，需要重做站点和发布链 | 不采用 |
| Front Matter CMS | 中 | 不能替代安全发布事务 | 中，且依赖 VS Code | 只学习交互 |
| Keystatic | 中高 | 只能替代部分 Schema 表单与文件写入 | 中，仍需大量自定义 | 保留为本地编辑层备选 |
| Decap CMS | 中 | 不能替代私有草稿和上线核验 | 中高，引入在线认证和远端草稿 | 只学习 Git 状态机 |
| Sveltia CMS | 中 | 不能替代专用发布和恢复边界 | 中高，引入在线 CMS | 保留为未来远程协作备选 |
| Pages CMS | 中 | 不能替代本地工作流 | 高，自托管还需要数据库和 GitHub App | 只学习配置模型 |
| Memos | 低 | 只能承担上游采集 | 高，会形成额外内容源 | 只学习采集体验 |
| 继续 Astro + 本地发布台 | 高 | 已覆盖全部关键职责 | 可控，但必须限制功能扩张 | 采用 |

## 决策

继续使用 Astro 公开站点和现有本地发布台，不切换到上述任何一个完整技术方案，也不把它们接入当前生产发布链。

后续采取“吸收经验、保持边界、按真实痛点演进”的方式：

1. 保留 Markdown/Git、R2、本机 SQLite 派生索引和静态 Cloudflare 部署；
2. 保留本地发布、远端同步、部署和线上核验的事实分离；
3. 不新增在线 CMS、在线内容数据库或另一份正文权威源；
4. 不因为第三方项目有更多功能就复制其全部信息架构；
5. 只有真实使用中反复出现的问题，才从候选项目选择一个成熟模式进行窄幅实现；
6. 引用或复制开源代码前单独核对许可证、依赖和安全边界；Publii 的 GPL-3.0 与其他候选的 MIT 不能等同处理。

继续开发不等于继续扩张功能。当前阶段的主线仍是复核和发布真实内容、观察失败原因、修正错误状态并删去重复入口。

## 单人使用与 AI 开发的复杂度约束

XGIF 当前主要由一名使用者借助 AI 开发和维护。AI 可以降低生成代码、补测试和阅读局部实现的成本，但不会自动承担以下长期责任：

- 判断多个内容和发布状态是否一致；
- 证明 Git、Cloudflare 和线上页面对应同一版本；
- 在恢复、删除、来源或授权出现问题时做最终决策；
- 识别跨批次、跨会话和跨工作区的变更所有权；
- 在未来重新理解由多个 AI 会话生成的抽象和兼容层。

因此，第三方项目的“可吸收经验”是遇到具体问题时的参考索引，不是开发待办清单。不得为了完整吸收 Publii、Front Matter CMS、Keystatic、Decap、Sveltia、Pages CMS 或 Memos 的能力而逐项实现对应功能。

当前发布台已经是一套专用应用。2026-08-03 的粗略本地统计为：

- `workflow/` 中 JS、MJS、HTML 和 CSS 合计约 29,598 行；
- 上述类型合计 115 个文件；
- `workflow/tests/` 有 46 个测试文件。

这些数字不是质量指标，也不要求为了减少行数而重写；它们只说明任何新抽象、入口、状态和运行时都会产生真实维护成本。

以后新增或扩展能力必须先通过以下门槛：

1. 问题在真实使用中反复出现；建议至少记录 3 次，安全或数据风险除外；
2. 不处理会阻塞内容任务、造成错误事实或增加数据风险；
3. 已经确认不能通过删除、合并或调整现有流程解决；
4. 实施后能减少操作步骤、重复规则、失败恢复成本或维护面；
5. 不增加新的正文权威源、在线数据库、常驻服务或日常主入口；
6. 有确定性测试、失败恢复点和清晰回滚方式。

不满足前两项时不开发；不满足第五项时必须另写 ADR。普通功能改进应优先替换旧复杂度，而不是与旧入口并存。

在没有外部用户的开发阶段，不能把“等待真实使用”作为停止验证的理由。AI 需要主动执行可重复的开发验收任务：读取类任务可以使用当前本地环境，写入、导入、删除、恢复和同步事务使用隔离环境或测试数据。开发验收发现的事实错误、安全风险和不可恢复问题可以直接驱动修复；它不能证明市场需求，也不能用来为新增功能制造依据。项目进入真实使用后，再用真实任务记录替代开发场景记录。

## 可吸收的设计原则

### 从 Publii 吸收本地发布心智

- 首页只说明当前站点、未同步变化和一个主要下一步；
- 发布失败保留恢复点，明确显示本地内容仍然安全；
- 备份、恢复和迁移使用普通用户能理解的语言；
- 不把底层 Git、构建和托管细节全部暴露为日常主操作。

### 从 Front Matter CMS 与 Sveltia 吸收内容库设计

- 列表字段、搜索、排序和默认筛选可以配置；
- 内容、媒体、体检和标签治理保持清晰边界；
- 图片密集内容提供网格，文章和任务队列默认使用高密度列表；
- 批量操作只显示当前选择和状态真正可用的动作；
- 素材库显示引用关系、来源、授权、缺失字段和存储状态。

### 从 Keystatic 吸收 Schema 驱动思想

- 逐步减少浏览器表单、服务端校验和 Astro Schema 之间的字段重复；
- 优先共享枚举、默认值、字段说明和只读/可编辑规则；
- 不急于引入 Keystatic 依赖，先在现有代码中建立最小、可测试的字段契约；
- Schema 抽象不得弱化服务端发布校验，也不得让通用 CRUD 绕过专用事务。

### 从 Decap 吸收 Git 事实状态机

- UI 状态必须能映射到具体分支、提交、PR、检查、合并和部署事实；
- 同一内容哈希复用已有同步凭据，不重复创建分支；
- 失败状态保留原分支和明确的下一步，不用模糊的“重试同步”；
- PR 合并、Cloudflare 构建成功和线上核验继续是三个独立事实。

### 从 Pages CMS 吸收配置与写入安全

- 列表视图、媒体路径、提交信息和低风险动作可以声明式配置；
- 写回结构化内容时保留不归当前编辑器所有的字段；
- 每个动作必须明确其输入路径、输出路径、允许的文件类型和 Git 影响；
- 通用配置不能覆盖 XGIF 的来源、授权、内容哈希和私有数据规则。

### 从 Memos 吸收采集体验

- 导入入口允许先收集，再进入正式内容工作台整理；
- 快速采集不要求用户先完成全部来源、标签和发布字段；
- 导入后的草稿必须进入现有 Markdown、私有快照和体检流程；
- 不增加一个长期保存正文的 Memos 数据库。

## 实施边界与优先顺序

### 当前主线

1. 复核和发布现有真实内容；
2. 记录内容导入、体检、批量发布、同步和下架的真实失败原因；
3. 修正错误状态和重复入口；
4. 保持备份、恢复演练、R2 对账和生产证据可靠；
5. 只有同类问题反复发生，才实施下面的参考能力。

### 第一优先级：低风险吸收

- 内容库列表、筛选、排序和字段显示的轻量配置；
- 更清楚的发布事实时间线与失败恢复入口；
- 素材引用、来源、授权和存储状态的统一展示；
- 让主要动作保持唯一，低频设置进入上下文。

这些改进不得改变内容权威源和部署架构。

### 第二优先级：经过证据支持后再做

- 把文章和图片的重复字段定义收敛为内部 Schema 契约；
- 把媒体路径、R2 状态和图片规则收敛为明确的适配层；
- 改善快速采集到正式草稿的 Inbox 流程。

只有重复维护错误已经出现，且抽象能减少而不是增加代码时才实施。

### 暂不实施

- 安装 Keystatic、Decap、Sveltia、Pages CMS 或 Memos 到生产仓库；
- 引入在线 CMS 认证、PostgreSQL 或另一套内容数据库；
- 允许第三方 CMS 直接提交到 `main`；
- 将公开和私有内容放入同一远端工作流；
- 为可能出现的多人、移动端或 Newsletter 需求预建功能。

## 候选方案的未来定位

如果需求变化，不需要重新从全部项目开始比较：

- 仍是单人本地，但现有表单维护成本成为主要瓶颈：优先隔离评估 Keystatic；
- 出现两名或更多远程编辑，需要 Git 审核：优先比较 Sveltia CMS 与 Decap CMS；
- 只需要最简单的 GitHub 在线编辑层：优先评估 Pages CMS；
- 决定放弃现有自定义站点和发布治理，退回通用静态博客：才评估 Publii；
- 需要独立快速采集服务：评估 Memos，但必须保持单向导入和唯一正文权威源。

## 重新评估条件

满足以下任一条件，并有一段真实使用记录支持时，才重新评估切换或接入：

1. 两名或更多编辑必须在不同设备远程协作；
2. 现有发布台的维护时间持续高于内容生产和复核时间；
3. 同类表单或字段同步错误反复发生，内部 Schema 收敛仍不能解决；
4. Git/PR 操作成为内容发布的主要瓶颈，而不是偶发失败；
5. 必须由非技术编辑独立发布内容；
6. 产品明确需要 Newsletter、会员、付费订阅或多级审核；
7. 某个候选方案通过隔离 PoC 证明能完整保留内容、URL、私有数据、恢复和生产证据，同时显著减少未来维护成本。

## 隔离 PoC 规则

重新评估时先做可删除的隔离实验：

1. 使用临时目录或独立仓库，不修改当前工作区；
2. 只复制 5 篇脱敏示例内容和少量测试图片；
3. 不提供 `workflow/.env`、私有仓库凭据、真实 R2 写权限或正式域名；
4. 验证不可变 `contentId`、文章/图片 Schema、未知字段保留和 URL；
5. 验证草稿、同步、PR、部署和线上核验能否保持事实分离；
6. 演练导出、恢复、删除和回滚；
7. 比较完成一次真实任务所需时间、人工步骤、失败恢复能力和新增运行时；
8. PoC 通过后另写 ADR，不能直接把实验接入生产。

## 后果

- 当前不发生框架、CMS、内容数据库或部署迁移；
- 已有内容和未提交工作不会因技术调研被转换或重写；
- 第三方项目成为设计和源码参考，不成为默认依赖；
- 后续开发需要证明它解决的是反复出现的真实问题；
- 继续开发的评价标准从“功能数量”改为发布效率、状态真实性、数据安全和恢复能力；
- 如果未来需求变为远程多人协作，Sveltia/Decap/Pages CMS 可以重新进入候选；如果仍是本地单人模式，Keystatic 只作为编辑层 PoC 候选。
