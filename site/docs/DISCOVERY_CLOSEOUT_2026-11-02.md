## 原定目标

让图片与文本分享形成可继续浏览的真实推荐链，使用 M4 Ollama 离线推荐，
统计仅用于当前浏览器验证；后续上传图片能识别完全重复，并提示需要人工对照的相似图。
交付后继续使用 Astro、Markdown、本机发布助手与可重建索引。

## 做得好的地方

- 先修复弹窗丢推荐、图片只能跳文章和已看循环，扩大候选后仍诚实显示耗尽状态。
- 沿用既有本机和静态边界，M4 只做离线计算；图片指纹使用确定性算法，适合当前规模。
- 保存服务端重新校验，人工确认与文件 SHA 关联，缓存损坏或缺失不被误报为没有重复。
- 真实图片、HTTP、浏览器、Linux 视觉、CI、生产和恢复各有对应证据。

## 长期经验与规范落点

1. 从真实浏览链修问题。弹窗、曝光计数、推荐补位和图片动作必须在实际节点上验收，不能只看模板。
2. 区分字节相同、感知相似、主题相关与人工满意。四者不能互相代替，也不应共用“去重”结论。
3. 发布限制覆盖完整生命周期，包括复制、恢复、批量操作、构建和模型语料入口。
4. 把异步请求与当前对象关联；操作版本、人工确认、文件 hash 各自绑定实际写入对象。
5. 公开 URL 是长期接口；旧迁移建议必须连同当时前提复核，不能当作永久授权。
6. 合并、部署、恢复与仓库清理是四份证据，任何一项都不能从相邻状态推断。

以上要求已写入 [开发与交付规范 §14](DEVELOPMENT_AND_DELIVERY_STANDARD.md#14-连续浏览与本机查重的经验补充)
及 [仓库收尾规范 §10](REPOSITORY_CLOSEOUT_AND_GIT_HYGIENE_STANDARD.md#10-托管-worktree-与会话结束验收)。

## 清理依据与执行验收

盘点时只有一个主工作区和一个托管 worktree，无开放 PR。
`codex/image-similarity` 的树与 `origin/main` 完全相同；#51/#52 的较旧树需结合已合并 PR 和后续修改判断，
不能用祖先检测或“整个旧分支与当前 main 相同”作为唯一清理条件。

最后文档 PR 合并并完成生产核验后，依次执行：

1. 主工作区只快进更新，保留 `.env`、SQLite、私有来源和台账；核对私有 history 和本机服务。
2. 停止 worktree 的旧预览，确认没有进程使用其中 SQLite。
3. 将被忽略的离线缓存、私有字节和嵌套备份仓库保全到主工作区
   `workflow/backups/worktree-closeout-2026-11-02/`，校验文件 hash、SQLite 与私有 Git 对象。
4. 使用 Codex 托管 worktree 归档工具保留可恢复代码快照；主工作区继续提供日常服务。
5. 以预期 SHA 保护，删除 #51/#52/#53 的远端开发分支和本次收尾分支；
   本地相关分支在确认等价吸收或已有归档后删除，包含本地 URL 文档分支。
6. 再次核对：本地 / 远端仅 main、一个主 worktree、零开放 PR、干净状态、
   当前生产 build 与 main 一致、8787 / 4321 可用。

实际执行回执保存在主工作区 `workflow/.runtime/discovery-closeout-2026-11-02.json`；
本节是清理顺序和验收门槛，未执行动作不得提前登记为已完成。
公开源 Markdown 为 124 条，其中两条 hold；当前公开推荐语料为 122 条。
URL 讨论纪要中的 124 个公开条目是先前核查时点事实，不能覆盖本轮下架后的数量。

## 下次重点关注

- 新任务先读本纪要、Handoff 和开发规范，重新核对 main 与生产事实；不从已归档聊天恢复旧待办。
- 优先增加真实图片与内容，观察本机曝光 / 点击 / 重复访问；不把单标签页统计泛化为全站效果。
- 感知查重允许裁剪、加字、GIF 后续帧漏检；先人工对照，只有重复真实摩擦再扩展能力。
- 结束会话前再次核对最后一份文档是否已合并，以及忽略数据是否确有恢复位置。
