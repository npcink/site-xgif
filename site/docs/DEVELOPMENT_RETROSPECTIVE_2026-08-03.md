5. 清理本轮临时资源和废弃远端分支；

## 关键过程与判断

### 1. 先把“共享现场”与“发布候选”分开

共享工作区同时存在程序修改、内容文件、推荐清单和视觉截图。直接在该目录收尾，会让“用户正在做的工作”和“本轮允许进入主线的内容”失去边界。

本轮从最新主线建立隔离工作树，只吸收已经确认的内容提交和两项待发布内容。这个选择牺牲了表面上的一步完成，但换来了明确基线、精确暂存、独立测试和可撤销候选。共享目录最后仍保持原状。

### 2. 质量门禁不应迫使内容造假

一篇完整内容短于原有 80 字阈值。简单扩写可以让测试通过，却会损害内容真实性；直接降低全站阈值又会放宽其他内容的质量门禁。

最终采用双层契约：正文仍需满足最低有效长度；低于常规阈值时，只有显式 `shortFormReviewed: true` 才能通过。发布器展示该选择，服务端和站点测试共同校验，正文一旦变化就重新要求人工确认。

### 3. 视觉失败先判断属于哪一类事实

PR #35 首轮 Linux CI 出现 5 个视觉失败。其中既有图片弹层只等待“容器可见”造成的异步竞态，也有新增图片后筛选结果从 1 项变为 3 项的断言过时，还有内容增长引起的真实基线变化。

处理顺序是先修等待语义和数据断言，再下载 CI 实际截图，多次重跑比较 SHA-256，并人工查看稳定差异，最后只更新确认需要变化的 Linux 基线。这比在 macOS 上批量刷新截图更能保护长期视觉契约。

### 4. 推荐生成必须区分“可构建”和“完整健康”

严格推荐生成首次因向量端点不可达而失败。规则模式可以继续生成，但发布它会把降级状态误写成完整健康。

本轮保留最后一次成功的混合推荐，确认 SSH 连通性后建立临时、仅回环监听的端口映射，核对模型，再用 `--require-embeddings` 重建。完成后关闭通道。推荐发布从干净主线环境执行，只提交一个 JSON 文件，避免共享旧索引误报的 10 项“待同步内容”污染发布判断。

### 5. 生产测试也会陈旧

代码、内容、CI 和 Cloudflare 构建全部正常后，真实生产巡检仍失败，原因不是站点缺文章，而是脚本只认可已经废弃的 `/articles/<id>` sitemap 路径。

修复没有降低断言，而是从文章索引发现真实文章链接，再核对当前根级详情路由是否进入 sitemap，并增加静态契约测试。这个问题说明：自动化测试本身也是需要与产品契约同步维护的代码。

## 做得好的地方

1. **保护了真实现场。** 所有合并、修复和生成物发布都在隔离工作树完成，没有以“清理”为名改写共享脏工作区。
2. **没有为了绿灯牺牲事实。** 短内容没有被填水，向量失败没有伪装为健康，生产 200 没有被误报为版本正确。
3. **失败被转化为契约。** 异步弹层增加语义等待，短内容增加显式确认，生产路由增加巡检回归。
4. **恢复证据与最终内容对应。** 内容变化后重新演练和备份，私有快照、SQLite 备份与最终内容指纹一致。
5. **发布证据层次清楚。** PR、CI、主线、Cloudflare 构建、生产 URL 和人工视觉核验分别记录，没有互相替代。
6. **清理发生在验证之后。** 只有生产闭环完成后才删除远端分支、临时工作树和端口映射。

## 下次重点关注

1. 发布开始前先形成一张“候选资产表”：内容分支、PR、工作树、主线 SHA、内容指纹、恢复证据和运行中后台版本。
2. 把公开内容、推荐清单、程序修复拆成独立候选；每个候选只承担一种主要风险。
3. 让内容批次保持小而频繁。远端分支 push 后尽快创建 PR，合并或明确废弃，不长期悬空。
4. 视觉测试固定执行“语义就绪 → Linux 产物 → 稳定性复跑 → 人工查看”的顺序。
5. 在内容冻结后立即执行恢复演练、最终备份和 R2 对账；其后任何内容变化都触发整组证据重做。
6. 推荐发布默认从干净主线运行严格向量模式；共享后台只用于日常编辑，不作为收尾候选的事实源。
7. 合并后首先核对 `/build.json`，随后运行严格生产巡检和代表 URL；不要等到所有清理完成才发现生产契约过时。
8. 当前共享本地后台仍可能运行旧脏分支。未来若要收敛到主线，应作为单独任务盘点和迁移，不在发布收尾中强行覆盖。

## 提炼出的开发思路

### 1. 先分清事实所有者，再写自动化

Markdown、SQLite、GitHub、Cloudflare、R2 和生产 URL 各自回答不同问题。系统越自动化，越不能用一个“成功”状态吞掉这些边界。

### 2. 先冻结候选，再收集证据

测试、恢复演练和备份只对特定代码版本与内容指纹有效。候选尚在变化时不断积累绿灯，最终只会得到一组彼此不对应的历史结果。

### 3. 门禁应阻止风险，不应诱导伪造

好的门禁能指出事实缺口并允许显式人工判断；坏的门禁会迫使用户填假来源、灌水正文或隐藏降级状态。例外需要被建模、记录并在事实变化后失效。

### 4. 故障恢复是主流程的一部分

恢复演练、最终备份、私有异机快照和 R2 对账不是发布后的附加项。它们决定这次发布是否真正可逆，应在阶段完成定义中占有同等位置。

### 5. 自动化结果也必须接受现实校验

视觉测试可能有竞态，生产巡检可能固化旧路由，状态页可能运行旧分支。对高价值结论，应回到实际产物、目标 SHA 和真实 URL 验证。
