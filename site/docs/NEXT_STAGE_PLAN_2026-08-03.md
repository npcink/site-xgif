## 1. 阶段判断

XGIF 当前不缺新的 CMS、框架或功能方向。当前主要问题是：工作区中已经积累了较大的内容、代码、记录和视觉变更，需要先确认所有权、拆分批次、补齐恢复证据，并用真实内容完成一次可核验发布。

下一阶段不以增加功能数量为目标，而以以下结果为目标：

> 将当前大批量未提交工作收敛成边界清楚、可恢复、可独立审查的批次，并完成一次内容从本地事实到线上核验的真实闭环。

## 4. 当前主攻目标

🎯 当前主攻目标：收口当前工作区，并完成一个真实内容发布闭环。

原因：当前 144 个工作区变更横跨内容、代码、记录、文档和视觉基线。没有先收口这些事实时，任何新功能都会继续扩大所有权、测试和发布风险。

完成信号：

1. 每个现有变更都归属到明确批次，未知或无主变更为零；
2. 内容、代码、记录、文档和视觉基线不被混进同一目的不明的提交；
3. 新鲜恢复演练、最终私有备份和内容体检都有可检查结果；
4. 至少一个真实内容批次完成隔离同步、PR、检查、合并、Cloudflare 部署和线上核验；
5. 整个过程没有新增产品功能或新的内容权威源。

暂缓任务：

- Schema 驱动表单：尚未证明字段重复是当前主要瓶颈；
- 媒体存储抽象：当前 R2 和本地图片已有明确边界，没有第二个真实存储需求；
- 快速采集 Inbox：先观察现有 Flomo 导入的真实成本；
- Keystatic、Sveltia、Decap、Pages CMS、Memos：只作为条件触发的参考或隔离 PoC；
- 多用户、移动端、Newsletter、会员和在线 CMS：当前单人本机模式不需要。

## 5. 分阶段执行

### 阶段 A：收口工作区

目标：先知道当前每一类变更是什么，再决定如何验证和发布。

行动：

1. 按内容、站点代码、视觉基线、工作流记录和文档列出变更清单；
2. 标记每个变更的来源、目的、是否完成和是否应公开；
3. 内容同步继续从 `origin/main` 创建隔离 worktree，只复制白名单内容和实际引用资源；
4. 代码变更不得借内容同步分支发布；
5. 草稿、私有来源、SQLite、日志、密钥和本地缓存不得进入公开提交；
6. 未确认所有权的文件保持不动，不重置、不覆盖、不批量暂存。

验收：每个变更都有明确去向；没有“顺便一起提交”的文件。

### 阶段 B：刷新安全证据

目标：在继续公开同步前，证明当前内容可以恢复，体检结果对应当前版本。

行动顺序：

1. 运行恢复演练；
2. 演练成功后创建最终 SQLite 和私有内容备份；
3. 核对私有内容 Git 的本地与异地提交一致；
4. 对当前内容重新生成体检报告；
5. 对 R2 台账、远端对象和私有字节执行只读对账；
6. 把“未测量”“失败”和“通过”分开记录。

验收：恢复演练与备份均为新鲜状态，内容体检时间晚于最近内容变更，R2 不一致项有明确处理结论。

阶段 B 会更新本地运行记录或报告，执行前必须再次确认工作区所有权；本计划本身不代表这些动作已经完成。

### 阶段 C：完成一个真实发布批次

目标：用最小真实批次验证已经存在的发布闭环，不开发新能力。

行动：

1. 选择边界清楚、体检通过的小批量公开内容；
2. 使用现有隔离同步创建内容分支；
3. 核对提交只含选定 Markdown 和实际引用资源；
4. 创建 PR 并等待站点、发布台和 Workers Builds 检查；
5. 合并后等待唯一一条生产构建完成；
6. 通过 `/build.json`、生产巡检和真实内容页面核对线上版本；
7. 记录每一步的人工操作、耗时、失败原因和恢复动作。

验收：本地版本、同步提交、合并提交、Cloudflare 构建和线上内容能对应同一版本；没有把 HTTP 200、push 或绿色 CI 单独描述成上线成功。

### 阶段 D：观察十次真实任务

目标：让后续开发由使用证据驱动。

在后续十次真实的导入、编辑、发布、同步或下架任务中，只记录：

- 重复发生的问题；
- 每次多余步骤和寻找入口的时间；
- 错误或含糊的状态；
- 恢复是否困难；
- 用户必须绕过系统才能完成的动作。

不因为一次偶发不便立即开发功能。普通改进建议至少出现 3 次；数据安全、内容泄漏、错误发布和不可恢复问题第一次出现就进入 P0。

阶段结束后，只选择一个最高频或最高风险问题解决。完成并验证后，再重新排序剩余问题。

## 6. 允许开发的范围

下一阶段只允许三类代码变更：

1. 阻塞真实内容闭环的缺陷修复；
2. 会导致内容错误、私有数据泄漏、状态虚假或无法恢复的安全修复；
3. 能明确删除重复入口、合并现有流程或减少维护面的简化。

任何新功能必须说明：真实案例、重复次数、当前绕行方式、预期减少的步骤、失败恢复方式和准备删除或替换的旧复杂度。

## 7. 明确停止项

下一阶段不做：

- 新 CMS、数据库、常驻服务和在线管理后台；
- 多用户、角色权限和远程协作；
- 移动端发布台；
- Newsletter、会员和订阅；
- 通用工作流引擎、插件系统或“以后可能用到”的扩展点；
- 为了统一代码而进行的大规模 Schema、路由或存储重写；
- 同时推进多个 UI 重构；
- 未经真实使用证据支持的 AI 功能。

## 8. 下一阶段结束条件

同时满足以下条件时，本阶段结束：

1. 当前大批量工作区变更已经分批收口；
2. 恢复、备份、内容体检和 R2 对账证据新鲜；
3. 至少一个真实内容批次完成线上闭环；
4. 十次真实任务观察已经完成；
5. 已选择并解决最多一个由证据支持的主要问题；
6. 没有新增运行时、内容源或长期维护平台。

之后重新评估主要矛盾。若发布闭环已经稳定，主线应转向持续内容生产，而不是自动进入下一轮基础设施开发。
