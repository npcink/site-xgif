# XGIF 发布、恢复与阶段收尾规范

状态：当前有效

适用范围：公开内容批次、推荐清单、站点代码、生产部署，以及与其对应的本地恢复证据

最后更新：2026-08-03

## 1. 目的

本规范用于回答三个问题：本次改动是否安全进入主线，生产是否确实运行了目标版本，阶段结束后能否从现有事实恢复。

它补充 [`LOCAL_PUBLISHER_ENGINEERING_STANDARD`](../../workflow/docs/LOCAL_PUBLISHER_ENGINEERING_STANDARD.md)。后者约束发布助手内部工程行为；本文约束一次跨越本机、GitHub、Cloudflare、R2 和生产站点的完整收尾。

## 2. 长期边界

| 系统 | 拥有的事实 | 不能证明的事实 |
| --- | --- | --- |
| `site/src/content/` | 公开正文与元数据 | 是否已推送、合并或上线 |
| `workflow/` 与 SQLite | 本机编辑流程、可重建索引、操作状态 | 公开远端和生产的最终状态 |
| 私有内容 Git | 草稿、私有来源、回收站与恢复历史 | 公开站点已部署 |
| GitHub | 提交、分支、PR、检查与合并 | Cloudflare 已提供该版本 |
| Cloudflare `/build.json` | 当前生产构建的提交版本 | 页面内容和关键路径均正确 |
| 生产 URL 与 sitemap | 用户实际可访问的结果 | 本机数据是否有恢复副本 |
| R2 对账 | 图片引用、台账、远端对象和私有字节的一致性 | 文章发布或站点部署完成 |

禁止把相邻事实当作结论：HTTP 200、测试通过、代码已 push、PR 已合并或构建成功，都不能单独称为“发布完成”。

## 3. 证据阶梯

每次报告必须明确停在哪一层；未执行的层级写“未执行”，不能省略。

1. **本地验证**：目标提交在干净、可复现的源码环境中通过相应测试。
2. **远端候选**：提交已推送到明确分支。
3. **PR 与 CI**：PR 已创建，所需检查均通过。
4. **主线来源**：PR 已合并，记录准确的 `main` 提交 SHA。
5. **生产构建**：`/build.json` 与目标 SHA 一致。
6. **生产核验**：严格生产巡检和关键真实 URL 通过。
7. **人工验收**：需要主观判断的视觉、内容或操作体验由人确认。

前一层不能替代后一层。生产核验失败时，即使 CI 全绿，本轮仍未完成。

## 4. 收尾前置检查

### 4.1 保护共享工作区

先只读检查：

```bash
git status --short --branch
git worktree list --porcelain
git fetch origin --prune
git rev-parse origin/main
```

- 共享工作区有未提交内容时，不切分支、不 reset、不 stash、不使用 `git add .`。
- 从最新 `origin/main` 创建独立 worktree 和 `codex/*` 或 `content-sync/*` 分支。
- 内容发布和程序改动使用不同的提交白名单；推荐清单优先使用只包含一个生成文件的独立 PR。
- 先盘点开放 PR、历史内容分支和临时 worktree，再决定哪些需要合并、保留或删除。

### 4.2 冻结目标范围

开始写入前记录：

- 基线 SHA；
- 本轮允许修改的路径；
- 内容数量和内容指纹；
- 已存在的恢复演练、SQLite 备份、私有快照和 R2 对账时间；
- 本轮是否包含代码、内容、推荐或生产脚本。

范围变化后重新评估测试和恢复证据，不沿用旧结论。

## 5. 标准执行顺序

### 5.1 合并公开内容候选

1. 从最新主线建立隔离候选。
2. 只合并已确认的内容提交或精确复制白名单内容。
3. 运行内容体检，分别记录可上线、需复核和阻断数量。
4. 短内容不得为了通过长度门禁而填充无意义文字。确属完整短内容时，使用 `shortFormReviewed: true` 明确记录人工判断；正文修改后必须使旧确认失效。
5. 把历史内容分支收敛到一个可审查 PR；合并后删除已吸收或废弃的远端分支。

### 5.2 验证候选

基础验证：

```bash
(cd workflow && npm test)
(cd workflow && npm run test:browser)
(cd site && npm test)
(cd site && npm run test:visual:linux)
(cd site && npm run check:deploy)
git diff --check
```

按改动范围裁剪时，必须说明跳过了什么和原因。发布状态、恢复、队列或远端逻辑变化时，不能只运行静态测试。

视觉基线规则：

- Linux 容器结果是权威基线，macOS 字体栅格差异只作为线索。
- 截图失败先区分“页面未就绪、断言过时、数据量改变”和“真实视觉回归”。
- 异步弹层等待语义完成状态，例如 `aria-busy=false` 和目标标题，不只等待容器可见。
- 更新基线前下载 CI 实际产物，重复运行确认稳定，并人工查看差异。

### 5.3 PR、合并与主线检查

1. 精确暂存目标文件并运行 `git diff --cached --check`。
2. push 后创建 PR，等待站点、发布助手和 Workers Builds 所需检查。
3. 检查失败时修根因；不能通过放宽门禁或隐藏失败完成收尾。
4. 合并后记录新的主线 SHA，并等待主线检查完成。

### 5.4 恢复演练与最终备份

恢复证据顺序固定为：

```bash
cd workflow
npm run data:verify-recovery
npm run data:backup
```

原因是恢复演练会形成新的数据库维护事实，最终 SQLite 备份必须在其后创建。执行后确认：

- 临时损坏数据库被隔离，真实数据库和正文未被修改；
- 重建内容数、回收站数、代码版本和内容指纹符合预期；
- 私有内容快照已产生，异机私有远端同步结果可见；
- 如果演练或备份后内容再次变化，旧证据立即失效，必须重新演练并备份。

### 5.5 R2 对账

```bash
cd workflow
npm run r2:reconcile
```

必须分别核对 Markdown 引用、R2 台账、真实远端对象和私有字节。默认只读；孤立对象不因一次扫描立即删除。只有对象键明确、观察期满足、远端健康且私有字节完整时，才进入单对象清理流程。

### 5.6 推荐清单

发布验收使用严格向量模式：

```bash
cd workflow
npm run recommendations:build -- --require-embeddings
```

- 向量服务不可用时保留最后一次成功的混合推荐清单，不用规则回退覆盖它。
- 本机端口映射只监听 `127.0.0.1`，按需临时建立，任务结束后关闭；不得在文档或日志记录凭据。
- 记录文档数、缓存命中、生成数、向量维度和最终模式。
- 推荐清单从干净 `origin/main` 环境发布，只提交 `site/src/data/recommendations.json`。共享脏分支报告的“待同步内容”不能作为主线事实。

### 5.7 部署与生产核验

合并后执行：

```bash
cd site
EXPECTED_SHA=<main-sha> REQUIRE_APEX_REDIRECT=true npm run test:production
```

生产巡检至少验证：

- `www` 主站可用，裸域重定向保留路径和查询参数；
- `/build.json` 精确等于目标 SHA；
- 文章索引可发现真实文章；
- sitemap 使用当前公开路由契约；
- 本轮新增或关键文章返回 200 且出现在 sitemap；
- 必要时手动触发 GitHub Production smoke，保留运行链接。

巡检脚本必须从实际页面或当前路由契约发现目标，不能永久写死已经废弃的 URL 结构。修改路由时，同一 PR 更新巡检和契约测试。

### 5.8 清理

只有在合并、部署和生产核验均完成后才清理：

- 已合并或明确废弃的远端内容分支；
- 本轮临时 worktree；
- 临时 SSH 端口映射；
- 已关闭 PR 的本地候选分支（确认无恢复价值后）。

不删除共享脏工作区，不把“本地后台仍在运行”解释为“它运行的是最新主线”。后台版本必须通过运行时版本信息单独确认。

## 6. 常见失败与处理

| 现象 | 首先核对 | 正确处理 |
| --- | --- | --- |
| 本机视觉失败、Linux 通过 | 字体栅格和容器基线 | 以 Linux 为准，不批量刷新截图 |
| CI 截图失败 | 页面是否真正加载完成、筛选数据量、实际差异 | 等待语义完成状态，下载产物复核 |
| 共享发布器报告意外待同步内容 | 当前分支、索引和主线是否一致 | 用干净主线上下文发布，不放宽门禁 |
| 严格推荐生成失败 | 模型端点和本机隧道是否可达 | 保留最后成功清单，恢复端点后重试 |
| 生产 200 但巡检失败 | `/build.json`、sitemap、路由契约 | 修复契约或生产问题，不把 200 当成功 |
| 恢复/备份完成后又改内容 | 内容指纹是否变化 | 重新恢复演练，再创建最终备份 |
| 命令提示找不到 `package.json` | 当前目录是否正确 | 按 `site/`、`workflow/` 明确执行目录 |

## 7. 禁止的捷径

- 在共享脏工作区直接整理、提交或同步历史内容。
- 用无意义扩写绕过内容质量门禁。
- 因 CI 截图变化直接覆盖全部视觉基线。
- 在向量失败后发布一个未标注的规则降级清单。
- 把 push、PR、绿 CI、HTTP 200 或 Cloudflare 构建任一单项称为上线完成。
- 备份后继续修改内容，却仍引用旧备份作为最终恢复证据。
- 为通过生产巡检而降低版本、重定向或 sitemap 断言。
- 批量删除 R2 对象、共享 worktree 或不明来源分支。

```text
范围：代码 / 内容 / 推荐 / 运维

PR/CI：<PR + required checks>
主线：<merged sha>
本地验证：<commands + results>

人工验收：<done/not done>
清理：<branches/worktrees/tunnels>
保留问题：<owner + next action>
```

## 9. 完成定义

一次阶段收尾只有同时满足以下条件才算完成：

- 目标变更已通过对应的本地测试和差异检查；
- PR 所需 CI 通过并合并到主线；
- 生产构建 SHA 与目标主线一致，严格生产巡检通过；
- 当前内容指纹对应的恢复演练、最终 SQLite 备份和私有快照存在；
- R2 和推荐状态已按本轮范围验证，降级项被如实标注；
- 临时资源已清理，共享用户工作区保持不变；
- 报告明确区分机器证据、人工验收和未执行事项。
