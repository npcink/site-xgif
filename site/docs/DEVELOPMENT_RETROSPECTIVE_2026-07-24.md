# XGIF 阶段开发复盘：从静态站部署到可恢复的单人内容系统

最后更新：2026-07-24

阶段功能收尾基线：`bb04f4d`（PR #12）

生产站点：`https://www.xgif.cn`

## 1. 复盘结论

XGIF 最终形成的不是传统 CMS，而是一套边界清楚的单人内容工作流：

```text
本机采集与整理
→ Markdown / 图片元数据
→ 本地真实预览
→ Git 分支与 PR
→ GitHub 自动验证
→ Cloudflare Workers Static Assets
→ 生产巡检确认真实版本
```

系统刻意把不同职责拆开：

- **公开站点**只读取 Git 中的公开 Markdown，构建为静态文件；
- **本地发布助手**负责导入、AI 整理、质量检查、批量管理和同步，不对公网开放；
- **SQLite**只做可重建索引，不保存唯一正文；
- **R2**只保存新图片字节，不管理标题、来源或发布状态；
- **Git**保存公开内容和代码的可审计历史；
- **本机私有 Git 远端**保存草稿、私有正文副本和 R2 原始字节；
- **Cloudflare**负责静态托管、R2 公网读取及边缘防护，不成为第二套 CMS。

最重要的成果不是功能数量，而是建立了四条长期有效的原则：

1. 权威数据必须可说明、可恢复，派生数据可以删除重建；
2. 内容状态、Git 状态和部署状态必须分开表达；
3. AI 可以减少填写工作，但不能伪造来源、授权或替代发布决策；
4. “构建成功”不等于“生产已生效”，上线必须对应到具体提交和真实 URL。

## 2. 项目演进历史

### 2.1 仓库边界与 Astro 站点

项目最初同时存在站点、发布工具和旧 Next.js 设计。为了避免部署目录和源码所有权混乱，仓库收敛为：

- `site/`：当前 Astro 公开站点；
- `workflow/`：只在本机运行的发布助手；
- `old/`：只读 Next.js 视觉档案。

这一调整解决了后续多次出现的根本问题：Cloudflare 只能构建 `site/`，不能把含 `.env` 和本地操作能力的 `workflow/` 部署出去。根目录只负责 Git、CI 和项目导航。

视觉迁移没有直接重写旧版，而是保留旧 Next.js 基线，用结构测试和 Linux Playwright 截图保护首页、文章详情、图片弹层和移动端布局。这样既能继续迭代 Astro，也不会失去已经认可的视觉依据。

### 2.2 Cloudflare：从 Pages 判断到 Workers Static Assets

最初根据旧入口选择 Cloudflare Pages，但实际创建项目时，Cloudflare 新项目流程已经转向 Workers Static Assets。项目及时修订方案：

- Root directory：`/site`
- Build command：`npm run build`
- Deploy command：`npx wrangler deploy`
- Wrangler 项目：`site-www-xgif`
- 静态资源目录：`./dist`
- 不配置 Worker `main` 脚本
- 不配置运行时绑定或密钥

这里的经验是：平台界面和推荐会变化，不能因为刚写过一份文档就固守旧决定。ADR-003 被 ADR-004 正式替代，旧记录保留用于说明为什么改变。

部署过程还验证了受保护分支的正确价值：`main` 不允许直接推送，所有生产变更通过分支、PR、GitHub 检查、Cloudflare 构建和合并完成。最终 `www.xgif.cn` 成为 canonical 域名，裸域 `xgif.cn` 通过 Cloudflare 301 跳转，并保留路径与查询参数。

### 2.3 本地发布助手：从表单到发布工作台

发布助手最初只负责生成文章和图片 Markdown，随后在真实使用中逐渐补齐：

- AI 整理文章和图片资料；
- 重复检查与发布质量检查；
- 本地站点预览与草稿真实预览；
- 内容列表、搜索、分页和筛选；
- 当前页全选与符合筛选条件的全选；
- 批量发布、退回草稿、修改属性和同步；
- 回收站、批量恢复和明确确认后的永久清理；
- Git 分支、提交、推送和部署状态核验。

界面曾经把大量元数据、Git 选项和发布选项同时展开，也把“草稿、本地发布、待提交、待推送、已同步”等状态并列显示。真实使用证明这会增加认知负担。

后续收敛为三个内容状态：

1. 草稿；
2. 本地发布；
3. 云端发布。

Git 提交、推送和 Cloudflare 部署属于同步过程，只放在“同步详情”中。AI 常用字段保留在主流程，低频来源、授权和 Git 选项折叠到详细资料或高级设置。

这个过程说明：后台“不好用”往往不是 CSS 问题，而是状态模型和操作层级没有收敛。先明确用户真正要完成的动作，再决定字段和按钮的位置。

### 2.4 flomo 导入与来源治理

flomo ZIP 导入最初解决批量生成草稿，随后围绕真实数据补充：

- 正文指纹精确去重与相似内容提醒；
- 默认选中可导入项；
- 全选、取消全选和只看未选中项；
- 从正文开头、结尾、独立行、Markdown 链接及“来源/原文/出处”格式提取 URL；
- 多个链接时只采用唯一明确来源，避免擅自猜测；
- 按域名推断煎蛋、知乎、虎扑和 NGA 等来源名称；
- 清理正文中的来源链接行和 flomo 分组标签；
- 把内部导入标签与公开内容标签分离；
- 导入后统一保存为草稿，仍需人工复核。

来源治理的核心不是“尽量把字段填满”，而是“有证据才结构化”。没有链接时使用“来源待确认”，不能把 flomo 导入误标为原创；多个链接无法判断时保留复核状态，不能让 AI 随机选择。

### 2.5 图片来源、R2 与边缘保护

图片来源分为三类：

- `original`：有可核验的作者、来源与授权；
- `user_provided`：用户明确确认可公开发布，并写最小授权台账；
- `unknown`：微信群或 QQ 群转存，无法确认原作者和授权。

`unknown` 图片允许发布，但必须如实显示“来源待核实”，并在公开页提供版权投诉与下架入口。AI 不得推测作者或授权。

随着表情包增加，新图片字节改存 Cloudflare R2：

- Bucket：`xgif-memes-prod`
- 公网域名：`img.xgif.cn`
- 对象键：`memes/<sha256>.<ext>`
- 长缓存且 URL 不带查询参数
- 外站非空 Referer 拦截
- 查询串拦截
- 单 IP 速率限制

R2 没有成为元数据库。标题、标签、来源、发布状态仍在 Markdown；`records/r2-assets.jsonl` 只记录对象位置和哈希。后来又补充了：

- 真实远端 HEAD 核验；
- 按 SHA-256 保存的本机私有原始字节；
- 私有 Git 远端备份；
- Markdown、台账、远端对象和私有字节四方对账；
- 孤立对象连续观察 30 天后才允许精确删除单个对象。

这避免了两个常见错误：把“R2 有对象”误认为“内容可恢复”，以及为了清理孤立文件而引入不可逆的批量删除风险。

### 2.6 SQLite、回收站与可恢复性

当内容管理需要分页、批量操作、回收站和操作历史时，仅扫描 Markdown 和依赖浏览器状态开始变得笨重。项目引入 Node.js 内置 SQLite，但明确限制其职责：

- 内容索引；
- 回收站索引；
- 操作历史；
- 数据库迁移版本。

SQLite 不保存唯一正文。数据库损坏时：

1. 先运行 `PRAGMA quick_check`；
2. 把损坏数据库及 WAL/SHM 隔离；
3. 从 Markdown 和回收站旁车重新建立；
4. 使用 SQLite Backup API 创建一致备份。

后续列表查询改为增量索引与 SQL 搜索、筛选和排序，不再每次完整读取所有 Markdown。数据库既发挥了查询价值，又没有成为新的事实来源。

本机私有 Git 历史只白名单保存内容文件、私有正文、回收站、台账和本地图片，并配置私有 GitHub 远端，降低整机以外的内容丢失风险。

### 2.7 稳定 ID 与公开正文边界

早期 URL 使用日期加中文标题，复制后编码过长，标题变化也会改变地址。因为项目尚无访客，内容一次性迁移为：

```text
YYYYMMDD-xxxx
```

`contentId` 同时作为 frontmatter、Markdown 文件名和公开 URL，一旦生成便不可修改。标题和发布日期可继续编辑，不影响链接。

外部文章公开边界曾经历一次明确变化：

- ADR-009：公开只展示编辑摘要，完整正文留在私有目录；
- ADR-010：运营者决定公开完整正文，同时保留来源链接、投诉邮箱和私有副本。

这不是代码细节，而是内容与版权风险决策，因此用新 ADR 替代旧 ADR，而不是悄悄改实现。当前公开 Git 和 Cloudflare 会包含外部来源完整正文；来源链接和投诉机制不等于已经取得转载授权，收到有效投诉后必须及时处理。

### 2.8 系统加固与生产证据

收尾审计发现了几个容易被忽略的系统问题：

- 发布器端口存在，但可能仍是旧进程；
- 422 或其他非 5xx 响应曾被误判为健康；
- 回环服务仍可能受到恶意 Host、Origin 或跨站修改请求影响；
- `toISOString().slice(0, 10)` 会在北京时间日期边界生成错误日期；
- 构建成功无法证明生产正在运行该提交；
- R2 台账无法证明远端对象和恢复副本真实存在。

因此补充：

- 发布器源码版本哈希和 `/api/health`；
- 旧进程自动识别与安全重启；
- Host、Origin、JSON Content-Type 和 CSRF 防护；
- Asia/Shanghai 日历日期函数；
- 真实 HTTP 集成测试；
- 导入正文禁止原始 HTML；
- 收紧 CSP，去除 `unsafe-inline`；
- 新图片宽高元数据；
- 构建产物站内断链检查；
- 基础可访问性检查；
- `/build.json` 暴露生产 commit 和构建时间；
- GitHub 每日生产巡检。

生产验收最终不再是“控制台显示绿色”，而是：

1. GitHub 检查成功；
2. Cloudflare Workers Build 成功；
3. `/build.json` 对应预期 commit；
4. 真实文章、来源、投诉页和 R2 图片可访问；
5. R2 外站盗链被拒绝；
6. `xgif.cn` 对 HTTP/HTTPS 都返回 301，路径和查询参数完整保留。

## 3. 当前权威数据与恢复顺序

| 数据 | 权威位置 | 是否可删除重建 |
| --- | --- | --- |
| 公开文章正文与元数据 | `site/src/content/articles/*.md` + Git | 否 |
| 图片元数据与发布状态 | `site/src/content/images/*.md` + Git | 否 |
| 新图片字节 | R2 + 本机私有哈希备份 | 否 |
| 旧本地图片字节 | `site/public/images/memes/` + Git/私有备份 | 否 |
| 草稿与外部文章私有副本 | 本机文件 + 私有内容 Git 远端 | 否 |
| R2 对象位置 | `workflow/records/r2-assets.jsonl` | 可由多方核对，但不应随意删除 |
| 回收站内容 | `workflow/trash/` + 旁车 + 私有内容 Git | 否，清理前需确认 |
| SQLite 内容索引 | `workflow/.runtime/xgif.sqlite3` | 是 |
| Astro 构建产物 | `site/dist/` | 是 |
| Cloudflare 线上部署 | Git `main` 的派生产物 | 是 |

恢复时先找权威内容，再重建索引和部署，不能反过来从 SQLite 或浏览器状态恢复正文。

## 4. 关键开发经验

### 4.1 先找主要矛盾，不要从加功能开始

最初很多不适表现为“缺少按钮、列表太长、字段太多”，但主要矛盾分别是：

- 批量导入：选择模型不清楚；
- 内容管理：内容状态和同步状态混杂；
- 发布图片：来源契约与真实素材来源不匹配；
- 线上同步：本地发布与云端部署没有证据链。

只有先解释状态和权威边界，界面优化才不会变成继续堆按钮。

### 4.2 本地服务也需要安全边界

只监听 `127.0.0.1` 能减少暴露面，但浏览器仍可能被跨站请求利用，Host 也可能被重绑定。回环服务同样应验证请求来源、修改方法和会话令牌，并且绝不能通过公网隧道直接暴露。

### 4.3 数据库的价值是查询，不是成为唯一真相

SQLite 适合单人本地工具，但必须让 Markdown 和旁车能够独立恢复。引入数据库前先写清：

- 哪些数据只能在数据库；
- 数据库删除后会怎样；
- 如何验证和备份；
- 谁是最终权威源。

如果这些问题答不清，就不应引入 D1 或线上数据库。

### 4.4 对象存储只解决字节，不解决内容管理

R2 降低 Git 仓库和静态部署的图片负担，但不应顺带接管标题、标签、发布状态和权限。存储与 CMS 分离，使项目仍能用 Markdown 审查内容，也能随时替换对象存储实现。

### 4.5 AI 应负责草拟，不应负责证明

AI 擅长标题、摘要、标签和描述，不擅长证明来源、作者和授权。无法获得的信息应明确为空或“待确认”，而不是为了通过校验生成看似完整的元数据。

### 4.6 状态必须少而互斥

面向用户的状态应回答“内容现在能在哪里看到”：

- 草稿；
- 本地发布；
- 云端发布。

Git 是否提交、是否推送、Cloudflare 是否部署是过程状态，不能与内容状态并列。批量操作必须明确“可处理、跳过、失败”，而不是让按钮在不同状态下神秘消失。

### 4.7 平台事实要实时核验

Cloudflare Pages/Workers 的入口和推荐会更新；控制台截图与旧文档可能不一致。部署错误应先核对：

- 当前产品类型；
- 工作目录；
- 构建和部署命令；
- 产物目录；
- 是否错误加入运行时适配器。

DNS 的 `URI` 记录也不能代替 HTTP 301；重定向需要已代理的 DNS 记录和 Redirect Rule。

### 4.8 视觉基线必须固定运行环境

macOS 与 Linux 的字体栅格不同，本机截图像素差异不等于设计回归。项目以 Playwright Linux 容器为权威视觉环境；本机失败时先判断是否平台差异，不能直接重写全部基线。

### 4.9 发布完成必须有分层证据

建议始终按以下顺序验收：

```text
源码与测试
→ Git commit
→ push
→ PR checks
→ merge commit
→ Cloudflare production build
→ /build.json commit
→ 真实页面与边缘规则
```

其中任一步成功都不能替代后一步。

## 5. 发生过的问题与纠正方式

| 问题 | 根因 | 纠正 |
| --- | --- | --- |
| Wrangler 找不到静态目录 | Cloudflare Root 在仓库根 | Root 改为 `/site`，保留 `assets.directory: ./dist` |
| 误以为应使用 Pages | 平台入口和旧认知变化 | 根据当前平台事实改用 Workers Static Assets，并用 ADR 替代旧决定 |
| 发布器显示运行但实际是旧代码 | 只探测端口/宽松状态码 | 服务标识、源码版本和严格 2xx 健康检查 |
| 北京时间日期偶尔错误 | 使用 UTC 字符串截取日期 | 固定 Asia/Shanghai 日历日期函数 |
| 后台状态过多 | 内容状态与 Git/部署状态混在一起 | 收敛为草稿、本地发布、云端发布 |
| 图片发布要求无法获得的作者与授权 | 校验契约不符合群聊素材现实 | 增加 `unknown`，如实披露并提供投诉入口 |
| flomo 正文来源链接没有结构化 | 只检查固定位置或手工填写 | 检查正文任意位置，明确链接才自动采用 |
| 标签和导入分组混入正文 | 未区分内容标签和管理标签 | 导入时剥离、规范化，并把内部分组留在台账 |
| 中文标题 URL 过长且不稳定 | URL 与可编辑标题绑定 | 一次性迁移为不可变 `contentId` |
| R2 只有一份公开对象 | 台账不等于备份 | 哈希私有字节备份、远端核验和安全清理观察期 |
| 构建绿色但无法确认线上版本 | 缺少生产提交证据 | `/build.json` + `EXPECTED_SHA` 生产巡检 |
| 裸域使用 URI DNS 记录 | 把 DNS 元数据误当 HTTP 跳转 | 代理 A 记录 + Cloudflare Single Redirect，实测 301 |

## 6. 当前日常操作

启动本地工作台：

```bash
cd workflow
npm start
```

管理器和站点预览应分别可访问：

```text
http://127.0.0.1:8787
http://127.0.0.1:4321
```

常用验证：

```bash
cd workflow
npm test
npm run data:status
npm run data:verify-recovery
npm run r2:reconcile

cd ../site
npm test
npm run test:visual:linux
npm run check:deploy
npm run test:production
```

正常生产发布只使用一条路径：

```text
内容或代码分支
→ PR
→ GitHub checks
→ 合并 main
→ Cloudflare Workers Builds 自动部署
→ 生产巡检
```

不要在自动构建运行时同时执行本机 `wrangler deploy`，避免两个版本互相覆盖。

## 7. 当前阶段边界

截至 2026-07-24，本阶段已经完成：

- `www.xgif.cn` 生产部署；
- `xgif.cn` 永久跳转且保留路径和查询参数；
- 本地文章、图片、批量导入和内容管理闭环；
- SQLite 可重建索引与恢复演练；
- R2 新图片存储、对账、备份和防滥用；
- 稳定内容 ID；
- 外部文章完整正文发布与投诉入口；
- GitHub、Cloudflare 和真实生产证据链；
- 本地发布助手安全加固。

当前不需要新增：

- D1；
- Vectorize；
- 在线 CMS；
- 多用户账号；
- Worker 上传 API；
- 远程管理后台；
- 为了“以后可能需要”而建立的复杂搜索或消息系统。

下一阶段主线应回到内容本身：复核现有草稿、持续发布文章和表情包、处理真实反馈。只有同一问题在真实使用中反复出现，才新增对应能力。

## 8. 未来开发决策清单

每次准备增加功能前，先回答：

1. 它是否直接降低发布一篇文章或一张图片的成本？
2. 这个问题是否已在真实使用中重复出现？
3. 当前权威数据在哪里，失败后如何恢复？
4. 是否会引入第二套内容、状态或权限真相？
5. 能否通过本地工具或构建期处理，而不是增加线上运行时？
6. AI 输出中哪些是建议，哪些必须有外部证据？
7. 如何证明它已经进入生产，而不仅是本地或 CI 成功？
8. 删除、迁移和回滚的最小安全单位是什么？

如果前两项没有明确答案，或者第 3、4 项说不清，应暂停实现，先继续使用当前简单方案。
