# XGIF 开发历史归纳与经验总结

日期：2026-08-03

范围：技术选型、开源项目借鉴、复杂度控制、发布助手收口与后续开发方式

## 1. 起点：不是选择“功能最多的 CMS”

最初的问题是当前项目是否应改用 Hexo 或 Ghost，以及有哪些相似开源项目可供学习。调查后，真正需要回答的不是框架流行度，而是：新的方案能否在保留现有内容、URL、来源治理、私有恢复、Git/PR 和生产证据的前提下，显著降低未来维护成本。

结论是继续采用 Astro、Markdown 和本地发布助手：

- Hexo 与 Astro 都能生成 Markdown 静态站，迁移主要是横向重写，不能消除 XGIF 的定制内容契约和发布流程；
- Ghost 擅长在线编辑、定时发布、多人角色、Newsletter 和会员，但当前没有这些需求，引入它会增加数据库、认证、升级、备份与双重内容真相；
- Ghost Headless + Astro 仍需同时维护 Ghost 和本地发布助手，并不能自然替代现有恢复与发布事实链。

完整论证见 [ADR-017](decisions/ADR-017-retain-astro-over-hexo-or-ghost.md)。

## 2. 开源项目调研：吸收模式，不复制产品

后续比较了 Publii、Front Matter CMS、Keystatic、Decap CMS、Sveltia CMS、Pages CMS 和 Memos。没有一个项目能在不扩大运行时和数据边界的情况下完整替代现有发布助手，但它们提供了可借鉴的成熟模式：

| 项目 | 值得学习 | 当前不直接采用的原因 |
| --- | --- | --- |
| Publii | 本地优先、备份、预览和发布心智 | 会连同站点生成一起替换 Astro，Git/PR 事实链不匹配。 |
| Front Matter CMS | 高密度内容列表、元数据侧栏、媒体与预览短路径 | 依赖 VS Code，不能替代专用发布事务和恢复。 |
| Keystatic | Schema 驱动字段和 Astro/文件集成 | 只能覆盖部分 CRUD，仍需保留大量自定义服务。 |
| Decap / Sveltia | Git 分支、审核和失败状态机 | 远端草稿与当前私有内容边界冲突。 |
| Pages CMS | 配置化集合、字段、媒体和写入保护 | 在线认证与数据库会增加当前不需要的运行时。 |
| Memos | 快速采集、先收集后整理 | 会形成额外正文数据库，不能替代静态发布系统。 |

形成的原则是：把第三方项目当作遇到具体问题时的模式索引，而不是待实现的功能清单。完整比较见 [ADR-018](decisions/ADR-018-retain-local-publisher-and-learn-from-open-source-cms.md)。

## 3. 复杂度反思：AI 降低编码成本，不降低系统成本

项目主要由一人借助 AI 开发。AI 能快速生成代码、测试和文档，但不会自动承担长期状态一致性、发布真实性、恢复决策、跨 worktree 所有权和未来维护理解成本。

因此，判断一项能力是否值得实现时，不能只看“AI 能不能写出来”，而要看：

- 是否解决重复出现的真实问题；
- 是否减少而不是增加状态、入口和失败面；
- 是否保持单一内容权威源；
- 是否具有确定性校验、恢复点和回滚方式；
- 未来重新理解和维护它的成本是否低于带来的收益。

这次主动拒绝了批量 AI 标题流水线、语义重复工作台、在线 CMS、多用户后台、大范围工具栏重排和纯审美视觉重做。它们不是遗漏，而是没有通过当前单人项目的收益门槛。

## 4. 从大分支回到小批次

旧开发分支累积了内容迁移、发布状态、导入、编辑器、首页和视觉基线等混合变化。直接整批提交会让审查、测试、回退和所有权失真。

最终采取的办法是：保护原共享脏工作区，从最新 `origin/main` 建立独立 worktree，把有价值的改动重建为五个小垂直切片：

1. PR #40：内容同步后自动创建或复用开放 PR，但永不自动合并；
2. PR #41：将主状态收口为草稿、发布中和已核验上线；
3. PR #42：flomo 批量分组、异常整批复核和最终字段服务端重验；
4. PR #43：只简化高频编辑器动作，不引入新的 AI 管道；
5. PR #44：明确首页只筛选精选内容，并提供全站搜索路径。

每批都独立测试、审查、提交、push、PR 和合并。详细提交与验证证据见[下一阶段实施收口](NEXT_STAGE_IMPLEMENTATION_CLOSEOUT_2026-08-03.md)。

## 5. 这段历史形成的开发思路

### 先确定事实边界

本地测试、远端分支、PR checks、主分支合并、Cloudflare 部署、线上版本和人工验收是不同证据层级。任何一层都不能自动替代下一层。

### 先保证能恢复

Markdown 是公开内容权威源，SQLite 可重建；删除、同步和恢复携带版本或哈希；失败保留分支、记录和下一步。宁可显示未知，也不伪造成功。

### 先完成任务，再优化界面

优先处理数据安全、发布事实和工作流阻断，然后才处理高频点击，最后才考虑视觉。一个任务保留一个主动作，低频能力退出主界面。

### 批量减少重复，人工保留最终判断

系统可以集中分组、检查和生成候选，但来源、授权、异常内容与最终公开决定仍由人明确确认。批量工作允许少数例外逐条覆盖。

### 用最小切片控制 AI 开发风险

每批先声明目标、非目标和验收条件；从干净基线实现；只暂存明确文件；测试失败先找根因；合并后核对远端事实；确认干净且可恢复后再清理临时 worktree。

## 6. 当前结论与下一阶段

截至 2026-08-03，已知 P0 工程问题已经收口。接下来不继续堆功能，而是完成 5–10 次真实自用发布循环，记录任务类型、卡点、额外补救和是否完成。

只有重复摩擦、数据风险、发布阻断或可以稳定消除的高频重复操作，才进入下一批开发。具体门槛、Git/worktree 规则、验证矩阵和完成定义统一以[开发与交付规范](DEVELOPMENT_AND_DELIVERY_STANDARD.md)为准。
