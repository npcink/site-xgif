# XGIF 开发与交付规范

状态：生效

版本：1.0

日期：2026-08-03

适用范围：`site-xgif` 的站点、内容、本地发布助手、GitHub 与 Cloudflare 交付流程

## 1. 目的

本规范把项目从 2026 年 7 月至 8 月的开发、排错、发布和复盘经验固化为后续人和 AI 都必须遵守的工作方式。目标不是让流程更复杂，而是保证单人项目始终具备以下特征：

- 能用最少系统完成真实内容发布；
- 内容、状态和发布结论有可核对的事实来源；
- 任何失败都尽量可恢复，不覆盖用户工作；
- 只为重复发生的真实问题增加复杂度；
- 每个改动足够小，能够独立审查、验证和回退。

历史事实、PR、测试结果和本轮纠错过程见[下一阶段实施收口](NEXT_STAGE_IMPLEMENTATION_CLOSEOUT_2026-08-03.md)。架构取舍见 [ADR-017](decisions/ADR-017-retain-astro-over-hexo-or-ghost.md) 和 [ADR-018](decisions/ADR-018-retain-local-publisher-and-learn-from-open-source-cms.md)。

## 2. 项目基本判断

XGIF 当前是一个由单人使用 AI 开发和维护的轻内容站，不是多人 SaaS、通用 CMS 或内容平台。默认技术方案保持为：

- Astro 静态站点；
- Markdown 公开内容；
- 本地发布助手；
- 可重建的本地 SQLite 索引；
- GitHub PR 作为公开变更入口；
- Cloudflare Workers Builds 作为正常生产部署路径。

在真实需求没有改变以前，不切换 Hexo、Ghost 或数据库型远程 CMS，不新增多租户、账号权限、在线协作、消息队列、第二套内容数据库或常驻后台服务。

## 3. 决策原则

### 3.1 真实问题优先

进入开发的事项至少满足一项：

1. 同一个问题在两次或以上真实操作中重复出现；
2. 问题可能造成内容错误、来源失真、覆盖较新版本或无法恢复；
3. 问题阻断“创建或导入 → 复核 → 本地发布 → 同步 PR → 合并 → 线上核验”；
4. 一个小改动能够稳定消除每次都会发生的重复操作。

未达到门槛的想法只进入待观察清单，不立即实现。不得以“其他 CMS 有”“以后也许需要”或“AI 可以顺便做”为理由扩张范围。

### 3.2 先处理主要矛盾

每一阶段只确定一个主攻目标。优先级顺序为：

1. 数据正确性与可恢复性；
2. 发布事实与状态可信度；
3. 能否完成真实工作流；
4. 高频操作效率；
5. 视觉和低频便利性。

安全事实链未闭合时，不先做视觉重构；真实操作尚未重复时，不先建通用能力。

### 3.3 吸收经验，不复制系统

借鉴开源 CMS 时只吸收可独立验证的模式，例如草稿与发布分离、版本记录、显式复核、可恢复删除、清晰的主动作和诚实状态。不得因为借鉴 Ghost、WordPress 或其他项目而复制其账号体系、插件体系、多人审批或线上运行时。

## 4. 不可破坏的架构边界

| 边界 | 规范 |
| --- | --- |
| `site/` | 只负责公开 Astro 站点、公开内容、站点测试和部署配置。 |
| `workflow/` | 只在本机运行，负责导入、编辑、AI 辅助、复核、恢复和 Git 内容同步；不得部署到公网。 |
| `old/` | 只读历史视觉参考，不参与构建和发布。 |
| Markdown | 公开内容权威源；标题或日期可改，`contentId` 不可重建。 |
| SQLite | 派生索引，必须能够从 Markdown 和旁车数据重建，不能成为唯一内容真相。 |
| R2 / 本地图片 | 图片字节来源；公开内容必须保存可核对的来源、授权或待核实声明。 |
| GitHub | 公开程序、公开内容、PR 和部署历史；草稿、私有正文、凭据与运行日志不得进入公开提交。 |
| Cloudflare | 只部署 `site/` 的静态产物；正常发布等待 Workers Builds，不能与手工 Wrangler 并行部署同一提交。 |

改变以上任一边界前必须：提供真实不足证据、比较最小替代方案、写新的 ADR，并说明迁移与回退方式。

## 5. AI 使用边界

AI 可以：

- 生成可编辑的标题、摘要和标签候选；
- 在不改变原文字节顺序的前提下增加 Markdown 段落空行；
- 帮助检查代码、测试、文档和工作流；
- 根据明确事实给出建议和批量处理方案。

AI 不可以：

- 自动确认来源、作者、授权或内部人工复核；
- 改写、删减、截断或合并导入正文后宣称只是“排版”；
- 让发布助手或无人值守 AI 自动化自行合并公开内容 PR；只有得到明确授权且必需检查通过后才可合并；
- 把推送、HTTP 200、CI 绿色或候选构建说成“已上线”；
- 在证据不足时猜测线上状态、运行版本或用户验收结论。

任何 AI 生成结果都必须保持可编辑、可拒绝，并在写入或发布前通过确定性校验。

## 6. 变更切分规范

每批改动在编码前写清楚：

- 要解决的一个具体问题；
- 验收条件；
- 明确不包含的内容；
- 受影响的路径和事实边界；
- 最小验证方法。

一批改动应能单独提交、单独测试、单独 PR、单独回退。禁止把内容迁移、发布状态、编辑器重构、首页视觉和基础设施改造混在一个大提交里。

当旧分支包含大量混合改动时，以最新 `origin/main` 为基线重建最小垂直切片，不整批复制旧差异。

## 7. Git 与 worktree 规范

### 7.1 开工前

必须核对：

```bash
pwd
git status -sb
git branch --show-current
git fetch origin main
git rev-parse origin/main
git worktree list
```

共享目录存在未提交修改时，默认这些修改属于用户或其他任务。不得 reset、stash、checkout 覆盖、批量格式化或顺手提交。

### 7.2 隔离开发

- 从最新 `origin/main` 创建 `codex/*` 独立分支和 worktree；
- 在该 worktree 内单独安装依赖和执行测试；
- 提交前再次核对绝对路径、分支和 `git status`；
- 只 `git add` 明确列出的文件；不得使用会把运行记录一起带入的宽泛暂存；
- 普通代码或文档 PR 不得顺带提交 `workflow/records/*.jsonl`；
- `flomo-imports.jsonl`、`r2-assets.jsonl` 和 `user-provided-assets.jsonl` 是受 Git 跟踪的隐私最小化内容台账，只能在对应内容发布批次中精确暂存；
- `publication-events.jsonl`、`.env`、SQLite、私有来源、原始导入包和本地备份不得进入公开提交。

### 7.3 推送与合并

`main` 受保护，正常流程为：

```text
独立分支 → 精确提交 → push → PR → 必需检查 → 合并 main
```

普通 Git 操作用 `git`；只有 PR、checks 和 GitHub API 使用 `gh`。多 worktree 环境下，远端合并后必须用 `gh pr view` 或 API 核对状态和合并提交，不得仅凭本地切换分支是否成功判断合并结果。

## 8. 内容与发布事实规范

### 8.1 内容状态

面向编辑者的主状态保持互斥：

1. 草稿；
2. 发布中；
3. 已核验上线。

“发布中”可以用次级筛选区分本地待同步、PR 待合并/部署和待线上核验。内容体检问题不与发布进度混为同一个主状态。

### 8.2 事实层级

报告时必须区分：

| 层级 | 能证明什么 |
| --- | --- |
| 本地测试通过 | 当前 worktree 的代码通过所执行的测试。 |
| 提交并 push | 远端分支存在该候选。 |
| PR checks 通过 | 候选满足配置的 CI / 构建门槛。 |
| 合并 main | 源码已进入受保护主分支。 |
| Cloudflare 构建通过 | 指定提交完成部署构建。 |
| `/build.json` 与线上探测一致 | 线上运行的是指定提交且所探测路径正常。 |
| 人工验收 | 真实任务和展示满足使用者预期。 |

后一层不能由前一层推断。任何报告必须说明证据停在哪一层。

### 8.3 内容同步

- 内容同步只能创建或复用合法的开放 `content-sync/*` PR；
- 自动化永不自动合并；
- 失败必须保留已推送分支、错误事实和手工比较入口；
- 本地删除不等于线上删除，必须经过版本化 `git rm`、推送、合并和线上消失核验；
- 发布、删除和恢复都必须携带内容版本或哈希，拒绝覆盖较新的 Markdown。

## 9. 产品与界面规范

- 保持 PC 优先、简单、直接、高效；
- 一个任务只保留一个明确主动作；
- 高频动作直接可见，低频设置进入侧栏、详情或“更多”；
- 状态名称描述事实，不描述内部实现步骤；
- 批量工作应集中一次人工复核，允许少数例外逐条覆盖；
- 不因功能存在就增加按钮，先证明它减少真实操作成本；
- UI 改动必须验证真实交互路径、键盘/可访问性和控制台/网络结果；静态断言不能替代浏览器证据；
- 只有布局或视觉合同确实改变时才更新截图基线，不能用批量更新掩盖回归。

## 10. 验证规范

验证范围按风险选择，但不得低于改动所触及的事实层。

### 10.1 发布助手改动

通常需要：

```bash
cd workflow
npm test
npm run test:browser
```

涉及恢复、R2 或真实进程时，再运行对应 doctor、备份、恢复演练或对账命令。浏览器用例不得依赖本机恰好存在的草稿数量，应通过 API fixture 构造所需状态。

### 10.2 站点改动

通常需要：

```bash
cd site
npm test
```

涉及交互时增加针对性的 Playwright 用例；涉及布局时运行 Linux 视觉基线；涉及部署配置时运行 `npm run check:deploy`。

### 10.3 所有改动

至少执行：

```bash
git diff --check
git status --short
```

合并前进行五轴审查：正确性、安全性、回归风险、可维护性、范围控制。发现失败时先定位根因，不放宽关键契约来换取测试变绿。

## 11. 文档规范

- 架构或难以逆转的决定写入 `site/docs/decisions/ADR-*.md`；旧 ADR 不删除，变更时由新 ADR 标记 superseded；
- 阶段事实、PR、验证结果和剩余风险写阶段收口文档；
- 长期反复适用的工作方式写入本规范；
- README 和 `PROJECT_HANDOFF.md` 只保留当前入口、边界和操作方式，并链接详细文档；
- 文档记录原因、取舍、证据边界和重新评估条件，不逐行复述代码；
- 任何数字、SHA、分支和线上状态都视为时间点证据，复用前必须重新核对。

## 12. 完成定义

一次开发任务只有同时满足以下条件才算完成：

- 目标和非目标清楚；
- 改动位于正确边界，没有扩大系统所有权；
- 验收条件通过，失败和未测项被如实记录；
- 差异完成五轴审查；
- 文档与实际行为一致；
- 只提交授权范围内的文件；
- 分支已 push，PR 状态和合并结果得到核对；
- 如声称上线，具有确切主分支、部署和线上证据；
- 临时 worktree 仅在干净且提交可恢复后清理；共享脏工作区保持不动。

## 13. 当前阶段的停止规则

截至 2026-08-03，已知 P0 开发项已经收口。下一阶段先完成 5–10 次真实自用发布循环，简单记录任务类型、卡点、额外补救和是否完成。在没有达到第 3.1 节门槛的新证据前，停止新增功能。

以下事项继续暂缓：批量 AI 标题流水线、语义重复工作台、远程 CMS、多用户后台、纯视觉重做和新的在线基础设施。重新评估条件见[下一阶段实施收口](NEXT_STAGE_IMPLEMENTATION_CLOSEOUT_2026-08-03.md)。
