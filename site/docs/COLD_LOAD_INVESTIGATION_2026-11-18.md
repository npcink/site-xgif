# 首次加载调查与候选修复

日期：2026-11-18。状态：候选修改，尚未合并或生产部署。调查基线／当前生产版本为 `3727e5f9c719a54c09caa5bcdc5681f96b4e784a`。

## 4.27 秒的含义

Cloudflare 当时的慢样本为 `/tags/哲学` 的一次中国 Windows Chrome 导航，约 4,266ms。窗口内访问量很小，不能据此判断所有用户普遍需要 4 秒。该值是整页加载时间，不是白屏时间，也不等于首次可操作时间。

[官方指标说明](https://developers.cloudflare.com/web-analytics/data-metrics/page-load-time-summary/)中的 Processing 包含资源等待，并非纯 CPU 时间；TCP 包含 TLS。面板各阶段的聚合百分位不能相加，也不能直接归到同一次慢访问。

同日正式站手机视口、无网络／CPU 限速的独立冷浏览器实测：图片页 FCP 1.90s、LCP 3.28s、load 4.68s，热访问约 0.25s；标签页冷访问 FCP 0.72s、LCP 0.87s、load 1.19s。各为少量诊断样本，不能代替真实访客分布。没有观测到布局偏移或 JS 长任务，不能将此推广为所有设备均不存在 CPU 瓶颈。

## 已复现的问题与修改

- 默认图片、文章、搜索和标签列表本已存在于静态 HTML，却被 `filter-init.js` 隐藏，直到筛选模块及依赖完成。阻塞筛选模块的浏览器回归在旧代码下立即失败（列表 `visibility: hidden`）。候选只在 URL 有有效搜索／筛选条件或大于 1 的页码时隐藏列表；保留原 4 秒失败回退。默认内容可以先显示，交互脚本稍后接管。
- 仅筛选页面在 head 提前声明 `filter.js`、`list-pagination.js` 和 `catalog-loader.js` 的 modulepreload。仍由现有构建流程统一改写为内容版本路径，模块不重复执行。新增依赖时要同步检查这份小型预加载清单；未预加载不影响正确性。不提前下载全文索引或卡片分片。
- 弹窗、复制链接、图集和首页筛选的经典脚本使用 defer，按文档顺序执行，避免阻塞后续 HTML 解析。早于脚本就绪的普通链接仍有原生导航能力。
- 390×844 视口的图片库首图约从 y=579 开始，确实进入首屏；仅该图使用 eager／high。其余图片、后续分页保持 lazy 和 `sizes=auto`。标签页首图约位于 y=3681，不提高其优先级。原图、尺寸候选、编码质量和动画契约不变。

## 本地继续优化：缓存克隆触发屏外图片请求

本节是在候选 `8f63508` 上的后续调查，仍属于 PR #103，尚未生产部署。上一阶段 GitHub 检查已通过：站点 76 项、工具 184 项、579 页链接、Linux 浏览器／视觉 136 项（另 2 项专用夹具按条件跳过）、专用图集 2 项与 dry-run 均成功，日志没有重试。以上不替代本节修改后的检查。

### 定位与决定

以固定构建快照，比较原加载顺序、主样式提前、主样式提前且其他 lazy 图片低优先级。每组交替测量 5 次，使用本地 HTTPS／HTTP/2、文本 gzip、150ms 模拟延迟、200,000 B/s 下载、100,000 B/s 上传、无 CPU 限速、新建浏览器上下文且禁用缓存。与前一节 HTTP/1 静态服务器实验的条件不同，不能跨表计算提速。

仅调整样式顺序的手机 FCP 中位数 568→548ms，LCP 568→560ms，load 5.303→5.370s；再降低其他图片优先级也没有减少请求数或流量。没有稳定、足够的额外收益，因此不提交样式顺序和图片低优先级的实验修改。

意外发现：启用 JavaScript 的手机图片页初次访问请求了 24 张图片，但屏幕只需首图，浏览器原生 lazy 预计还会预取附近几张。关闭筛选模块后只有 4 个图片请求；关闭瀑布流模块仍有 24 个。定位到 `createCatalog` 为缓存卡片执行的 `card.cloneNode(true)`：即使克隆节点没有插入页面，当前文档仍可能对其图片发起请求。

修复将已有静态卡片序列化到 `<template>` 的惰性内容中保存，恢复所选卡片时再克隆并插入列表。模板中的图片不会为缓存自行下载，继续使用原生 lazy；不引入新的 IntersectionObserver 加载器、占位图、额外运行服务或依赖。卡片顺序、DOM 内容、筛选、分页、原图和无 JavaScript 的普通链接不变。禁用 JavaScript 时浏览器可能主动关闭原生懒加载，不将该模式的图片请求数当作本修复的指标。

## 搜索请求链与过期任务（候选后续，尚未部署）

### 已复现与修复

- 冷搜索原先等待轻量目录返回，才请求全文索引；两份文件独立，可并行获取。现在只有确实需要关键词匹配时才并行启动目录和全文请求。普通浏览、翻页和纯图片类型筛选仍不提前下载全文索引。
- 原来的过期检查只在全部卡片准备好后阻止替换页面，却未阻止旧查询继续下载卡片。现在在匹配结果返回后、每批卡片请求开始前及克隆卡片前核对查询版本。失效任务不再安排后续分片，也不再构造无用节点。
- 已发出的请求继续完成并进入现有缓存，不强制 abort。其他查询或重试可能共享这些请求；只有后续尚未发出的工作被取消。每组最多同时请求 4 个卡片分片的上限不变。

旧代码上的三项回归已确认失败：阻塞图片目录时全文请求尚未启动；输入“无语”后在索引响应前改为“CUP 5080”，旧词仍请求 4 个卡片分片；“学习”的首批 4 个文章分片等待期间改成无结果词，旧任务仍继续请求后续分片。修复后定向桌面／手机 10 项通过，覆盖并行启动、过期结果、批次停止、缓存复用和原有失败重试；又补充了目录失败时复用尚在下载的全文请求的回归。
