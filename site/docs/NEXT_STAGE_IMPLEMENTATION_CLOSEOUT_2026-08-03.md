## 结论

本轮建议已经按“先解决真实阻塞，再做小范围体验收口”的顺序完成。当前项目继续采用 Astro 静态站点、Markdown 内容和本地发布助手，不切换 Hexo、Ghost 或其他 CMS，也不继续复制开源 CMS 的完整后台能力。

现阶段应停止扩展功能，转入真实自用验证。下一阶段的主任务不是再造一批界面，而是由唯一使用者实际完成若干次“导入或新建 → 复核 → 本地发布 → 同步 PR → 合并 → 线上核验”，记录最常重复、最影响完成率的摩擦，再只修排名第一的问题。

## 验证证据

每批均从最新 `origin/main` 建立独立 worktree，经过本地验证、差异审查、独立 PR 和 GitHub 检查后才合并。共享旧工作区中的未提交内容没有被重置、暂存或覆盖。

本轮执行过的主要验证包括：

- 发布助手：183 个 Node 单元/契约测试、HTTP 集成检查、21 个桌面浏览器场景；
- Astro 站点：首页修复通过构建、44 个 Node 测试、163 个生成页面的站内链接检查；
- 首页行为：桌面与移动两个 Playwright 项目均验证精选筛选、动态计数、全站搜索跳转和浏览器返回恢复；
- 所有 PR 的 `Astro site`、`Local publisher` 和 `Workers Builds: site-www-xgif` 检查通过；
- 每批均执行 `git diff --check`，并只暂存明确列出的源码、测试和文档；未提交 `workflow/records/*.jsonl`。

这些证据表示源码、CI 和 PR 构建检查通过，不等同于真实内容已经完成生产发布，也不替代人工线上验收。

## 明确没有吸收的方案

以下内容不是遗漏，而是基于单人自用和当前阶段主动拒绝：

- 不切换 Hexo 或 Ghost；迁移成本高于当前收益，并会破坏现有 Astro 展示、Markdown 数据和本地发布流程的协同；
- 不引入数据库型远程 CMS、账号/权限、多人审批、Webhook 编排或插件市场；当前没有对应使用者和运维需求；
- 不搬运旧分支中的批量标题对话框、批量 AI 资料流水线、语义重复工作台和大范围操作栏重排；这些会扩大状态、接口与测试面；
- 不进行纯审美首页重做，不批量更新视觉截图基线，不把内容变化伪装成 UI 改版；
- 不自动合并内容 PR，不以推送成功、HTTP 200 或 CI 绿色冒充“已上线”；
- 不为了“以后可能需要”提前建设多租户、在线编辑器、实时协作或复杂工作流。

## 当前剩余风险

1. 尚未以真实 ZIP 和真实文章连续走完整发布链；自动化覆盖不能证明实际操作没有摩擦。
2. 发布状态依赖 GitHub 与线上核验事实；网络不可用时会诚实显示未知，不能为了界面好看改成成功。
3. 原共享工作区仍保留用户未提交的历史改动与运行记录；本轮没有擅自清理。后续应先识别其是否仍有独立价值，再决定归档或删除。
4. CI 通过只说明候选构建正常；若要声称生产可用，仍需对合并后的确切主分支提交执行一次真实发布和线上检查。

## 下一阶段建议

### 主攻任务：完成真实自用闭环

先完成至少 5 次、最好 10 次真实内容循环，混合覆盖：

- 新建文章；
- flomo ZIP 导入并处理异常项；
- 插入或复用图片；
- 本地发布和质量检查；
- 同步内容分支并打开 PR；
- 合并后确认线上内容与素材可访问。

每次只记录四项：任务类型、卡住的位置、额外点击或手工补救、最终是否完成。不要先建设新的埋点、反馈系统或看板；一份简单日志即可。

### 修复门槛

只有满足以下任一条件，才进入下一批开发：

- 同一个问题在至少 2 次真实循环中重复出现；
- 问题会导致内容错误、来源失真、覆盖新版本或无法恢复；
- 问题使完整发布链不能完成；
- 一个小改动可以稳定减少每次都要发生的重复操作。

未达到门槛的想法记录到待观察清单，不立即实现。

### 暂缓事项的重新评估条件

- 只有真实内容量使标题整理成为持续瓶颈，才评估批量标题候选；
- 只有疑似重复内容频繁越过现有指纹和人工复核，才评估语义重复工作台；
- 只有异地编辑或第二位稳定编辑者出现，才重新评估 Ghost 或其他远程 CMS；
- 只有当前 Astro 展示层持续阻碍内容目标，才讨论生成器迁移；
- 只有首页真实使用数据显示发现路径有问题，才启动视觉或信息架构重做。

## 工作审视报告

### 做对的部分

- 把“是否更换 CMS”转化为当前工作流的具体阻塞，而不是比较功能清单；
- 从庞大旧改动中重建五个可独立验证的小批次，避免一次合并数千行混合变化；
- 先完成事实链和发布安全，再处理导入效率、编辑器点击和首页表达；
- 保留用户共享脏工作区，不以清理方便为由覆盖历史工作；
- 对每个提议都使用单人项目的收益/维护成本门槛，明确拒绝了大量“看起来先进”的功能。

### 发现并纠正的问题

- flomo 契约测试最初仍锁定旧的“异常项永远不能直发”规则，已改为约束显式复核和最终字段重新校验；
- 新增浏览器测试首次使用多元素定位器执行单值断言，已改为同时验证两条分组值；
- 首页 Playwright 用例结束时仍有远程图片代理请求，已加入 `unrouteAll({ behavior: "ignoreErrors" })` 清理并在桌面、移动端重跑通过；
- PR #43 的普通合并命令在远端合并后因本机 `main` 被另一 worktree 占用而报错，随后核对 PR 状态和合并提交；之后使用不切换本地分支的 GitHub API 完成 #44 合并。

### 可以继续改进的执行方式

- 后续每批在开工前就写清楚“接受条件”和“明确不包含”，减少从旧分支比较时的上下文噪音；
- UI 变化应继续以真实任务路径测试为主，视觉截图只在布局确实变化时更新；
- 合并命令应默认适配多 worktree 环境，避免工具在远端成功后又因本地分支切换失败而产生含混结果；
- 下一轮不应继续以功能数量衡量进度，而应以真实发布循环的完成率、错误率和重复摩擦衡量。
